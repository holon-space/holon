## Bug

Keystone smoke logged a `send_raw_keystroke(enter)` failure whose message
named `split_block` and "Block not found" (verbatim signature confirmed
against `crates/holon-integration-tests/src/pbt/driver_input.rs:565`):

```
[PressKey] send_raw_keystroke(enter) failed: ... split_block ... Block not found
```

**This is not a new signature.**
`docs/Testing/bugfunnel/entries/2026-07-10-creation-slot-after-commit-stale-text.md`
already records, as its second of two defects: "Enter in the slot also
dispatches `split_block` on the nonexistent `__virtual:` id ('Block not
found')". That is Enter + `split_block` + "Block not found" — the same
string family as this sighting, and a materially closer match than
`2026-08-24-split-block-indent-no-previous-sibling` (a mis-armed slash-command
menu dispatching `block.indent`, refusing with "no previous sibling to
become parent" — a different dispatched operation and a different refusal
message).

The 2026-07-10 entry's remedy section states that defect was FIXED overnight
2026-07-11: Enter capture was gated on `RowOrigin::is_creation_placeholder`
so it dispatches exactly one `commit_creation_slot` create instead of
unconditionally chaining into `split_block` on the virtual id. It also names
a follow-up wart left open at the time — "slot's per-keystroke Change handler
still dispatches `set_field` against the virtual id" — which is a different
dispatch (`set_field`, not `split_block`) and does not by itself explain a
2026-08-24 recurrence of the split_block string.

Separately, `crates/holon-frontend/src/user_driver.rs:695-700` (in
`commit_creation_slot`, immediately before its own 3s liveness wait) documents
the same general race by name: "A driver that writes the instant focus moves
would race ahead of the create and see 'Block not found'." That comment is
about a driver skipping the wait for the newborn's row to land — a plausible
mechanism for this signature, but not the one the 2026-07-10 fix addressed
(that fix was in production Enter-capture logic, not in a driver's create/
wait ordering).

The raw log and the specific case/seed for this 2026-08-24 sighting did not
survive a session restart; only the orchestrator's adjudication note
(signature, A/B method, dates 2026-08-24/25) is available.

## Root cause

Not diagnosed. Adjudicated DRAWN by A/B: rerun at the landing lane's tip and
at the base arm both came back green (4/4), so this occurrence was not caused
by the lane under test. That is orthogonal to whether the underlying
mechanism is: (a) the 2026-07-10 defect regressing (its fix's own follow-up
wart shows the surrounding code was known to be incompletely hardened), (b) a
distinct edge of the driver-vs-birth race the `user_driver.rs:695-700` comment
names, generated by a different keystroke path than the one that comment's
own 3s wait guards against, or (c) something else entirely. No generic
"concurrent mutation" guess is offered here in place of these — the two
concrete, code-grounded candidates above are strictly better leads than that.

## Missing piece

The specific case/seed is gone, so there is no way to tell which candidate
mechanism (or another) produced this run. Making it attributable would need
either the failing case's seed captured before rotation, or a keystone hook
that dumps the operative block ids and the driver's resolved split target at
the moment `send_raw_keystroke` dispatches — which would show directly
whether the target block ever existed, was a stale virtual id, or vanished
mid-flight.

## Remedy

OPEN in the sense that the mechanism is undiagnosed. UNCLASSIFIED rather than
NOTED: the A/B clears the landing lane, but a materially close, previously-
FIXED defect sharing this exact signature means "drawn and done" would
understate the possibility of a regression. If this signature recurs, capture
the case's log before rotation and check first whether
`RowOrigin::is_creation_placeholder` gating (the 2026-07-10 fix) still holds
on the path that produced it.
