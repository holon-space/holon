THE PRECONDITION THIS LANE DID NOT LAND, and the measurement that stopped it
================================================================================
The task asked navigation.focus to refuse a block_id that "does not parse as an
entity URI OR does not exist". The parse/shape half landed. The EXISTENCE half
was implemented, measured, and REVERTED — it is escalated, not forgotten.

What was built: a `block_exists.sql` probe of `block_raw` (base table, not the
matview, so a create->navigate chain sees its own insert) run before the history
write, refusing with "no such block".

What it did to the windowed suite (the whole reason it is not in the diff):

    thread 'benchmark_windowed_per_case_boot_cost' panicked at
    crates/holon-app/src/wiring.rs:453:22:
    boot [component=session stage=session-resolve]: seed_default_layout failed:
    Operation 'focus' on entity 'navigation' failed: navigation.focus: refusing
    'block:journals' as a main focus target - no such block. Focusing it would
    render an EMPTY panel with no error.

    Summary 153/266 tests run: 140 passed, 13 failed
    (every failure a windowed test that boots the app; all 13 the same message)

WHY, root-caused rather than guessed (scout read, file:line):
  - `block:journals` IS a real first-class block, not a synthetic target:
    crates/holon-frontend/src/lib.rs:101-137 builds it (`JOURNALS_PAGE_ID`,
    `set_page(true)`), and seed.rs:74 seeds "the journals machinery ...
    regardless".
  - In the LORO arm the row does not exist YET at focus time.
    `ordering.create_in_tree` (crates/holon/src/core/sql_block_operations.rs:577-601
    -> crates/holon-loro/src/block_cell_registry.rs:796) writes only the Loro
    tree; seed.rs's SQL insert branch (:125-148) runs only when persisted ==
    false, i.e. SqlOnly.
  - crates/holon-app/src/wiring.rs:446-473 then projects the seeded layout into
    `block_raw` AFTER `seed_default_layout` returns, by its own comment:
    seed_default_layout "does not itself project to SQL". So boot focuses a
    block whose SQL row lands strictly later. SqlOnly is unaffected.
  - The invariant is nevertheless SEMANTICALLY right: assets/default/index.org:26-45
    inner-joins `block b ... JOIN focus_roots fr ON b.id = fr.root_id`, so a
    focus root with no block row renders empty by construction.

So this is a BOOT-ORDERING fork, not a link-click bug, and its remedy touches
every boot in the Loro arm: either hoist the wiring.rs:463 SQL flush above the
focus dispatch, or split the focus out of `seed_default_layout` to after it, or
make the Loro-arm seed mirror rows synchronously the way the SqlOnly branch
does. Out of scope here; escalated with this evidence.

It is PINNED, not merely written down: the last assertion of
`focus_refuses_a_target_that_names_no_block` focuses
`block:00000000-0000-4000-8000-000000000000` and `expect`s SUCCESS with the
message "KNOWN HOLE: a nonexistent block: target is still accepted (existence
unchecked)". The day existence is enforced, that line flips expect -> expect_err.

Incidentally disclosed by the same measurement: on a Loro-arm first launch the
main panel's very first focus root is a block SQL cannot yet join, so the
opening frame is empty-by-construction until the flush lands. Not triaged in
this lane.
