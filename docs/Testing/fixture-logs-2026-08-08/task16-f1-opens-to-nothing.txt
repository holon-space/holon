clicking the trailing chevron on the `2026-08-08` nested-page row flips the

UNEVALUATED[expand_toggle_content] node with a `live_query` node — and the two

the truth.

========================================================================
WHY THE #16 PBT WAS GREEN THROUGH THIS

The #16 windowed test already clicked the REAL chevron at measured bounds
through the production `on_mouse_down`. It asserted:
  - the gate `Mutable` flipped,
  - `materialize_if_gated()` returned Some,
  - the chevron painted the open glyph.
All three are true in the broken app. They are facts ABOUT THE AFFORDANCE, not
about the affordance's RESULT. Nothing asserted a painted descendant row.
That is the ORACLE gap, and it is the primary classification.

The secondary ENVIRONMENT gap is why the shared harness could not have caught
it either. `support::TestServices::watch_query_live` (frontends/gpui/tests/
support/mod.rs) returns

    ReactiveView::new_static_with_layout(rows, CollectionVariant::list(0.0))

whose `items` are ALREADY populated at construction and whose `start()` is a
documented no-op for static variants (reactive_view.rs:928-940). A canned
`live_query` therefore paints with NO driver at all. Production's is
driver-backed: `items: MutableVec::new()` — empty until the driver the shell
starts fills it. A fixture built on the canned watcher paints rows that
production would still be waiting for, and cannot expose a 0-px shell.

So the harness was made prod-faithful BEFORE the red was allowed to count.

========================================================================
THE PROD-FAITHFUL FIXTURE

`an_opened_nested_page_paints_its_children` (frontends/gpui/tests/
nested_page_chevron_gate.rs) uses:

  * the REAL `embedded_page` content shape — a `live_query(#{prql:
    "from descendants", item_template: tree(...)})`, not the static `text`
    the round-1/2 tests used;
  * a DRIVER-BACKED collection: rows live behind a `ReactiveRowProvider` and
    `ReactiveView::new_collection`, so they reach `items` only once the driver
    runs — and the fixture's `watch_query_live` calls `start_reactive_views`
    on the tree it returns, mirroring `ReactiveEngine::watch_query_live`
    (reactive.rs:2727);
  * the gate and materialisation assertions as PRECONDITIONS, so a failure
    can never be misread as "the toggle did not flip".

LOCALIZATION — three probes, each ruling out one explanation

1. Is the shell even mounted?  Probe printed
     [probe] watch_query_live CALLED
     [probe] materialised widget = Some("live_query")
     [probe] props = ["query_context_id", "render_expr", "query_lang", "query"]
   So the node carries every prop `live_query::render_placed` needs, and the
   ReactiveShell IS created. Not a missing-props fallback.

2. Is it a timing artifact of the harness?  Twenty rounds of
   `sleep(50ms) + run_until_parked() + bounds.flush()` — a full second of real
   settling, matching the dogfood's 4s:
     [probe settle 0] painted = ["▼", "A Nested Page"]
     ...
     [probe settle 19] painted = ["▼", "A Nested Page"]
   Rows never arrive. Not timing.

3. Is the data there?  Reading the view's own items beside the painted set:
     [probe settle 0] view_items=Some(2) painted = ["A Nested Page", "▼"]
     ...
   DECISIVE: the driver ran, the collection HOLDS BOTH ROWS, and none of them
   paint. The loss is in the render, not in the data or the query.

========================================================================
ROOT CAUSE — a 0-px shell, with the precedent already in the tree

`expand_toggle`'s container is content-sized:

    let mut container = div().w_full().flex().flex_col();

and it rendered its materialised content through the generic `super::render`,
which gives a `live_query` the `Panel` shell shape: `size_full` plus
`height: relative(1.0)`. A percentage height has nothing to resolve against in
a content-sized flex-col parent, so the shell resolves to 0 px and takes every
row with it — painted geometry for the rows never exists.

This is not a new diagnosis. `live_query::render_content_height`
(frontends/gpui/src/render/builders/live_query.rs:30) exists precisely for it,
and `column::render` (column.rs:180-196) already routes a `live_query` child to
it with a comment naming the same failure ("has no definite height to resolve
against and collapses to 0 px, taking the whole section with it"). Also
`accordion::render_bounded`, which solves it the other way by pinning a
definite height first. `expand_toggle` was the one lazy container that never
adopted the routing.

FIX (frontends/gpui/src/render/builders/expand_toggle.rs):

    let content_el = if content.widget_name().as_deref() == Some("live_query") {
        super::live_query::render_content_height(&content, ctx)
    } else {
        super::render(&content, ctx)
    };

CORRECTION TO THE #16 RESIDUAL (it was wrong in the other direction)

The round-2 residual said the `HeadlessBuilderServices` gap means "MCP
describe_ui reports every toggle closed regardless of what the user opened".
The dogfood contradicts that: describe_ui reported the toggle OPEN and the
live_query node PRESENT while the window painted nothing. Whatever the
headless-services gap costs elsewhere, it did not manifest as under-reporting
here, and the residual must not be read as "describe_ui under-reports toggles".
The accurate statement is narrower: `HeadlessBuilderServices` implements
neither `block_expanded_view` nor `set_block_expanded_view`, so a toggle driven
purely through that surface has no view-store seed to read — untested either
way, and NOT the behaviour observed in the live app.
