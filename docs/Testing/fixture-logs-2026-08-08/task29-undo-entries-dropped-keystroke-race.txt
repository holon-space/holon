§2  ROOT CAUSE

  crates/holon-frontend/src/operations.rs:39
      dispatch_operation spawns one un-awaited task per keystroke.
  crates/holon/src/core/sql_operation_provider.rs:2401,2471
      set_field reads the prior content in a statement separate from its UPDATE;
      a keystroke that interleaves there captures a prior value already superseded,
      so the stored inverse skips a character.
  crates/holon/src/api/operation_engine.rs (leaf dispatch → undo push)
      the entry is pushed after the dispatch returns, i.e. in COMPLETION order,
      so the stack order need not match the write order; and the multi-character
      deltas that the stale prior produces are not word-boundary-coalescible
      (holon-core/src/undo.rs classify_delta), which is why undo moved ~1 char
      per press instead of one word group.
  crates/holon-core/src/undo.rs:53-66
      verify_precondition then LEGITIMATELY fails, and the entry is dropped.

The drop is the correct behaviour of a correct staleness check reading a history
that was recorded wrong. The bug is upstream of the check.

§4  FIX

crates/holon/src/api/operation_engine.rs — `EntityWriteLocks`: capture-prior /
write / journal is ONE step per entity, striped over 64 fair
`tokio::sync::Mutex`es keyed by (entity, id). Acquired after the compound
interceptors, so a compound's constituent dispatches each lock their own target
and no hold nests on the same entity; `replay` takes the same lock so an
undo/redo write queues behind in-flight writes instead of interleaving.

§6  DISCLOSURE

MCP already answered `success:false` with a reason (frontends/mcp/src/tools.rs)
— the dogfood pass drove undo through a script that discarded the reply, which
is why it read as silent — but every surface described a PERMANENT loss as a
retryable failure: the GPUI toast said "Undo/redo failed" (the press did not
work), MCP said "Undo skipped (stale)" (try again).

All three now read `holon_api::undo_step_dropped_detail`, beside `UndoOutcome`
itself: "<undo|redo>: history step dropped — this edit can no longer be undone
(<engine reason>)". The GPUI toast carries its own `DegradedKind::UndoStepDropped`,
so a lost step never shares a kind with a press that merely failed. The ROUTING
is pinned, not only the words: `undo_disclosure` maps outcome → (kind, detail),
and `stale_dropped_entry_routes_to_its_own_kind_and_discloses_the_lost_step`
reds when the kind is reverted (mutant D2, lane-logs/29r2-mutD2.log).

ROUND 2 — the verifier's refutations and what they changed
=====================================================================

§7  COMPOUND BYPASS (the load-bearing one)

The round-1 acquisition-site comment claimed a compound's constituents
"re-enter this method" and take their own stripes. True for
instantiate_template and accept_proposal; FALSE for the two compounds that
matter:

  dispatch_constituent       → dispatcher.execute_operation directly; used by
                               run_convert_block_to_page for create /
                               move_block / set_field(marks) /
                               rewrite_link_resolution
  dispatch_merge_constituent → same shape; used by run_merge_blocks for
                               set_field(content) on the canonical

Neither compound took any stripe, so its planner read and its constituent
writes straddled in-flight writes to the same block, and its composite entry
was pushed outside every hold — the identical class the singles fix closed.
turn_into_page is the chord task #28 made reachable from a live window while
typing.

FIX: each compound takes the stripe of the block it REWRITES — `target` for the
block→page transform, `canonical` for the merge — across planner read,
constituents and composite push. Constituents keep dispatching straight at the
dispatcher, so the hold never nests: at most ONE stripe is held at a time
anywhere in the engine, which is what keeps the striping deadlock-free without
a lock order.

DISCLOSED SCOPE: only the rewritten block is held. A convert's minted page,
re-homed children and re-pointed linkers, and a merge's duplicate and moved
children, get no stripe — holding several would need the acquisition order this
design deliberately avoids.

§9  M2 IS NOW UNREPRESENTABLE

Every scheduling probe for M2 survived — a uniform forced pause (any pause at
the same point in every writer delays them all equally) and a
state-synchronized racer both left it green. The position is therefore enforced
by the type instead: the push goes through

    journal_step(&self, _held: Option<&MutexGuard<'_, ()>>, entry) -> Result<()>

and releasing the stripe first no longer compiles:

    error[E0382]: borrow of moved value: `write_guard`
      drop(write_guard);                            value moved here
      self.journal_step(write_guard.as_ref(), ...)  value borrowed after move

(lane-logs/29r2-mutM2-compile.log). The behavioural probe written for M2 was
DELETED rather than kept green-forever: no mutation could kill it.

§10  RESIDUAL FOUND WHILE BUILDING THE CONVERT RED

A content `set_field` schedules a DERIVED marks write that runs AFTER the op
returns — outside the journaled step and outside the stripe. Mixing typing with
marks writes on one block produced `found Some(Null)` marks with no undo entry
accounting for them. Not fixed here and not the same fix; filed as a follow-up.
