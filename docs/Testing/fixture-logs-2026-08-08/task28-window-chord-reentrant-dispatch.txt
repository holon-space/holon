§D — ROOT CAUSE
---------------
The COMPILED gpui is the Holon fork, git+https://github.com/holon-space/zed.git
?branch=holon at 44506e18 (Cargo.lock "name = gpui" / version 0.2.2). Line
numbers below are that tree's; a gpui upgrade must re-verify them there.

gpui App::update_window_id (crates/gpui/src/app.rs:1561-1602) starts with

    let mut window = cx.windows.get_mut(id)?.take()?;          // :1566

and only puts the window back in its `trail` at the end; the failing `?` picks
up its message from `.context("window not found")` at :1602. Global
`cx.on_action` listeners are invoked from Window::dispatch_action_on_node
(crates/gpui/src/window.rs:4729) — ours in the BUBBLE phase at :4802 — i.e.
while that `take()` is in effect, so a handler that calls
`cx.update_window(wh, …)` re-enters the emptied slot, gets None, and the `?`
turns it into Err("window not found").

Holon's window-registry handlers (frontends/gpui/src/lib.rs):

  undo / redo          share_ui::dispatch_undo → rt_handle.spawn + cx.spawn;
                       the window hop runs on the executor AFTER dispatch
                       returns                                    → always worked
  open_search          synchronous cx.update_window inside on_action → ALWAYS failed
  cycle_tab_next/prev  synchronous cx.update_window inside on_action → ALWAYS failed
  jump_to_tab_1..9     synchronous cx.update_window inside on_action → ALWAYS failed
  turn_into_page       element-level capture_action; the handler is handed
                       `&mut Window` directly                     → always worked

12 of the 15 published chords were broken; the 3 that worked are exactly the
3 that never re-enter the window.


§E — FIX
--------
* cycle_tab_* and jump_to_tab_* (11 chords): the window hop was pure ceremony —
  tab_strip::apply_cycle / apply_jump take `&mut App` and the closure's `window`
  parameter was `_window`. They now run directly on the dispatch-time `&mut App`.
* open_search (1 chord): genuinely needs a `Window` (it focuses the modal's
  input), so the hop is wrapped in `cx.defer`, which GPUI documents as running
  "at the end of the current effect cycle, allowing entities that are currently
  on the stack to be returned to the app".

Audit: every other `cx.update_window` in frontends/gpui/src is reached through
an `AsyncApp` inside a spawned task (share_ui, breadcrumb, tab_strip's query
pump, search_ui, input_box, editor_view, oracles_ui, the interaction pump) or
holds a real `Window` already. These three were the only synchronous
re-entrant sites.


§F — RESIDUAL, DISCLOSED
------------------------
Real-keypress equivalence is established by CONSTRUCTION, not by a hardware
press: the failure is in GPUI's action-dispatch re-entrancy, downstream of how
the keystroke arrived, and the windowed rung drives the real dispatch tree
rather than the MCP tool layer. A hardware cmd+k on a live build was not
performed in this lane (no interactive session available), so that last step
remains unobserved.

The cmd+] / cmd+2 presses run against a tab strip with fewer than two tabs, so
they assert "the handler reached its window", not "the active tab changed";
`navigation.activate` fan-out on a multi-tab strip has no coverage here.

cycle_tab_* / jump_to_tab_* now settle Succeeded unconditionally and have no
failure channel at all: dispatch_intent is fire-and-forget returning (), so the
journal entry attests that the handler RAN, not that the tab changed — a
downstream navigation.activate failure would still read Succeeded.

If the window dies between dispatch and the effect flush, open_search's entry
stays Pending forever where the pre-fix code settled Failed. That degrades to
"unknown", never to false success: key_chord_report's
`an_unsettled_outcome_is_reported_as_pending_never_as_success` pins the reply
side of that.
