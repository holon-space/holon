WHICH STORE IS AUTHORITATIVE, AND WHY IT IS NOT `collapsed`

Option (a) — "seed the gate from the `collapsed` field the handler already
writes" — was considered and REJECTED on the code's own documented grounds:
a block row's default `collapsed = 0` means "not explicitly folded", NOT
"auto-expand this lazy section" (shadow_builders/expand_toggle.rs states this
above the gate). Seeding from `collapsed` would therefore open every nested
page on first paint — the failure the 2026-07-16 ledger row
"Nested pages are NOT collapsed by default" already records, and the reason
the lazy gate defaults closed at all. `collapsed` also belongs to the OTHER
affordance on the same row: the leading `tree_item` disclosure chevron, kept
deliberately separate from the trailing one (double-chevron ruling
2026-07-21).

So the view-local expansion store stays the gate's authority (2026-07-16
Option B) and the fix is that EVERY writer writes it:

  crates/holon-frontend/src/reactive.rs
    BuilderServices::set_block_expanded_view — the write half of the
    pre-existing `block_expanded_view` reader; engine impl delegates to
    `UiState::set_block_expanded_view` (which bumps `viewport_generation`).
  frontends/gpui/src/render/builders/expand_toggle.rs
    the chevron handler records the click there, beside its unchanged
    `set_field("collapsed")` dispatch (document state, 2026-07-11 ruling).
  crates/holon-frontend/src/shadow_builders/expand_toggle.rs
    the live-follow subscription records EXTERNAL `collapsed` changes there
    too — otherwise a rebuild would undo a remote fold exactly as it undid the
    local click.
  crates/holon-frontend/src/user_driver.rs
    DirectUserDriver::set_block_expanded writes it in BOTH branches. The
    mounted-gate branch previously wrote only the `Mutable` + `set_field`, so
    the harness and production disagreed about the store; now the driver
    writes nothing production does not.

OBSERVABILITY (part of the ENVIRONMENT fix, added BEFORE the red): the
trailing chevron registered bounds but no `displayed_text`, so open-vs-closed
was unreadable from a painted frame — a test could see the element and not its
state. It now records its glyph and its vm node, like `tree_item`'s chevron
does, which is what lets the red assert the painted ▼/▶ rather than only the
in-memory gate.

THE DEFECT THE VERIFIER FOUND

Round 1 propagated BOTH `collapsed` edges into the view store:

    follow_services.set_block_expanded_view(&follow_target, !collapsed);

`collapsed` belongs to the LEADING `tree_item` chevron (the outline fold). So:

  embedded-page row folded
    -> user clicks the LEADING chevron to unfold the OUTLINE
    -> set_field(collapsed = false)
    -> live-follow writes set_block_expanded_view(id, true)   <-- DURABLE
    -> next structural rebuild opens the TRAILING nested-page gate and
       eagerly materialises a subtree nobody clicked, persistently.

That is exactly the "auto-expand every nested page / unbounded eager load"
class this file cites as the decisive reason to REJECT option (a). Round 1
rejected seeding from `collapsed` at build time and then reintroduced it at
edge time, with durability. The fold direction (0->1 -> store=false) is
correct and intended; only the unfold direction is harmful.

   every expand_toggle closed regardless of what the user opened. Pre-existing,
   and it matters because dogfood-explorer reads exactly that surface. It does
   NOT fan in cheaply: HeadlessBuilderServices holds an Arc<BackendEngine>,
   which has no UiState - UiState lives on holon-frontend's ReactiveEngine - so
   wiring it means threading a UiState through holon-app's describe_ui
   construction sites. Left flagged rather than done blind.
