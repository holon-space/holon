MECHANISM (read off the code, confirmed by the reds below)

  1. The `focus_roots` matview projects `(region, root_id, added_ts,
     history_id)` — crates/holon-turso/sql/schema/matview_focus_roots.sql.
     There is NO `id` column and no `parent_id`.
  2. `LiveData::subscribe` built its delivery list by reading `id` and
     `parent_id` off every changed row. For a focus_roots batch BOTH are
     absent, so the batch produced ZERO delivery pairs and `rows_delivered`
     early-returned on `deliveries.is_empty()`. A navigation's own delivery
     reached the correlator as nothing at all.
  3. The navigate entry therefore stayed pending. Any later edit ANYWHERE
     under that page delivers the child's `parent_id = page_id` as a tokenless
     block-row entry, which close rule 2 (newest-per-target) accepted — closing
     the navigate and billing it every millisecond since the click.

That is exactly the dogfood observation (11982ms for a navigation visible in
~100ms) and the 2026-08-07 latency-attribution FINDING 2 clock-bleed.

FIX: `Observable` (BlockRow(Option<WriteSeq>) | FocusRoot) is carried on BOTH
ends — what an interaction waits to see, and what a batch delivered. Matching
is scoped per (target, kind); a delivery of the wrong kind neither closes nor
supersedes an entry. `touched_entities` reads a focus_roots batch by its own
`root_id` column, keyed on the mirror's source name (not on the presence of a
`root_id` column — `blocks_with_paths` has one meaning "root ancestor").

POST-VERIFICATION AMENDMENTS — two remaining silent-failure shapes, closed.

(A) `Change::FieldsChanged` on the focus_roots mirror returned None SILENTLY
    while a missing `root_id` errored loudly — the just-fixed shape, one mirror
    narrower. DECIDED FROM THE MIRROR'S SEMANTICS, not handled speculatively:
    `focus_roots` is `navigation_history WHERE closed_at IS NULL`, so its rows
    are INSERTED and REMOVED, never partially patched, and a FieldsChanged
    carries the matview's rowid (the matview has no `id` column) rather than a
    block id — the delivered entity could not be named even if we chose to
    guess. So it is NOT treated as a delivery; it WARNs naming the change kind
    (`stage="e2e_delivery_unreadable" change="fields_changed"`, plus the
    entity_id and the field names). `Deleted` stays silent BY DESIGN and now
    says why in the doc comment: a delete means a root was CLOSED, and the
    navigation that replaced it arrives as its own Created row in the same batch.

(B) "Expires loudly" was pinned only on `prune_expired`'s RETURN VALUE — a change
    that dropped the `warn!` would have kept every pin green while the app went
    silent again. The disclosure now has ONE emission site (`disclose_expired`,
    used by both prune callers) and a pin that asserts the real `tracing` event.

WARM SWITCHES — the decision, per the 2026-08-07 row that left it open.

A navigation whose focus root does not change delivers no CDC batch at all, so
it has no observable. It is NOT given a substitute close condition: it expires
loudly as `stage="e2e_expired" action=navigate block=… waited_ms=…`. Pinned by
`a_navigation_that_delivers_nothing_expires_loudly`. Measuring a warm switch
needs a signal the pipeline does not emit today (a render/paint-side observable
for navigation); borrowing an unrelated batch's clock is precisely what this
lane removes. The 2026-08-07 warm-switch row stays OPEN as a feature request,
now with the alternative it must NOT take written down.

IDLE REAPER — `rows_delivered` now prunes before matching, so an expiry is
disclosed on the next delivered batch instead of waiting for the next dispatch
(the dogfood probes saw waited_ms≈56000 disclosures). A fully idle app still
runs no reaper: with the observable split a lingering navigate entry is inert
(only a focus-root delivery for the SAME page can close it, and newest-wins
supersedes it), so the residual is disclosure LATENCY, not a wrong sample.

NOT ADDRESSED (still open, unchanged by this lane): the secondary finding that
one 21-character type burst emitted ~14 `e2e action=set_field` lines for one
block from several subscribe_actor spans, so a p95 computed off this stream
double-counts single deliveries.
