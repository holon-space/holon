SITE 2 — ply. FIXED PER PATTERN. COVERAGE DISCLOSED HONESTLY.
==============================================================================

NO RED LOG EXISTS FOR THIS SITE, AND NONE WAS INVENTED.

Why: `frontends/ply` is an out-of-workspace crate (root `Cargo.toml` excludes
it; its own manifest carries a `[workspace]` table and a comment naming a
macOS 15+ SDK issue in its dependency chain as the reason). It has NO `tests/`
directory, no dev-dependencies, and no harness of any kind — its only entry
point is `#[macroquad::main]` in `src/main.rs`, i.e. a real window. There is no
seam through which a headless test could drive `build_query` today.

What the claim rests on instead (static, but not weak):
  * the defect is not behavioural inference — it is the literal
    `context_path_prefix: None` at live_query.rs:68 feeding
    `services.watch_query(...)`, the same engine entry point whose sentinel arm
    the MCP red above demonstrates end-to-end against a real engine;
  * the MCP red proves the mechanism on a real `BackendEngine` with real rows,
    so the shared consequence is measured, not assumed;
  * the ply builder's context construction was byte-identical to the MCP one
    that just red'd.

Fix applied (frontends/ply/src/render/builders/live_query.rs):
  * new `resolve_block_path(ctx, id)` mirroring the gpui helper — blocking
    `lookup_block_path` on a scoped, immediately-joined thread so `block_on`
    stays legal inside ply's synchronous immediate-mode render pass (the same
    shape `HeadlessBuilderServices::watch_query` already uses);
  * the `QueryContext` is now built INSIDE the `Entry::Vacant` arm. This is a
    behavioural requirement, not tidiness: ply re-renders every frame, and the
    prefix lookup is a blocking matview read. The watch-cache entry is what
    makes it once-per-query, exactly as the gpui fix used the entity-cache miss.
  * failure arms in ply's idiom:
      lookup failed -> `error_text(...)`, the crate's existing visible-failure
        widget (red 12pt text), same treatment as a compile failure;
      no query engine -> `tracing::warn!` naming the block and the consequence,
        then `QueryContext::for_block` (no prefix). Disclosed degradation, not
        a crash: `BuilderServices::query_engine()` legitimately defaults to
        `None` for a Loro-only session, and the gpui lane already rejected a
        version that panicked on this.
