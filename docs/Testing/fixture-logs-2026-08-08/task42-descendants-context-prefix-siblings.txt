TRIGGER: code exploration in the #16/#27 chevron lane. cd4cd93e fixed the gpui
builder and its commit message explicitly named sibling callers that pass
`context_path_prefix: None` into the same engine arm. Confirmed independently by
the #27 acceptance run, where `describe_ui` reported the nested page's rows as
UNEVALUATED/empty while the real window painted them.

MECHANISM (one sentence): `BackendEngine::bind_context_params`
(crates/holon/src/api/backend_engine.rs:470-481) binds the literal string
`"__NO_PATH__/"` for a `QueryContext` whose `context_path_prefix` is `None`, and
the `descendants` PRQL stdlib entry (crates/holon/sql/prql_stdlib.prql:3-8) is
`from block_with_path | filter (path | text.starts_with $context_path_prefix)`
— so every context-dependent `from descendants` built by such a caller matches
exactly zero rows, silently.

--- FIX -----------------------------------------------------------------------
frontends/mcp/src/describe_ui_expand.rs, EngineResolver::expand_live_query:
the context is now built from a resolved path
(`engine.lookup_block_path(&uri).await` -> `QueryContext::for_block_with_path`).
The expander is already `async` with the engine in hand, so no thread hop is
needed here (unlike the gpui builder's synchronous render pass).

Failure arms, in this frontend's idiom — the REPLY is the instrument, so a
degradation must be a field in the reply, not a log line:
  * lookup failed  -> `Err` naming the block and the consequence; the existing
    caller arm turns it into `ViewKind::Error` ("live_query expansion FAILED
    (<lang>): context path prefix lookup for block '<id>' failed, so
    context-dependent rows cannot be resolved: <cause> — query: <query>").
  * NO query engine (Loro-only) -> UNCHANGED and already correct: the very
    first statement of `expand_live_query` errors with "this session has no
    query engine (no-Turso frontend)", which the same caller arm turns into a
    visible `ViewKind::Error`. describe_ui cannot expand ANY live_query without
    an engine, so unlike the gpui builder there is no partially-degraded
    `Ok(None)` state to fall back to; the mode is disclosed as an error node,
    never as empty content. Deliberately not converted to `Unevaluated`: this
    matches the pass's existing contract for "expansion was attempted and could
    not complete".
