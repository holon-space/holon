4b — 4x "Shared edit saved - org file pending - block:<REDACTED>"
================================================================================

WHERE THE TEXT COMES FROM. Also a toast, not a tracing macro:
  frontends/gpui/src/share_ui.rs:1631-1635
      DegradedKind::SharedSubtreeNotMaterialized (amber /26A0)
      label "Shared edit saved - org file pending"
  frontends/gpui/src/share_ui.rs:308-315   detail carries the block id

WHAT IT MEANS. A block carrying a shared_tree_id whose OWNING PAGE is not a
registered shared-subtree mount. The shared content therefore owns no dedicated
org file and write-back cannot resolve a disk path:
  crates/holon-orgmode/src/di.rs:796-815   walk up to the owning page,
      found = current.is_share_mount(); if not a mount -> disclose
  crates/holon-orgmode/src/di.rs:633-645   live (non-seed) upserts only
  crates/holon-orgmode/src/di.rs:823-832 -> ShareDegradedDisclosure
      (crates/holon-app/src/loro_seams.rs:662-671) -> degraded bus

CONSEQUENCE: the edit is durable in Loro and SQL and syncs to peers, but the
on-disk org projection never catches up. There is NO retry and NO flush — the
doc comment states materialisation is not built yet, and no code path raises
the all-clear, so the condition holds for the whole session
(crates/holon-loro/src/degraded_signal_bus.rs:88-91). A repo-wide search for a
site that clears SHARED_SUBTREE_NOT_MATERIALIZED found none.

WHY "4x" IS NOT A RETRY LOOP. Disclosure is deduped once per shared_tree_id per
session (di.rs:816-822, set constructed once at di.rs:563-565) and the bus
upserts by (subject, kind) (degraded_signal_bus.rs:238-248). Four identical
lines therefore mean four renders of one sticky toast, or four distinct
shared_tree_ids — not four failed writes.

THE CORROBORATING LOG SIGNATURE, exactly 4 occurrences, on 4 DIFFERENT pages:

  WARN …:org.ingest_file{path=<VAULT-PATH>}: holon_filesystem::file_sync_controller:
    [FileSyncController] a `share-role` drawer property was found on a page that
    is NOT a registered shared-subtree mount — ingesting it as a normal file.
    path=<VAULT-PATH> page_id=block:<REDACTED>

That is the mechanism in one line: the on-disk `share-role` marker SURVIVES a
restart, but the share-mount REGISTRATION does not. On the next cold start the
pages are ingested as ordinary files, so every subsequent edit to their shared
subtrees is disclosed as "org file pending" and never written back.

The block id Martin quoted appears exactly once in the log, inside the
creates_ids list of the ORGSYNC_DIFF for one of those four files — i.e. it is a
block on a page that carries a share-role drawer and is not a registered mount.
That ties the toast to the four WARNs.
