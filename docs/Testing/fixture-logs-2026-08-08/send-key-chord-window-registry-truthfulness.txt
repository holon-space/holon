2. THE REPLY ITSELF, unit-tested per registry and per outcome
-------------------------------------------------------------
The classification is now a pure function, `holon_mcp::key_chord_report::classify`
(pressed, matched actions, journal entries) -> (status, detail), 7/7 green
(lane-logs/lane11-mcp-report-units.log). The cmd+z case is the first test:

    a_window_registry_undo_that_ran_is_executed_not_nothing_ran
        entries = [ window.undo -> Succeeded ], matched = ["undo"]
        => status "executed", detail None

    equivalent reply JSON for a cmd+z press:
      {
        "status": "executed",
        "detail": null,
        "keys": ["cmd","z"],
        "entity_id": "block:<id>",
        "matched":    [{"action":"undo","registry":"window","context":null}],
        "dispatched": [{"entity":"window","operation":"undo","target":null,
                        "outcome":"succeeded","error":null}]
      }

The other six pin the rules that keep it honest:
  - a matched action that FAILED reports dispatched_but_failed with the verbatim error
  - a failure anywhere in the press window outranks a matched success
  - an unsettled outcome reports dispatched_outcome_pending, never success
  - an empty press window is bound_but_not_dispatched
  - a press the driver declined is credited with nothing
  - a chord that ran a DIFFERENT action is dispatched_other_action


3. WHY THERE IS NO LIVE MCP REPLY CAPTURE HERE (disclosed, not skipped)
-----------------------------------------------------------------------
A live instance was booted for exactly this — throwaway sandbox, verified boot
line `Config dir: /tmp/holon-lane11/config, db: /tmp/holon-lane11/config/holon.db,
orgmode: Some("/tmp/holon-lane11/vault"), loro: false`, MCP on port 8712 (never
8520), later killed and the sandbox removed. Every send_key_chord call — with
the window fronted via System Events AND relaunched under
HOLON_GPUI_FORCE_ACTIVE=1 — fails BEFORE the reply is built:

  send_key_chord("block:4dca296c-...", ["cmd","enter"]): the chord is bound but
  the press failed: refusing to press KeyChord({Cmd, Enter}) into the wrong
  editor: GpuiUserDriver::send_key_chord: "block:4dca296c-..."'s editable_text
  never took window focus within 5s. Engine focused_block=Some("block:4dca296c-...");
  editors reporting window focus: []. The gesture reached the element but did
  not seat a caret, so any following keystroke would land nowhere (or in
  another block).

The driver refuses to press when no editor can take WINDOW focus, and in this
non-interactive session none can. So the tool errors instead of replying, for
EVERY chord — the reply cannot be captured from this session at all. This is
the same click-to-focus/window-focus gap already flagged by this lane (now with
a verbatim error string from the real GpuiUserDriver rather than only the
TestPlatform one), and it is the reason the coverage above is a windowed test
plus a unit-tested classifier rather than a live capture.
