# Pushing Holon's edits into a LogSeq DB graph (W2)

`kvs_writer::push(graph, base_before, base_after)` turns a `BaseDiff` into
tail transactions. Everything below was MEASURED against LogSeq 65.33 through
the oracle (see [LogseqDbOracle.md](LogseqDbOracle.md)); nothing here is read
off the source.

## What push writes

One transaction of two datoms per changed block — the retract of the stored
`:block/title` and the assert of the new one — appended to the tail and
flushed into the B+-trees through [B](LogseqDbTreeOrder.md) when the tail
crosses the branching factor. This is the same shape `ldb/transact!` writes;
`head_to_head_with_logseq_applying_the_same_pushes` holds it to that byte for
byte.

Scope is the title. Creation, removal, re-parent, re-order, tags,
`requires`, `contributes_to`, `advice_suppressed` and properties are each
refused by name. `out_of_scope_shape` destructures `BaseBlock` exhaustively,
so a field added to the base fails to compile rather than becoming a
difference push cannot see.

Every refusal is decided before a single datom is appended. A push applies in
full or leaves the graph exactly as it found it, and each refusal test asserts
the rows are untouched rather than only that an error came back.

## Two refusals that are not about scope

**Built-in pages.** LogSeq's outliner refuses to edit a built-in entity; its
storage layer does not. Holon writes the storage layer directly, so nothing
below `push` would stop it from rewriting the graph's own schema. Push refuses
them.

Holon replicates LogSeq's `outliner-validate/built-in-entity?`, which has
THREE legs and says in its own docstring that the flag alone is not enough:

| leg | fixture count |
|---|---|
| `:logseq.property/built-in?` | 179 |
| `:file/path` (`logseq/config.edn`, `custom.css`, …) | 5 |
| internal `:db/ident` (the `:logseq.kv/*` entries) | 8 |
| **total LogSeq calls built-in** | **192 of 213** |

Holon's first attempt implemented leg 1 only and found 179. It refused the
other 13 anyway — but only because all 13 happen to be untitled, so
`current_title` errored first. A guard that is correct by coincidence is not a
guard, and no behaviour test could see the difference: only comparing the
SETS could. `logseqs_own_built_in_verdict_matches_ours` does exactly that,
against a committed recording of LogSeq's verdict
(`tests/fixtures/logseq-db/built-in-entities.json`, regenerated by
`oracle/probe_built_in.cljs`) so the pin holds with no oracle installed and
moves only when LogSeq's own answer moves.

**A stale base.** The retract half of a replacement names the value it
supersedes. If the graph's current title differs from what `base_before`
recorded, LogSeq changed the block since the import, and pushing would either
retract a value that is no longer there or overwrite an edit Holon never saw.
Push refuses and asks for a re-import. The comparison is sound because the
importer copies `:block/title` into `BaseBlock::content` verbatim
(`project.rs`), so a mismatch is a real divergence and not a projection
artifact.

### The ident leg is a measured APPROXIMATION, and says so

LogSeq's `internal-ident?` is a MEMBERSHIP test over the idents it declares
plus the ones it mints at runtime — not a namespace rule. Same namespace,
opposite verdicts: `:block/title` is internal, `:block/uuid` is not.

Exact membership was tried and rejected BY MEASUREMENT: LogSeq's declared
schema set holds 146 idents and misses 35 of this graph's 171 — every
`:logseq.kv/*` and every closed-value ident, created at runtime — including
all eight entities that are built-in by the ident leg alone. Matching on the
declared set would make those PUSHABLE: an under-refusal, the direction that
loses data.

So Holon keeps a namespace rule over `block` and `logseq*`, and records what
it costs. Of 191 measured idents, **182 agree exactly and all nine
disagreements are OVER-refusals** — Holon calls internal something LogSeq does
not, so push declines an edit LogSeq would allow. Never the reverse.

| divergence | why it is kept |
|---|---|
| `:block/name`, `:block/tx-id`, `:block/uuid` | LogSeq calls 13 of the 16 declared `block/*` idents internal. Dropping the arm to avoid these three would UNDER-refuse those 13. |
| `:logseq/foo`, `:logseqfoo/bar`, `:logseq-plugin/x`, `:logseq.thirdparty/x`, `:logseq_x/y`, `:logseqified/x` | third-party namespaces that merely begin with "logseq" |

The `block` arm was briefly DELETED on the grounds that it was "measured
unreachable", and that was wrong twice over. Unreachable described the
FIXTURE'S DATA, not the predicate: a constructed entity whose only evidence is
`:block/title` drives it directly. And the justification counted only the
three idents the arm gets wrong while omitting the 13 it gets right. Since
`is_built_in` is `pub`, a caller reaching an entity push cannot reach would
have got the permissive answer with nothing in the text to warn them. Fail
closed: over-refusing is visible, under-refusing rewrites LogSeq's schema
silently.

No base-reachable entity is built-in by a `block/*` ident alone — every such
entity in this graph also carries the flag, so leg 1 answers first — which
makes the arm a guard against future reach rather than a live path. It is
driven in tests by a constructed entity, never by fixture data.

`internal-ident-reference.json` holds LogSeq's verdicts for all 191 idents,
obtained by CALLING `internal-ident?`, and the test compares every one with no
skips.

### What is closed by CONSTRUCTION and what is closed by this fixture's DATA

Worth separating, because three claims in this document were originally
written as though the second were the first.

**Construction-closed.** Orphan exclusion: `datoms_now` walks the reachable
eavt tree, so datoms stranded in unreferenced rows cannot enter the reader at
all. This holds for any graph, not just this one — an orphan that DID carry a
uuid would still be excluded, because reachability is what decides, not the
shape of the datom.

**Fixture-closed, with residual risk named.** The `root.schema`
cardinality-many coverage: all 19 of this graph's cardinality-many attributes
are declared in the root, asserted by test. That is a fact about THIS graph.
A graph whose root omitted a many-attribute would route it into the
cardinality-ONE supersede path and silently drop values, and nobody has
established whether such a graph can exist. Open, W3.

**Not measurable at all, and stated as such.** `a_bare_cardinality_one_assert_
supersedes_rather_than_accumulating` rests on what cardinality-one MEANS, not
on an observation: LogSeq's transactor will not emit a bare assert on a
cardinality-one attribute — verified twice, including through the explicit
`[:db/add …]` vector form — so there is no graph to read the answer off.

### Tail replay is cardinality-aware, and resolves by POSITION

Measured against LogSeq, both directions:

| tail carries | LogSeq restores |
|---|---|
| `:block/tags {3}` + assert 5 | `(3 5)` — a many-assert ADDS |
| the above + retract 3 | `(5)` — a retract removes ONLY the named value |
| two sessions, both editing one title, no store between | the LATER value, with BOTH transactions carrying the SAME tx id |

The third row is why cardinality-one supersedes by tail POSITION and never by
tx magnitude. Nothing updates the root's max-tx while edits sit in the tail,
so a second session allocates the same id again; a highest-tx merge is
ambiguous exactly there and can keep the superseded value.

Superseding a cardinality-many attribute would silently drop values, and 149
of this graph's entities carry `:block/tags`. The root schema declares all 19
of the graph's cardinality-many attributes — asserted, because a partial
schema would route the missing ones into the lossy path.

One shape cannot arrive from LogSeq at all: a retraction naming a value the
entity never held. The transactor drops the datom and writes an EMPTY
transaction `[[]]` instead. That empty transaction IS a real input, and is
pinned as readable and pushable.

### One reader, or the guards disagree with each other

Every predicate here — `current_title`, `is_built_in`, `entity_by_uuid` —
reads `datoms_now`: the reachable eavt tree with the tail replayed over it, an
assert adding and a retraction removing the matching `(e, a, v)`.

That is not tidiness. `is_built_in` used to scan `graph.rows` through
`datom_tuples`, which returns `&[]` for the tail row because the tail is a
list of transactions rather than a node map. So a built-in marker LogSeq had
transacted but not yet flushed was INVISIBLE, and push rewrote a built-in
page — measured, `PushReport { transactions: 1, datoms: 2, blocks: [195] }`
where `PushBuiltIn` was owed. Meanwhile `current_title` replayed the tail
deliberately. Two readers, two answers about the same graph, and the
disagreement resolved in the direction that WRITES. LogSeq's tail holds up to
32 datoms before it flushes, so this is an ordinary state of a live graph.

Both directions are measured, not assumed:

| what the tail says | LogSeq's verdict | probe |
|---|---|---|
| `built-in? true` asserted, unflushed | built-in | `probe_tail_builtin.cljs` |
| `built-in? true` retracted, entity has an internal `:db/ident` | STILL built-in (leg 3 holds) | `probe_tail_builtin.cljs` |
| `built-in? true` retracted, entity is flag-only | NOT built-in | `probe_mirror.cljs` |

Sixteen of the fixture's built-ins are flag-only, so the third row is
reachable rather than hypothetical. A reader honouring tail asserts but not
tail retractions passes the first row and fails the third.

The test helpers call the PRODUCTION predicate rather than walking the graph
themselves. The previous test helper had its own recursive walk, which is
exactly why neither the two missing predicate legs nor the tail blindness
could surface as a failure: two readers cannot disagree if only one of them is
ever asserted about.

## The fixture's shape, and why the overflow test needs two pushes

Measured on `tests/fixtures/logseq-db/holontest.sqlite`, pinned by
`the_fixtures_built_in_share_is_pinned`:

| | count |
|---|---|
| entities in the graph | 213 |
| entities LogSeq calls built-in | 192 |
| entities LogSeq does NOT call built-in | 21 |
| blocks in the import base | 206 |
| base blocks push may target (titled, non-sentinel, not built-in) | 12 |
| of those, user-authored (not a LogSeq-minted `0000000N-` panel) | 8 |

Nearly all of the base is LogSeq's own property, class and kv pages, which the
importer currently admits as blocks. That is a read-leg defect, ruled as LW-7.a
(the importer will exclude built-ins) and handled in its own increment, not
here. Push's refusal stays afterwards as a backstop.

Related, measured for that increment: FOUR non-built-in entities have a
built-in parent — 198, 208, 212 and 215, every one of them a LogSeq
"Linked references" / "Unlinked references" panel with
`:block/parent` = `:block/page` = 188. So an exclusion must say what becomes of
a non-built-in child of an excluded parent. On this fixture no person-written
block sits under a built-in parent, but the fixture's user content is shallow
and that is not evidence the case cannot arise.

### A note on entity sets

"Entities in the graph" means entities reachable from the eavt root, which is
what LogSeq's `d/datoms` reports. Scanning the raw `kvs` rows instead reports
two more — 197 and 199 — because the fixture carries 17 UNREFERENCED rows that
still hold datoms. They are abandoned nodes, not deletions: the tail is empty,
so nothing retracted them. Any census that walks rows rather than the tree
counts garbage.

The consequence for testing: 12 blocks are 24 datoms, under the branching
factor of 32, so ONE push cannot overflow the tail. The overflow leg therefore
drives two successive pushes. That is the harder case anyway — the second
push crosses 32 on its fifth block, with the first push's transactions already
sitting in the tail when the flush fires.

## What each oracle leg can and cannot see

Measured by skipping the flush (`overflowed = false`) and re-running all three:

| leg | sees a skipped flush? |
|---|---|
| `validate_db.cljs` (leg 1) | NO — stays `Valid!` |
| `diff_graphs.cljs` (leg 2) | NO — stays exactly the 12 expected deltas |
| head-to-head byte comparison | YES — 437 identical, 19 differing, 2 rows only LogSeq's |

The head-to-head is also walked prefix by prefix
(`bisect_the_pushed_edits_prefix_by_prefix`): the two writers are compared at
every N = 1..24 with a store forced on both sides, because a single end-state
comparison can be green because two divergences cancelled. All 24 prefixes
agree.

LogSeq replays the tail on restore, so a graph that never flushed is
semantically identical and both semantic oracles pass it. Only the row-by-row
comparison against LogSeq's own writer can tell. That is why the head-to-head
exists and why a green leg 1 and leg 2 are not sufficient evidence that the
writer is right.

Both writers take the fixture's 456 rows to 458 for these 24 edits — one
split, two new nodes — and all 458 rows match byte for byte including the
`addresses` column.

## Note on B's evidence

B's 458/458 head-to-head was measured entirely on entities that are built-in
pages by LogSeq's own predicate — all 17 of its targets carry
`:logseq.property/built-in? true` and are therefore in the 192 — which push
refuses. That does not weaken B's claim: it is a claim about the WRITER, and
the writer does not care whose datoms it is storing (same datoms in, same bytes
out). It does mean the scenario was not one a person could produce.
`head_to_head_with_logseq_applying_the_same_pushes` re-establishes the identity
on the blocks push can actually reach, driven through the `push` entry point
rather than a hand-picked entity list.

## W3 prerequisite: reference re-derivation

Push writes titles. A title edit that adds or removes a `[[link]]` should also
move `:block/refs`, and what LogSeq does there is UNMEASURED:
`db_pipeline` documents that it does NOT rebuild refs on an edit, and
`save-block!` — the layer above, which might — is not drivable under nbb
(`No protocol method ICollection.-conj`). So the comparison W3 needs is against
LogSeq's FRONTEND, and if nbb still cannot drive it, that measurement needs the
real application once. Treat it as a W3 prerequisite, not a W3 finding.
