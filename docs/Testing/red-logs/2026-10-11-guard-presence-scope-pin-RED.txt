What the pin is for: `already_bound` asks whether a guard is bound by ATTEMPTING
the registration (`Injector::try_provide` with a root-scope provider). That
closes the wrong-scope gap ONLY because fluxdi's `try_provide` consults the same
root-scope unnamed table the consumer's resolve reads. If fluxdi ever answered
from the local scope, walked scopes, or took a named binding for the unnamed
one, a guard the dispatcher can never see would read as bound and the gate would
run open — silently, with no test failing.

What was simulated: `already_bound` (crates/holon/src/di/guard_bindings.rs) got a
presence check that walks scopes AND ignores names, ahead of the real probe —
`injector.dependency_graph()` collects every ancestor's local providers and lists
named bindings under the same `type_name`:

    if injector
        .dependency_graph()
        .nodes
        .iter()
        .any(|node| node.type_name == std::any::type_name::<T>())
    {
        return true;
    }

Nothing else changed. The simulation was reverted after this run.

Red for the right reason: in both tests the container binds the net gate ONLY
where the consumer cannot see it (a child injector at module scope; the root

gate — the panic that arrives names the NEXT guard the test container leaves out,
`WriteTierAuthority`. So the failure is exactly the reopened gap: a guard the
dispatcher would never resolve counted as bound.
