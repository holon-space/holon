# Proposal: Overlay — local data over content owned elsewhere

Status: Approved (D201.a); increment 1 in progress. D198.a (a page share's SQL
row carries the page's identity) is increment 1. Section 11 records the
approved defaults; the three review fixes are folded into §5 and §10.
Paths are relative to the repo root.

## 1. First principles

**The problem.** A user must attach data to content that the user cannot write,
or must not write:

- The content belongs to another person (a page that Bob shares with Alice).
- The format has no writer (cooklang, a read-only Markdown vault).
- The content belongs to an external system (a Todoist task, a mail).
- The data must stay local to this device, this process, or this hypothetical scenario.

Today each case either fails or has its own solution. A cooklang block refuses
every store-origin write (Model.md:178-194, invariant 14). A page share folds P
onto a mount with a fresh id and copies only the title and tags
(`crates/holon-loro/src/loro_share_backend.rs:1001-1040`). The UI layout uses
its own device-local document (ADR 0033 §2). The "twin overlay" and "overlay
world" are named but not designed (Simulation.md:33-34; ADR 0031:217-231, 282).

**Definition.** An overlay record is `(target, scope, data)`:

- **target**: a stable id of a base entity, plus an anchor that can find the
  entity again if the base re-mints its id (see §5).
- **scope**: which audience holds and sees the record. The scope axis is
  `process ⊂ device ⊂ user ⊂ share`, with `scenario` as a separate axis.
- **data**: one of three kinds, from a closed vocabulary:
  - **Placement**: the parent and sibling position of a *foreign root* in my tree.
  - **Attach**: my own blocks hung under a foreign block (tasks, links, notes).
  - **Facet**: a value for an overlay-able field of the target (tags,
    properties, collapsed).

**What an overlay is NOT.**
- It is not a fork. It never shadows the base's **content** (text, title).
  An edit to read-only text stays a disclosed refusal (invariant 14). If the
  overlay shadowed text, the user would silently hold a private copy of the document.
- It is not a copy of the base. It holds only the delta that the user owns.
- It is not per-render-slot widget state. `Mutable` state stays on the
  ViewModel node (Model.md:300-302).
- It is not a merge. The base and the overlay never merge into each other. The
  read view composes them by a fixed rule, and each side keeps its own authority.

**Optimization targets.** (1) No silent loss: an overlay whose target is gone
stays visible. (2) The read path stays inside the 200 ms p95 SLO. (3) Reuse the
existing machinery (Loro, org round-trip, undo, cells, sync) instead of a new store.
(4) Fail-closed audience: an overlay never reaches a principal outside its
scope (the ADR 0028 H3 direction).

## 2. The key observation: the mount node is already an overlay record

On the recipient side, the mount node is an ordinary node in Alice's own global
doc. It carries `mount_kind`, `shared_tree_id` and `shared_root`
(SUBTREE_SHARING.md "Mount nodes"; `crates/holon-loro/src/shared_tree.rs:486`).
Its parent and sort position are *Alice's* data. Its target is P. That is a
**Placement** overlay at user scope. D198.a makes the SQL row carry P's
identity: the row `P` gets `parent_id`/`sort_key` from the mount node and every
other field from P in the shared doc. The current fold (reparent P's children to
the mount, drop P's row, copy only title and tags) goes away.

The inverse shape is a **graft** node: a node in *my* container that points at
a *foreign* block and holds my children and facets for that block. Mount = a
foreign subtree hung into my tree. Graft = my subtree hung onto a foreign
block. Both are link records, and one resolver handles both.

## 3. Relation to ADR 0028's stitching layer

**Stitching resolves container-crossing links. An overlay is a link or facet
that is written into a scope the target's owner does not own.** So:

- The owner's own crossing links (the private container knows that the shared
  container hangs under block X) are **base** facts. Stitching resolves them.
  They are not overlays. ADR 0028 says "no mounts on the owner side".
- The recipient's mount, and every graft, are **overlay** facts. The same
  stitching resolver resolves them, and it also applies their facets.

Answer to the question "is stitching an overlay, or a layer on top?": neither
exactly. Stitching is the structural half of the overlay machinery. Overlays
add facets and scopes to the link records that stitching already needs.
Recommendation: build ONE resolver (the stitching emitter) and make D198.a its
first increment.

## 4. Where the data lives, per scope

| Scope | Store | Syncs to | Precedent |
|---|---|---|---|
| process | in-memory map in the emitter | nothing | conditions (Model.md:229-231) |
| device | a device-local Loro doc, outside `ContainerRegistry` | nothing, by construction | `layout_doc`, `holon_layout.loro` (ADR 0033 §2; `crates/holon-loro/src/loro_backend.rs:2054-2058`) |
| user | graft and mount nodes in the user's own private container, written to a companion org file | the user's own devices (C1 everything-policy) | mount nodes today |
| share | a container whose audience is the share's principals | the share's audience | not built; future (annotations that recipients see together) |
| scenario | the scenario store / Loro fork (D5 pending) | nothing until accept; accept = replay through the dispatcher | Simulation.md:70-76; ADR 0031 "accept = semantic replay" |

Rules that follow from existing invariants:
- **Never SQL-only.** Turso is an ephemeral cache (Replication.md:30, Model.md:29).
  An overlay stored only in SQL is lost at the next start.
- **Registry membership enforces the scope**, not a filter (ADR 0033 §2). A
  device overlay is not in `ContainerRegistry`, so no replication path can send it.
- **User overlays are ordinary content.** A task that Martin adds under a
  heading of `docs/Architecture/Model.md` is a real PKM block. It must be
  searchable, undoable, in git, and it must survive SqlOnly mode. So user-scope
  grafts round-trip to an org companion file, for example
  `Overlays/docs/Architecture/Model.md.org`, one heading per graft with an
  `:OVERLAY_TARGET:` property.

## 5. Read merge

**Where.** Merge in the stitching emitter, at the point where the authority
emits block rows. The emitter feeds both the SQL projection and the UI read
model (D172.a moves the UI read model to the Loro diff; an SQL-only join would
not reach it). Model.md layer 3 ("verbatim, never re-merges") stays true: the
projection writes the *stitched* rows verbatim, and the composition happens one
layer earlier.

**Rules per data kind.**
- Placement: overrides `parent_id` and `sort_key` of a foreign **root** only.
  Inside a foreign container, the structure belongs to the base.
- Attach: additive. My blocks appear as children of the foreign block, after
  the base children, in the graft's own order.
- Facet: tags = base ∪ overlay. A property key = overlay value if set, else base.
  Each merged row carries a provenance mask (which fields are local) so the UI
  can mark local values and write routing can find their home.
- **The provenance mask is derived, never stored in the properties bag.** A
  `_`-prefixed property key is erased on org write-back
  (`crates/holon-org-format/src/models.rs:886,908`), and any stored copy is a
  second truth that can drift from the overlay records. The emitter recomputes
  the mask from the overlay records on every emit and writes it to a dedicated
  projection column (`overlay_fields`), which no org file carries and no ingest
  reads. The overlay records themselves (mount and graft nodes) are the only
  stored truth.

**Precedence.** Option P1 (recommended): each overlay-able field declares ONE
scope in a closed vocabulary, like `BlockWriteField` (Model.md:85-96). Then
precedence only matters for the scenario layer, which is on top of everything
while the user views a scenario. Option P2: full stacking,
`scenario > process > device > user > base`, for every field. P2 is more
general, but the user can no longer predict which layer a write goes to.

**Cost and the SLO.** The emitter keeps an in-memory index `target → overlay
records`, maintained on commit (like `id_cache`, loro_backend.rs:2062-2064).
A base write on a target does one O(1) lookup. An overlay write is one Loro
commit plus a re-emit of one target row: the same cost as a `set_field`. No new
join enters the `block` matview, so IVM maintenance does not change. Measure
with the keystone latency gate and one release run before any claim.

## 6. Write routing

The dispatcher routes by `(target home, field)`, decided once, at the same
place as `WriteTierAuthority` (`crates/holon-core/src/write_tier_gate.rs`):

| Write | Base writable (own, or share with Write) | Base read-only / external / share with Read |
|---|---|---|
| content, title | base | `EditRefused`, disclosed (no change) |
| move of a foreign root | placement overlay | placement overlay |
| delete of a foreign root | leave: drop the placement and the local copy | leave: drop the placement and the local copy |
| move inside a foreign container | base (C3 boundary rules) | refused |
| create child | base | graft (attach) |
| overlay-able facet | base, unless the field is declared device/process scope | overlay, with a one-time "saved as a local note" disclosure |

The user sees: a small marker on local values (from the provenance mask), and
on a read-only block the edit menu offers "add a local tag" instead of greying
out "add tag".

**Deleting a foreign root leaves the share** (ruled for increment 1). A
recipient's delete of a placed page `P` removes only what is local: the
placement record, the loaded copy and its rows. It never deletes the shared
doc's root, so the owner's page — and every other recipient's — is unchanged.
It is disclosed with a notice: "You left the shared page X; the owner's page is
unchanged". The owner's own delete of `P` is a base write and deletes the page.

Leaving is irreversible, so only a delete leaves: `delete`, `delete_subtree`
and an ingest delete call `LoroBackend::leave_received_pages`, the one exit.
Deleting a block that `P` hangs under leaves `P`'s share too, like a delete of
`P`, and the op is declared irreversible. `LoroBackend::delete_block` refuses
to remove a block that is or holds a received page, so no other route can
remove `P` behind an inverse that would re-create it as a local block. A
Backspace join, `delete_keep_children`, `restore_join` and `merge_blocks` of
`P` refuse with `ShareExitRefused`. Every other block of a shared page merges
like any other block, except that a merge never moves children from one tree
to another. A batch rollback across a leave refuses, because the left share's
doc has left the write authority's routing set.

## 7. Failure modes (fail loud)

- **Orphan** (share revoked or lease expired, owner deleted P, file removed,
  external entity deleted). The overlay record is never deleted automatically.
  A graft whose target is gone renders as an ordinary block in the user's
  `Overlays/...` page, so nothing disappears. A sticky condition
  `OVERLAY_ORPHANED` (ADR 0035) names it, with remedies: re-attach, keep as my
  own block, discard. Keystone invariant: every overlay record resolves to
  exactly one live target, or it is in the orphan condition.
- **Base id changes.**
  - ADR 0028 H4 rotation: recipients get fresh ids and only the owner has the
    alias ledger. Recipient overlays then orphan (see Q4).
  - Read-only formats mint ids that are not stable: Markdown positional ids
    `file::b::<seq>` (`crates/holon-markdown/src/obsidian.rs:203-206`) and
    content-derived plugin ids (`crates/holon-plugin-host/src/adapter.rs:451-457`).
    One inserted paragraph upstream moves every later id. The target therefore
    stores an anchor (heading path + content fingerprint) and the emitter
    re-anchors at ingest. An anchor that matches 0 or more than 1 block goes to
    orphan, never to a best guess.
  - External systems: a server id is stable. A content key (ADR 0034
    consequences, jaq key) changes on rename, so the overlay orphans unless the
    reconciler reports the rename.
- **Conflicts.** Two own devices write the same user facet: Loro merge inside
  the user container (LWW per key). Overlay and base disagree: the overlay value
  shows, with the marker, so the user can see that the base value is different.
- **Read-only base.** Covered by §6. Invariant 14 stays: only the overlay-able
  vocabulary is redirected, and text edits still refuse.
- **Audience.** A user overlay on a shared page never enters the share
  container. That is H3 by construction: the overlay lives in a private container.

## 8. Fit of the six cases

Scenarios (Martin's real vault and repo):
1. Martin shares `Projects/Holon/Market launch.org` with Alice. Alice puts it
   under "Shared with me", folds it, and tags it `#review`. Martin sees none of this.
2. Martin mounts the repo's `docs/` as a read-only Markdown vault. Under the
   heading "Invariants" of `docs/Architecture/Model.md` he adds a task
   "Re-check inv 11 after D198.a" and a link to `Entity Identity.org`. The
   `.md` file does not change.
3. A Todoist task "Pay invoice" gets a local note and a `[[People/...]]` link
   in Holon. Todoist never sees them.
4. The phone sorts the `Now.org` query view by date, and the Mac sorts it by priority.
5. The editor tags each keystroke with a `write_seq` to order echoes (D200).
6. An agent proposes "archive everything done before July" and Martin
   previews the result before any write happens.

| # | Case | Fit | What it needs |
|---|---|---|---|
| 1 | Page share (D198.a) | **Yes** | Mount = Placement at user scope; SQL row id = P; collapsed and local tags as facets on the mount node. |
| 2 | Read-only formats (cooklang, Markdown `docs/`) | **Yes, with an anchor cost** | Grafts + companion org file; the anchor/re-anchor step for unstable ids; D56.a wiring for Markdown; invariant 14 redirect for facets. |
| 3 | External systems (Todoist, mail, calendar) | **Yes** | Graft per external entity, keyed by the connection's id or key (ADR 0034); orphan on delete. |
| 4 | Device-local UI state | **Partial** | `collapsed` is document state by ruling (`crates/holon-org-format/src/models.rs:1011`), so it stays base for own content. Only fields that are really per-device (view sort order) go to device scope. Needs a ruling on the field list. |
| 5 | Process-local tokens (D200 `write_seq`) | **Weak** | A process-scope record could hold it, but a token that changes on every keystroke would re-emit the row each time. Batch identity (D154.a, D200 option c) is the better home. Keep it as a possible consumer only. |
| 6 | Simulation / staging | **Partial** | Scenario = the top precedence layer. For blocks, the Loro fork stays the substrate (Simulation.md:33-34). For external state, the "twin overlay" = facet records at scenario scope. The gate stays on the current state (ADR 0031:217, G1=A) until an oracle needs more (ADR 0031:231). |

## 9. Options where the design forks

**F1 — the shape of an overlay record.**
- **O-A (recommended): overlay records are nodes** (mount and graft) in the
  scope's Loro container. + Reuses sync, undo, org round-trip, cell backings
  (invariant 12). + An orphan degrades to a visible block. − Every raw-tree
  reader must know that graft nodes are hidden in the stitched view: the same
  "Loro↔SQL shape difference" tax that the mount fold has today
  (Model.md:147-155), now in one resolver.
- O-B: a dedicated typed store `(target, field, scope) → value`. + Explicit,
  and the merge is cheap. − Needs its own sync, persistence, undo, org form and
  cell backing. − Attach (child blocks) does not fit a key-value map.
- O-C: SQL tables joined in the `block` matview (like `block_tags`,
  Schema.md:81-99). + No emitter change. − Lost at restart (ephemeral).
  − Invisible to the D172.a read model. − One more join in the hottest matview.
  Rejected.

**F2 — the merge point.** Emitter (recommended, §5) versus matview join
(O-C). The emitter is the only point that serves both readers.

**F3 — precedence.** P1, one declared scope per field (recommended), versus
P2, full stacking (§5).

## 10. First increment: D198.a page-share placement

**Scope.** Placement only. No facets, grafts or new scopes yet.

1. The SQL projection emits ONE row for a page share: `id = P`,
   `parent_id`/`sort_key` from the mount node, all other fields (with
   `#+TODO` keywords) from P in the shared doc. P's children keep parent P.
   Delete the fold in `loro_share_backend.rs:1001-1040` and the fresh mount row
   in `project_mount_to_sql` (:882-937). A block share keeps its synthetic container page.
2. A recipient `move_block(P, …)` writes the mount node only. It never writes
   the shared doc.
3. Update Model.md invariant 11 (the fold text at :147-155), and flip the
   EXPECTED DIVERGENCE assertion in `authority_owning_page_parity.rs` to
   `owning_page = P` (that test lives on the unlanded readauth-2 lane; it
   flips when the lanes are woven).
4. **One placement per target.** A second `accept_shared_subtree` of a share
   this device already mounts is REFUSED, before any network work, and the
   refusal names the existing mount: a page has one parent, so a second accept
   would be a second place for the same page. Re-placing is a move of the page
   (item 2), never a second accept.
5. **What the Loro authority answers for a placed root** (consistent with
   D197.a):
   - the page's parent (`get_block(P).parent_id`, and so the parent every
     reader derives) is the MOUNT's parent; its position is the mount's;
   - `owning_page(P) = P` and `owning_page(child of P) = P` — the file model:
     a page share keeps P's own file;
   - `children(P)` = P's children in the shared doc (Loro's write model), and
     `children(mount parent)` lists P in the mount's place;
   - a move of P (`move_block`, `update_block_position`, `update_parent_id`)
     writes the mount in the global doc; the shared doc is untouched.

**Keystone pin, red first.** The two-instance composed PBT has
`ShareContainer` (`crates/holon-integration-tests/src/pbt/composed/two_instance.rs:922`),
but it shares only the root selector
(`crates/holon-integration-tests/src/pbt/transitions/share_container.rs:57-59`).
Add `SharePage { page }` and `MovePlacedRoot { page, new_parent }` on the
receiver. Invariants:
- `inv-share-mount-carries-page-identity`: the receiver's SQL has exactly one
  row with id P; its properties include the owner's P properties; no row
  carries a fresh mount id. Red today, because SQL holds the mount id and no row P.
- `inv-overlay-placement-local`: after `MovePlacedRoot`, the receiver's parent
  of P changes, and the owner's parent of P does not change.

## 11. Rulings (D201.a) — the approved defaults

- **Q1** yes: `collapsed` on a *foreign* page is a user-scope overlay; on own
  content it stays document state (2026-07-11 ruling).
- **Q2** yes: the overlay-able vocabulary is `tags`, `properties`, `collapsed`,
  attach and placement — never content or title.
- **Q3** later: unstable base ids orphan loudly in v1; re-anchoring comes later.
- **Q4** yes: the owner-signed succession pointer carries the share root's new
  id, so placement survives H4 narrowing.
- **Q5** yes: pairing may replicate user-scope mounts (each own device then
  also fetches the share). Until that lands, pairing keeps refusing a receiver
  that holds a mount (D73.a), and the keystone keeps `ShareContainer` and
  `SharePage` exclusive.
- **Q6** yes: user-scope grafts live in `Overlays/<source path>.org`.
- **Q7** later: local removal of a base tag (a suppression facet).

The original questions follow for the record.

## 12. Increment 1 as built

- The keystone pin is `SharePage` + `MovePlacedRoot` in the two-instance
  composed PBT, judged by `inv-share-mount-carries-page-identity` and
  `inv-overlay-placement-local`, plus the deterministic chain
  `a_shared_page_keeps_its_identity_and_the_receiver_places_it_locally`.
- The global Loro→SQL projection skips mount nodes: a mount is a placement
  record, and the share's own projection owns every row of the tree it places.
  Its full reseed leaves alone the rows of the shares loaded right now (the
  share registry and the mount records), never rows that merely carry a
  `shared-tree-id` stamp.
- The share kind is decided once, at share time, recorded in the shared doc and
  copied onto each device's mount with the device's side (owner / recipient).
  The projection and the authority read that record, never the page's mutable
  `Page` tag.
- A page share is known by its page: `unshare(P)`, the accept response's
  `handle`, and the pairing refusal all name `P`. The mount id is internal.
- `DeletePlacedRoot` (receiver) leaves the share (§6); `inv-overlay-placement-local`
  judges that the owner's `P` survives and the receiver keeps nothing of it, and
  that the receiver's row takes both parent and sort key from its mount, in SQL
  and in the Loro authority.
- The oracle derives every page-share exemption (in `inv-two-instance-convergence`
  and `inv-boundary-respected`) from the MODEL's descendants of `P`, never from
  the receiver's rows, and `inv-share-mount-carries-page-identity` fails on any
  row, on either peer, that carries a `shared-tree-id` stamp the model puts in
  no share.
- The share projection re-reads the root's placement on every pass and is also
  woken by global-doc commits, so a move of the mount reaches the page's row.
- The UI read model (D172.a) still does not carry shared rows; the one
  stitching emitter of §5 is what closes that.
