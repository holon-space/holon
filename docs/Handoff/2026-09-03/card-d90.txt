> Low-code Inc 2 is built and green (report `scratchpad/reports/lowcode-inc2a/lane-report-lowcode-inc2a.md` after weave; lane WS `.claude/worktrees/lowcode-inc2a`): `crates/holon-plugin-host` (wasmi 2.0.0, four-function ABI, JSON Lines through linear memory, fuel + memory limits, `PluginFormatAdapter` registered from a yaml sidecar, undeclared scopes/columns refused), the cooklang guest (a faithful port; 517 KB raw / 205 KB gzip, `wasm-opt` not installed), a testkit guest, and the red-first differential PBT with ZERO divergences. MEASURED, release build, one host kept alive, warmed: 200 generated recipes = **517.5 ms plugin vs 23.9 ms native** (2.59 ms vs 0.12 ms per recipe, 21.6×). Per interaction (one recipe on save) that is 77× under the 200 ms SLO; a COLD full-vault scan of 200 recipes misses the plan's 200 ms kill line by 2.6×. Today's real Rezepte folder has 3 recipes. The plan's Inc 3 deletes `cook.rs`, `rows.rs` and the cooklang dependency from `holon-kitchen` (no dual path); Inc 6 adds tree-sitter grammars as guests (same interpreter cost class).
? The SLO is per interaction; a full scan is a boot/re-index event whose cost should be bounded by incrementality (parse only changed files, cache rows by content hash), not by interpreter speed. Keeping a native path "for speed" is exactly the dual path the refactor rule forbids.

- c | Keep cook.rs as the native fast path beside the plugin | +fastest today | -the dual path the plan and the refactor rule forbid; every format would want one; the point of the program (attach formats WITHOUT Rust) is lost
