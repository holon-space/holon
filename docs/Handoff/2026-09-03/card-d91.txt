# D91 German timer units (`~{9%Minuten}`) refuse the whole recipe — in BOTH the old parser and the new cooklang guest. Accept them, and how?
> The plan expected the upstream `cooklang` crate to accept what `cook.rs` refused, so the differential PBT would NAME the divergence. Measured instead: cooklang's own `parse` runs with `Extensions::all()`, whose `ADVANCED_UNITS` extension validates timer units against its English unit table and errors on `Minuten`, so the guest refuses exactly as `cook.rs` does — zero divergences, and dogfood entry `2026-09-02-a-german-timer-unit-refuses-the-whole-recipe` stays OPEN. Your three real recipes are German. The guest is a plugin: its extension set is a ONE-LINE choice in the guest source, and cooklang also supports a units/locale configuration (a `Converter` with a custom unit file) — either is low-code, neither is a parser change in Holon.
? A recipe file the user wrote must never be refused wholesale for a unit word; parse-don't-validate means the timer is a (quantity, unit-string) pair the app renders as written, and unit knowledge is a converter's concern.
* a | Parse with `ADVANCED_UNITS` OFF in the cooklang guest: timers carry their unit as the literal string; no unit validation at parse time; a later converter (if ever) maps known units | +every German (or any) unit parses; smallest change; matches parse-don't-validate | -no unit normalisation for timers (none exists today anyway)
- b | Keep `ADVANCED_UNITS` ON and ship a German unit table (cooklang `Converter` config in the guest or the sidecar) | +units are validated and convertible | -a unit table per language; the next language refuses again; a config knob users must find
- c | Keep refusing (status quo); the recipe shows the format refusal toast and no document | +strictest | -your own recipes stay unreadable; the dogfood entry stays OPEN
