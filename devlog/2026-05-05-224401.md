# #13 v5 — Org renderer matview lag fixed; next failure surfaces (2026-05-05)

Continues `devlog/2026-05-05-110315.md`.

## What I did

Audited the org-render-emitting code paths in
`crates/holon-orgmode/src/di.rs` and `org_sync_controller.rs` to test
the v4 hypotheses:

- **A — file write completes but renderer is async/batched.**
- **B — separate code path fires renders without bumping signals.**

Findings:

1. **`on_block_changed`** (event_rx, di.rs:1061) — writes file, pushes to
   `pending_marks`, fires `mark_progress`. ✅
2. **`re_render_all_tracked`** (event_rx fallback, di.rs:1029, 1045) —
   writes file, same accounting as #1. ✅
3. **`on_file_changed`** (file_rx and poll_tick, di.rs:1003 / 1019) —
   CAN write file (`org_sync_controller.rs:518`) when a parse uncovers
   structural changes; bumps `mark_progress` but does NOT push to
   `pending_marks`. The writes it triggers are accompanied by a fresh
   batch of `command_bus.execute_batch` events whose IDs DO go through
   event_rx normally — so the watermark still tracks them.

Hypothesis B is therefore not the culprit on its own.

Hypothesis A is. `CacheBlockReader::get_blocks` reads `SELECT * FROM
block` — the matview — via `load_all_blocks_via_matview`. Matviews
propagate via CDC, which lags the underlying base-table write by an
unbounded window. By the time `on_block_changed` runs in response to an
events-table CDC delivery, the source transaction has already committed
to `block_raw`, but the `block` matview need not yet reflect it. The
renderer renders a stale snapshot and writes a stale org file. Same
race class as inv10d (`block_with_query_source.sql` →
`block_raw`).

## Fix

`crates/holon-orgmode/src/di.rs:235`:

```rust
async fn load_all_blocks_with_hydration(&self) -> anyhow::Result<Vec<Block>> {
    let sql = format!(
        "SELECT b.id, b.parent_id, b.depth, b.sort_key, b.content, \
         b.content_type, b.source_language, b.source_name, \
         b.properties, b.marks, b.collapsed, b.completed, \
         b.block_type, b.created_at, b.updated_at, \
         COALESCE((SELECT json_group_array(tag) FROM block_tags WHERE block_id = b.id), '[]') AS tags \
         FROM {BLOCK_WRITE_TABLE} b"
    );
    // ... Block::try_from per row ...
}
```

The dead-coded matview path (`load_all_blocks_via_matview`) is removed;
the base-table + correlated-subquery shape is the only path. `Block`
has no `blocked_by` field (`crates/holon-api/src/block.rs:714`), so
not hydrating that column is safe. Tags are still hydrated from
`block_tags`.

Two pre-existing archlint hits in the same file silenced with ALLOW
comments (di.rs:850 — best-effort OS page-cache warmup; di.rs:1047 —
disclosed re-render path when an event lacks `_routing_doc_uri`).
