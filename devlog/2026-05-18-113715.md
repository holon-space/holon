## Fixed ViewModeSwitcher default mode selection

The production VMS was defaulting to list/table layout even when tree/outline should be the fallback. The layout_pbt wasn't the right test for this — it manually constructs modes and never exercises the backend's `collection_render_from_profile` variant-sort path.

**What happened:**

- Traced the root cause to `entity_profile.rs:404` sorting variants by priority **descending** (for Rhai condition resolution), which puts conditional variants before the unconditional `Predicate::Always` fallback.
- `collection_render_from_profile` emitted `modes` JSON in that priority-desc order.
- Shadow builder `view_mode_switcher.rs:19` blindly picked `modes[0]` as default — which is the first conditional variant (e.g., `table_view`), not the unconditional `tree_view` fallback.
- Extracted `view_mode_switcher_from_variants` helper in `block_domain.rs` to emit an explicit `default_mode` arg pointing at the unconditional variant.
- Updated shadow builder to read `default_mode`, falling back to `modes[0]` for legacy callers.
- Added three unit tests covering: unconditional variant selection despite priority order, single-variant short-circuit, and fallback when no unconditional variant exists.

**Decisions:**

- Kept `modes` JSON in priority-desc order so other consumers see a stable shape; only the shadow builder benefits from the explicit `default_mode` pointer.
- Fallback to `modes[0]` preserves compatibility with two-mode `result/source` switchers that don't go through this path.

**Status:** All 6 layout_pbt tests green, 3 new unit tests pass, VMS now defaults to tree/outline (the unconditional variant) rather than table/list.
