# #8: inv10d root layout regression — root cause + fix (2026-05-05)

Continues from `devlog/2026-05-05-110307.md` and `2026-05-05-110308.md`.

## TL;DR

`crates/holon/sql/queries/block_with_query_source.sql` switched
`FROM block` → `FROM block_raw`. The query only projects columns from
the writable base table; reading the matview was exposing it to a CDC
consistency race. After the fix, **inv10d passes on all 14 sampled
iterations** in a Full + SqlOnly PBT run (was 13/14 before).

## Root cause

`BlockDomain::render_entity(block_id)` at
`crates/holon/src/api/block_domain.rs:104` calls
`load_block_with_query_source(block_id)`. On error it falls through to
`render_leaf_block` which returns `RenderExpr::FunctionCall { name:
"render_entity", args: [] }` plus a single-row stream containing the
block itself. The interpreted root widget for that pair is
`live_block(block_id)` — an entity-level transclusion of the block.

`load_block_with_query_source` runs `block_with_query_source.sql`,
which is an INNER JOIN over the `block` table self-joining to find the
block's query-source child:

```sql
FROM block b
INNER JOIN block query_src ON query_src.parent_id = b.id
    AND query_src.content_type = 'source'
    AND query_src.source_language IN {query_langs}
LEFT JOIN block render_src ON ...
WHERE b.id = $block_id LIMIT 1
```

After the matview migration, `block` is a hydrated view over
`block_raw + block_tags + task_blockers` with `json_group_array`
aggregation and `GROUP BY` on every column. **During a concurrent CDC
cycle (after a structural mutation like `NavigateHome`'s
`navigation_history` write triggering watch_ui's structural matview
re-emit), the IVM-maintained block matview can transiently fail to
project the query-source child rows**. The INNER JOIN returns empty,
`load_block_with_query_source` errors, and render_entity falls through.

Confirmed via diagnostic at
`crates/holon-integration-tests/src/pbt/sut.rs:3997-4010` — the
extended assert message captures both expected and actual render
expressions plus data_rows:

```
[inv10d] Root widget 'live_block' doesn't match render source 'tree' (root_id=block:eu-feuf0a-...)
EXPECTED render expr: tree(#{parent_id: col(...), sortkey: col(...), item_template: render_entity(), creation_slot: true})
ACTUAL   render expr: render_entity()
data_rows.len()=1 ids=["block:eu-feuf0a-..."]
live_block(block:eu-feuf0a-...) [ops: ...]
  (empty)
```

A second confirmation came from a `tracing::warn!` (since reverted) in
the fall-through arm, which logged:
```
[render_entity] load_block_with_query_source(block:root-layout) FAILED
— falling back to render_leaf_block:
Block 'block:root-layout' not found or has no query source child
(prql/gql/sql)
```

## Fix

Switched all three `block` references in
`block_with_query_source.sql` to `block_raw`. The query only projects
`id`, `parent_id`, `content`, `properties`, `content_type`,
`source_language`, `render_source` — none of which require the matview's
`tags` or `blocked_by` JSON aggregation. `block_raw` is the
synchronously-written base table; reading it bypasses the matview's
IVM state machine entirely and avoids the consistency window.

```sql
FROM block_raw b
INNER JOIN block_raw query_src ON ...
LEFT JOIN block_raw render_src ON ...
```

The previous SQL is wrong both for performance (full matview hydration
to read 1 row + 2 children) and correctness (CDC consistency window).

## Why this didn't surface earlier

This is a class of "matview reads wherever a base-table read would do"
issue. Likely siblings — anywhere the codebase reads from `block` for a
query that doesn't need `tags` / `blocked_by`. **Audit candidates** via
`grep "FROM block\b" -n crates/holon/sql/`. Already known clean: the
`block_matview.sql` view itself, `block_with_path` (path lookups via
matview is fine — it's a reactive read), and the live_blocks LiveData
in PBT (which DOES read tags so must use the matview).

The matview migration's "validate broader test suites" gate (from
`devlog/2026-05-05-block-matview-handoff.md`) didn't catch this
because:
1. Most reads legitimately need the hydration (tags / blocked_by)
2. `block_with_query_source.sql` is hit only on render path, only
   during concurrent CDC, only when the IVM hasn't yet propagated the
   block's children
3. The Turso `set_null_flag` and `MatchCounter` panics were masking
   downstream symptoms throughout earlier sessions
