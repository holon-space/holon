## Editing Idle Event Loop & Block Ordering Replay

**Context:** Implemented a comprehensive fix to eliminate write-back traffic during idle periods by adding idempotency guards to `BlockOrdering::place()` and a Rust-side diff check in `prepare_update()`. Ran full PBT validation suites to confirm the fix doesn't regress behavior.

**What happened:**
- Implemented 5-step plan: DI for `BlockOrdering`, disk-order replay in `on_file_changed`, idempotency guards in `LoroBackend` + `SqlBlockOperations`, Rust diff + event gating in `prepare_update`, helper extraction
- All 7 unit tests from verification plan passed
- Ran `general_e2e_pbt` (Full + SqlOnly variants, 8 seeds each) and `gpui_ui_pbt` — discovered regression: bulk-* blocks created but missing from actual backend in headless Full mode
- Root-caused via log analysis: Loro creates blocks via outbound (5 ops confirmed in log), SQL projection happens, but subsequent reads against actual backend show 0 bulk-* blocks
- Generated 6 explicit hypotheses with validation commands; falsified H1 (BlockNotFound) and H2 (timeout), narrowed to H3–H5
- Discovered core architectural issue: `place()` should only fire for **existing-but-misaligned** blocks, not newly-created ones (which already get positioned via `POSITION_AFTER_BLOCK_ID_PARAM` hint)

**Challenges:**
- **Non-deterministic failures across variants**: SqlOnly works, headless Full fails, GPUI Full works — isolated to inbound event consumer state differences
- **Silent failure mode**: `place()` errors abort `on_file_changed` without explicit error messages; required adding debug logging to diagnose
- **Async coherence gap**: newly-created blocks exist in Loro outbound but the wait-for-cache poll doesn't guarantee Loro tree state matches SQL projection timing

**Decisions:**
- Reverted agent's 2s polling fix (masked root cause rather than fixing it); root cause is calling `place()` on new blocks when they should only be placed via inbound `POSITION_AFTER_BLOCK_ID_PARAM`
- Plan's core goal (idle loop elimination via `prepare_update` diff guard) is sound and passing unit tests; the `BlockOrdering` replay in Steps 1–3 is the regression vector and may need architectural rework

**Status:** Main diff guard works (idle SQL writes eliminated); Steps 1–3 (`BlockOrdering` replay) cause PBT regression in headless Full mode and need either deeper design (typed ordering intents on inbound events rather than post-hoc `place()` calls) or rollback. Awaiting decision on whether to land Steps 4–5 only or iterate on ordering architecture.
