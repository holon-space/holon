## DBSP zset clone churn investigation handoff

The DBSP operator graph in `turso_core::incremental::dbsp` is responsible for ~264MB of transient allocation churn (~3.4M clones) in a 6-minute session with only ~1000 rows of data—a ~3400× amplification factor indicating rows are being deep-cloned per operator hop per change event.

- **Profiled the problem**: Heap profiling with dhat (rust-heap mode) identified two dominant clone sites under `process_node` → `execute_node`: one cloning entire `Vec<(HashableRow, isize)>` deltas (~175MB, 210k blocks), another per-`Value` cloning within row vectors (~89MB, 3.1M blocks). Both are live-at-end = 0, pure transient churn.
- **Root cause identified**: `process_node` unconditionally clones entire delta vectors between operators, and fan-out patterns (one delta feeding multiple downstream operators) clone once per consumer. `HashableRow::clone` deep-clones its `Vec<Value>`, which deep-clones every `Value`.
- **Documented three fix hypotheses** in preference order: (1) move/borrow deltas and clone only emitted rows in read-only operators; (2) wrap row payloads in `Arc<HashableRow>` or `Arc<[Value]>` to make fan-out and pass-through refcount bumps; (3) intern `Value` strings as a fallback.
- **Created reproducible measurement framework**: isolated repro (2–3 materialized views, ~1k inserts + updates with dhat harness), debug counter on `HashableRow::clone`, and downstream validation via Holon's `turso_sql_replay` tool.
- **Defined acceptance criteria**: clone count per row-change should drop ~100×, the `process_node` clone family should leave the top-10 churn list, and all IVM correctness tests (existing suite + Holon e2e) must pass.
