## Slice 0: Index-Organized Materialized Views End-to-End

**Context:** The plan required implementing `CREATE MATERIALIZED VIEW … ORDER BY … LIMIT …` to allocate index-organized btrees instead of table btrees, and wire up the read/write/refresh paths to handle the new storage shape. Slice 0 delivers the minimal viable implementation: DDL allocation, write-time routing, read-time cursor logic, and REFRESH support. Overlay merging (in-transaction reads) defers to Slice 1.

**What happened:**

- **R0.b**: Added `BTreeCursor::new_index_with_index_info()` constructor in `btree.rs` to allow cursor allocation from a synthetic `IndexInfo` rather than a loaded `Index` struct (needed at DDL time when no index file exists yet).
- **R0.c**: Implemented `MatviewOrderBy::to_index_info()` and `::permute_storage_to_logical()` helpers in `view.rs` — the latter performs the critical column-order transformation from btree storage layout (sort columns + rowid + payload) back to logical query output order.
- **R0.a**: Updated DDL in `core/translate/view.rs` to allocate a `new_index()` btree (not a table) when `ORDER BY` is present; REFRESH now branches on `is_index_organized` to pick the right cursor type.
- **R0.d**: Wired all 4 commit-time cursor sites in `compiler.rs` (from-scratch population, delta write, refresh write, view-on-view) to branch on `is_index_organized` and pass `CursorType::MaterializedView` for reads and index cursor for writes.
- **R0.e**: Updated VDBE `OpOpenRead`/`OpOpenWrite` in `execute.rs` to detect `view.order_by.is_empty()` and allocate the correct cursor flavor.
- **R0.f**: Implemented `read_btree_delta_entry()` permutation logic for index btrees — extracts the rowid from the last stored column (per `get_index_rowid_from_record`), then reorders remaining columns back to logical order.
- **R0.h**: Added 5 smoke tests in `matview-order-by.sqltest` covering ASC, DESC, projection-with-sort-on-col-2 (regression check), post-insert ordering, and REFRESH.

**Challenges:**

- **Storage-to-logical column permutation**: The composite key is stored as `[sort_col_1, …, sort_col_n, rowid, payload_col_1, …]` but must be read back as `[query_output_col_1, …]`. The permutation is non-trivial when sort columns are a subset of output columns or reordered. Solved by computing a reindex map at cursor-open time and applying it in `read_btree_delta_entry`.
- **Rowid extraction position**: For index-organized matviews, the rowid is stored at a fixed position (second-to-last in the btree record, before the weight/multicopy counter). Code had to call `get_index_rowid_from_record(record, key_cols.len())` rather than assuming rowid is in a specific column.
