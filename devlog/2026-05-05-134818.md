## Fixed schema load panic when index targets materialized view

The `.tables` command was panicking when loading a database containing an index that pointed to a materialized view, rather than providing a useful error message.

**What happened:**

- Identified root cause: `core/schema.rs:1645` was calling `unwrap()` on `None` returned by `get_btree_table()` when an index referenced a matview
- Replaced both `unwrap()` calls in `populate_indices()` with explicit error returns that describe the actual problem
- Added `known_matview_names: &HashSet<String>` parameter threaded through schema load callsites (`core/util.rs`, `core/connection.rs`, `core/mvcc/database/mod.rs`, `core/vdbe/execute.rs`) to detect the matview case at load time
- Hardened `translate_create_index()` in `core/translate/index.rs` to reject `CREATE INDEX` on matviews upfront, preventing this corrupt state from being created in the first place

**Challenges:**

- Matviews aren't registered in `incremental_views` until after `populate_indices()` runs, so the matview-name set had to be built separately and threaded through the call stack to enable better error messages during schema load

**Status:** `/tmp/inspect.db` now opens with a clear parse error instead of panicking; new databases cannot enter this state via `CREATE INDEX`.
