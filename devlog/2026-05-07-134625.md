## Chained Matview Reads Inside Open Transactions

**Context**: G4 bug from holon PBT where chained materialized views fail to see uncommitted upstream changes when read inside an open transaction. The row appears after COMMIT but not before — indicating the read path misses the cascading delta propagation that COMMIT handles correctly.

**What happened**:
- Used differential fuzzer to fish for the trigger pattern (seed `12160730966503765661` exposed it)
- Minimized to 2-matview chain: base table → aggregate matview → join matview reading from aggregate
- Inside `BEGIN`, INSERT into base, then SELECT from chained matview shows missing row; after COMMIT it appears
- Root cause: `ensure_tx_changes_computed()` in `core/incremental/cursor.rs` only fed the circuit with direct `tx_state.table_deltas`, missing transitively-upstream matview outputs
- The COMMIT path (`apply_view_deltas`) handles cascading via topological walk, but the READ path inside tx didn't
- Implemented fix: walk upstream matview names (DFS), execute each with `execute_with_uncommitted()`, inject output deltas into circuit keyed by upstream view name

**Challenges**:
- SQL repro from bug report didn't fail in isolation — fuzzer was needed to find the trigger pattern; used smaller statement budgets to minimize generated SQL
- Distinguishing "read inside tx" vs "read after commit" required tracing through I/O state machine and understanding `last_tx_state_len` caching logic
- Initial fix attempt only improved some seeds; verified no regressions and that the original holon repros still pass

**Decisions**:
- Used fuzzer-first approach per workflow — found pattern SQL alone couldn't trigger, saving significant debugging time
- Kept fix minimal: cache invalidation sums `tx_state.len()` across upstream chain; no invasive rewiring of circuit state

**Status**: Fixed and committed (`7cf0a2e6`). Added 2 tests to `matview-on-matview.sqltest`; all 70 IVM integration tests pass; pre-existing test ordering flake unrelated to this fix.
