## Headline finding — production regression

`crates/holon/src/sync/loro_module.rs:120` constructed the
LoroSyncController's dedicated `SqlOperationProvider` with
`table_name = "block"`. After the matview migration
(`devlog/2026-05-05-block-matview-handoff.md`), `block` is a
materialized view; only `block_raw` is writable. Every Loro→SQL
outbound reconcile failed with:

```
[LoroSyncController] Outbound reconcile failed: execute_batch_with_origin failed:
Batch transaction failed: Database error: Failed to prepare statement:
Parse error: cannot modify materialized view block
```

The `inv-loro-no-errors` invariant in `sut.rs:3235` catches the
incremented `error_count`, panics the PBT, and was the failure mode
the prior handoff flagged as "pre-existing intermittent". It was a
real production bug all along — the matview migration's "validate
broader test suites" item (block-matview handoff §"what's left", #2)
was the unrun gate.

Fix: thread `BLOCK_WRITE_TABLE` through `loro_module.rs` (parallel to
the `event_infra_module.rs:112` site that already had it). The entity
name + short_name stay `"block"` so dispatcher routing and event
aggregate types are unchanged.

After the fix, the `cannot modify materialized view block` error is
gone across all sampled seeds.
