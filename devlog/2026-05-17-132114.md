## Senior Review & Plan Refinement: Watermark Semantics & Correctness Bugs

A thorough senior-engineer review of the glimmering-bubbling-crayon plan exposed two correctness bugs and several edge-case gaps in the initial watermark sync design.

**What happened:**

- Ran a skeptical review focused on implicit assumptions, edge cases, and validation gaps
- **Found Bug #1**: Phase 1 conflated two different hashes — `file.content_hash` (raw disk content) vs. `hash(rendered projection)` needed by `last_projection`. These aren't interchangeable; semantics decision required (Tasks `D-1`, `V-1`)
- **Found Bug #2**: Phase 4 used wrong watermark — `WatermarkState.global` advances at event row commit in `turso_event_bus.rs:102`, not when the cache feeding `BlockReader::get_blocks` applies it. Switching to `global >= target_ts` would race the cache; fix is per-consumer watermark with explicit consumer id lookup (Tasks `V-4a`, `V-4b`)
- Added crash-safety requirement: hash must write in same batch as block ops
- Tightened edge cases: `renderer_version` byte for binary upgrades, `HashSet` comparison for edge-set diff (not `Vec`), explicit cold-DB/first-boot path, Phase 3 scoped to `org.initial_scan.ingest` span
- Added verification metric: "zero block-table batches inside `org.initial_scan.ingest`" (not just zero log lines — legitimate `file.content_hash` writes for new files still occur)

**Decisions:**

- Keep Loro-side poll in Phase 4 (documented race at `:551–587` is real)
- Defer chord-op walks outside initial ingest span
- Run three quick validations (<15 min each) before coding dependent phases

**Status:** Plan rewritten with all findings integrated; five validation tasks added; ready for implementation phasing.
