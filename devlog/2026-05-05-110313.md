### Two distinct issues uncovered

**(a) Bare `block_raw.id` reference in correlated subquery** —
sut.rs:619 had:
```sql
SELECT id, parent_id,
  (SELECT json_group_array(bt.tag) FROM block_tags bt
    WHERE bt.block_id = block_raw.id) as tags,
  ...
FROM block_raw WHERE id = '{}'
```

Turso's parser doesn't accept the unaliased `block_raw.id` reference
inside the correlated subquery — the error surfaces as
"no such table: block" (Turso looks for a table whose name matches
the prefix of the dotted identifier). Fixed by aliasing the outer
table: `FROM block_raw b` + `b.id` references throughout. Verified:
that specific parse error is gone in the next single-shot run.

**(b) OrgSyncController write race** — separate failure class. The
test asserts that every ref-state block has a corresponding org-file
entry. Some blocks (e.g. `block:b4h-3-tdm1-98` + its `::src::0`
child, `block:93j32...`, `block:w9u`) are missing from the org file
even though `wait_for_org_files_stable` previously returned. Pattern:

- Both block + its source child missing → suggests OrgSyncController
  hasn't finished rendering the parent yet
- `wait_for_org_files_stable` may be undergated (returns once file
  size is stable, but a partial parent + source child pair could
  still have only the parent on disk briefly)

This is **not** the matview-CDC race I fixed for #8. The org sync is
file-IO + parser-driven; the gates are different.
