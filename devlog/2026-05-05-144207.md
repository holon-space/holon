## Completing Block Matview Migration and Fixing Schema Integration Issues

Continued from handoff on 2026-05-05, completing the removal of workarounds and integrating the block matview with the rest of the schema layer.

### What happened

- **Removed SUT live_block_tags workaround** — deleted `BlockTag` struct, `live_block_tags_cell` field, and the manual fold in `check_invariants_async`. The `live_blocks()` SQL now selects `tags` directly from the matview; `parse_block_row` already handled JSON parsing correctly.

- **Aligned test fixtures with table rename** — Updated `edge_field_e2e.rs` to use `block_raw` for the raw table, added `block_tags` junction table (needed because `find_document_uri` joins it unconditionally), and renamed the `TABLE` const. All 4 edge_field_e2e tests pass after the fix.

- **Fixed second SqlOperationProvider write-table miss** — `LoroShareBackend` factory in `loro_module.rs:310` was constructing the provider with `table_name="block"` (the matview). Changed to use `BLOCK_WRITE_TABLE` constant to match the earlier fix at line 125.

- **Discovered and fixed QueryableCache CREATE INDEX on matview crash** — `Block::type_definition().to_index_sql()` generated `CREATE INDEX ... ON block (parent_id)`, but `block` is now a matview and Turso doesn't support indexes on matviews. Modified `initialize_schema()` in `queryable_cache.rs` to skip schema init when the target object already exists as a view, letting `BlockMatviewSchemaModule` own the schema.

- **Fixed parse_block_row tag CSV mishandling** — The matview emits `tags` as JSON `"[]"`, but `parse_block_row` was calling `Tags::from_csv("[]")` on it, producing `["[]"]` instead of `[]`. Removed the erroneous `set_tags` override; the JSON parsing at line 143-155 was already correct.

- **Documented findings** — Updated memory file (`loro_sync_matview_write_regression.md`) with Turso panic details (`set_null_flag on unexpected cursor type` at `core/types.rs:2773`), which is a Turso-side issue exposed by the new chained matview shape and should be filed separately.

### Challenges

- **Dev DB schema mismatch** — User's dev DB carried the old `block` table from pre-migration. Resolved by having user delete the DB; added QueryableCache view-existence check to prevent future CREATE INDEX crashes on matviews.

- **Tag corruption in PBT** — The `parse_block_row` function was applying CSV parsing to the matview's JSON `tags` column, producing nested array corruption. Root cause: function tried to handle both org-property input (uppercase `TAGS`) and matview output (lowercase `tags`) with the same CSV logic.

- **Persisted regression seed failures** — `general_e2e_pbt` failed on `inv10d` with empty block children and a Turso panic. The Turso panic is a pre-existing Turso-side bug; the missing children are a consequence of that panic, not a holon regression.
