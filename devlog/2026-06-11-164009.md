## DBSP zset clone churn elimination via Arc-wrapped row values

Investigated and fixed the ~264MB allocation churn from whole-delta `Vec<(HashableRow, isize)>` clones across the DBSP operator graph (join, aggregate, antijoin, match-counter state machines and memo cache).

**What happened:**

- Read the handoff doc identifying clone sites in `process_node`/`execute_node` and traced them through the codebase
- Changed `HashableRow.values` from `Vec<Value>` to `RowValues = Arc<[Value]>` in `dbsp.rs`
- Updated all ~70 construction sites to use `impl Into<RowValues>`, keeping callers unchanged
- Switched `cursor.rs`, `view.rs`, and `compiler.rs` to the alias for consistency
- Ran full test suite (1939 turso_core tests pass), sqltests (9506 passed, 3 pre-existing MVCC failures), and matview fuzzer soak (40 seeded runs)
- Created `matview-delta` memory profile to measure impact (~1k rows, join/aggregate/LEFT-JOIN matviews with 1k DML)
- Compared against main via parallel worktree baseline build and perf captures

**Challenges:**

- `normalize_delta`'s HashMap iteration was randomizing UNION ALL rowid reuse, failing `test_normalize_delta_preserves_update_pair_for_union_all` ~40% of runs — sorted consolidation by first-occurrence input order fixed it (now 10/10 green)
- sqltests' tokio worker stack overflow reproduced identically on main (environmental, passes with `RUST_MIN_STACK=16M` on both)
- Matview fuzzer loop mode failed with generator "Too many local rejects" — switched to independent seeded runs instead

**Decisions:**

- Used `Arc<[Value]>` (slice, not `Vec`) to avoid double-allocation; constructors accept `impl Into<RowValues>` for ergonomics
- Introduced a type alias (`RowValues`) rather than inline `Arc<[Value]>` everywhere, following code-clarity patterns (no pre-existing alias existed)
- Measured via new `matview-delta` perf profile instead of unit microbench to catch real operator-graph behavior

**Status:** Committed, pushed to `ivm-arc-rowvalues` bookmark. HashableRow clone family reduced from **1.23M allocs / 73.7 MB → 0** on benchmark workload; total allocations 7.52M → 4.13M. All tests pass; matview fuzzer surface pre-existing correctness bugs (documented as follow-up candidates).
