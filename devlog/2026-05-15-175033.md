## GitHub MCP Client Sidecar Configuration

Adding a GitHub MCP server integration following the pattern of `claude-history.yaml`, with repository caching and vtable mappings for issues and pull requests.

**What happened**

- Reviewed and adopted a multi-phase plan addressing unknowns first: Phase 0 (probe GitHub MCP tool names and response schema), Phase 1 (verify nested-field handling), Phase 2+ (implementation)
- Accepted key improvements over initial approach:
  - Promoted schema verification to blocking phase 0, preventing wasted churn on incorrect YAML
  - Added explicit `source_path` handling for nested GitHub response fields (e.g., `issue.user.login`)
  - Used `#[serde(untagged)]` enum for `EnumerateFrom` back-compat with singular `field` syntax in existing configs
  - Switched to explicit `{owner, repo}` map syntax vs positional arrays for clarity and flexibility
  - Introduced `ResolvedFallback.bindings` as clean struct extension point
  - Documented pagination and rate-limiting caveats for multi-repository scenarios
  - Called out endpoint authentication gap (PAT vs Copilot OAuth) for Phase 0 resolution

**Decisions**

- Keep Phase 0 and Phase 1 separate despite overlap: separation clarifies which gates are blocking vs investigative
- Validation log with line-by-line source checks catches real issues (e.g., `enumerate_from` field placement in `mcp_vtable.rs` vs `integration_config.rs`)

**Status**

Plan finalized with rigorous unknowns map and back-compat safety. Ready for Phase 0 tool probe before YAML authoring begins.
