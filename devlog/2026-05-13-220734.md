## Fixed AggregateOperator SeekResult::TryAdvance bug in IVM populate

The materialized view populate path was losing aggregate state when GROUP BY keys grew wide enough to span btree leaf-page boundaries, causing row counts to drop to zero and json_group_array outputs to vanish.

**What happened**

- Reproduced the bug: block matview showed correct `tags=["Page"]` via incremental path, but from-scratch populate returned `tags=[]`
- Bisected trigger: 16-column GROUP BY + dual LEFT JOIN + `json_group_array(...) FILTER (WHERE ... IS NOT NULL)` + 164 real rows
- Added failing integration test `test_ivm_block_matview_drift::populate_after_data_returns_tag` that pins the issue
- Traced through AggregateOperator's apply_delta: `FetchKey` cursor seek was treating `SeekResult::TryAdvance` as `NotFound`
- With wide keys, `eq_only:true` seeks started returning `TryAdvance` instead of exact match, causing the code to skip `cursor.next()` and lose the existing aggregate state
- Multiset was rebuilt from scratch; LEFT JOIN producing `(b, NULL) weight=-1` and `(b, "Page") weight=+1` in same batch resulted in `state.count = 0`, skipping output emission

**Root cause & fix**

Both `FetchKey` seek (line 3115) and `FetchDistinctState::ReadValue` seek (line 3155) in `core/incremental/aggregate_operator.rs` now call `cursor.next()` + `cursor.has_record()` on `TryAdvance`, matching the JoinOperator fix pattern from 2026-03-11. The `eq_only:true` guard is insufficient — candidates can legitimately land past leaf boundaries.
