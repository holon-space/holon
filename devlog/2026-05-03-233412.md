## Measuring the `ensure_view` cache impact

**Context:** The prior profiling attributed ~18s/run (27% of `check_invariants`) to redundant `ensure_view` calls. The cache was implemented to eliminate those SQL round trips. Now measuring how many calls were actually cached.

**What happened:**
- Added atomic counters to `MatviewManager`: `view_exists_calls`, `cache_hits`, `ddl_creates` to track SQL round trips vs. cache hits.
- Incremented `view_exists_calls` on every call to the underlying `view_exists()` method.
- Incremented `cache_hits` on each cache-hit return path in `ensure_view()` and `preload()`.
- Exposed metrics via `BackendEngine::matview_stats()`.
- Added `Drop` impl on `E2ESut` to log final metrics at the end of each PBT case, gated by `is_running()` check.
- Built in release mode and prepared to run one full `general_e2e_pbt_sql_only` case to capture cache effectiveness.

**Build status:** Release build completed. Ready to run instrumented PBT case to see:
- Total `view_exists_calls` (baseline SQL round trips if no cache).
- Total `cache_hits` (round trips eliminated by the cache).
- `ddl_creates` (actual matview DDL operations, should be small — one per unique view definition).

**Next step:** Run one PBT case with metrics collection, then analyze the counter output to quantify the wall-time win. Once we have a concrete number (e.g., "318 cache hits, 22 DDL creates, 0.2s saved per case"), we'll decide whether to proceed with the `LiveData` experiment or if the cache alone is sufficient.
