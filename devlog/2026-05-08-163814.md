## Turso Matview First-Open Bug: Investigation, Workaround, and Upstream Fix

### Context
A fresh MCP connection's first query against the `block` materialized view returned partial results (28–54 rows instead of 1000), while subsequent queries on the same connection returned correct results. The plan was to build a minimal reproducer, implement a holon-side warmup workaround, and decide whether to keep the plumbing or revert it.

### What happened

- Built two reproducers (Turso public API + holon `turso_sdk_kit`) confirming the bug exists in Turso itself, not holon's wrapper. Fresh-connection reads return partial results on first matview access; same-connection reads are correct.
- Implemented a `SELECT COUNT(*) FROM block` warmup in `frontends/mcp/src/main.rs` post-bootstrap. Initial `LIMIT 1` warmup didn't work (short-circuited the cursor); full-scan `COUNT(*)` forced DBSP materialization and resolved the symptom.
- Reverted the entire `ensure_warmed` plumbing (`idle_signal` fields, function, call sites) once upstream Turso pin `290fbb4ff` ("fix: IVM matview cursor returns partial result on first read after IO yield") landed, making the workaround unnecessary.
- Audited for related Turso-bug workarounds: found `collapse_insert_delete_pairs` and `split_block` CDC drop rewrite both now redundant post-fix. Deleted `collapse_insert_delete_pairs` entirely (6 unit tests, 2 helper functions) after verifying `coalesce_row_changes` handles split_block correctly alone.
- Promoted both Turso reproducers from `cargo run --example` to `#[tokio::test]` for CI coverage (`turso_matview_first_open_partial`, `holon_turso_sdk_kit_matview_first_open`).
- Deleted now-dead example binaries (`turso_ivm_matview_first_open_empty_repro.rs`, `turso_ivm_split_block_cdc_drop_repro.rs`).
- Updated devlog and memory to FIXED status; updated `split_block_cdc_drop` memory entry to note the rewrite can revert to plain `set_field` UPDATEs in production once this pin ships.

### Deviations

**`LIMIT 1` warmup didn't work:** assumed any first read would warm the cursor; reality required full-scan `COUNT(*)` to force materialization. Second iteration to landing. **Public-API vs. holon-stack divergence:** public-API reproducer only triggers on fresh connections (B/D scenarios); holon-stack triggers on all four. Pinpoints that `turso_sdk_kit::rsapi::TursoConnection` behaves like a fresh connection per query — not operationally important post-fix, but useful for future Turso-bug debugging.

### Status
**Complete.** Turso pin `290fbb4ff` landed; warmup reverted; `collapse_insert_delete_pairs` and related workarounds deleted; both reproducers promoted to tests; workspace builds and all tests pass.
