# Phase 3.4 — sort_key sourced from Loro's internal fractional index

Date: 2026-05-11

## What landed

Until now we maintained `Block.sort_key` ourselves via
`crates/holon-core/src/fractional_index.rs::gen_key_between` and
shadowed it on a top-level Loro meta key written by
`update_block_sort_key` (Phase 3.2). Loro's `LoroTree` already keeps an
internal fractional index per node and exposes it as
`tree.fractional_index(target) -> Option<String>` in the exact same hex
format the `loro_fractional_index` crate produces — the format chord ops
already generate.

Phase 3.4 collapses the two:

- `read_block_from_tree` now reads `tree.fractional_index(node)` as the
  primary source of `Block.sort_key`. The legacy meta key remains an
  `ALLOW(fallback)` for older docs that haven't been migrated; once the
  fleet is migrated we can drop the `or_else`.
- `BlockCellRegistry::write_field("sort_key", new_key)` no longer
  writes a shadow meta value. It interprets `new_key` as a positional
  intent: scan the target's current siblings, find the sibling with the
  largest `tree.fractional_index` strictly less than `new_key`, and
  dispatch `LoroBackend::update_block_position(target, parent,
  predecessor)`. Loro's `tree.mov_after(target, predecessor)` (or
  `tree.mov_to(target, parent, 0)` when no sibling is smaller)
  generates the actual fractional index for the resulting position.
- The caller-computed `new_key` is discarded after the position lookup
  — it carried order info, not lasting value. Chord-op code stays
  unchanged (it still calls `set_field("sort_key", new_key)` with a
  key from `gen_key_between`); only the registry's interpretation
  changed.

## New / changed API surface

- `LoroBackend::update_block_position(target_id, new_parent_id,
  predecessor_id: Option<&str>)` — primary positioned-move primitive.
  `predecessor_id == Some(_)` → `tree.mov_after`; `None` → `tree.mov_to`
  with index `0`.
- `LoroBackend::update_block_sort_key` is `#[deprecated]`. Still callable
  for legacy paths: `apply_fields_changed`, `apply_create`,
  `apply_update_with_backend` keep using it so non-Loro-origin CDC
  events from the org-parser seed continue to write the shadow meta
  (which `read_block_from_tree`'s `or_else` reads). The deprecation
  warning is the marker for follow-up cleanup.
- `BlockCellRegistry::compute_position_for_sort_key` (private helper) —
  sibling scan that converts a caller's `new_key` into the
  `(parent_id, predecessor_id)` pair Loro's tree wants.

## Why this is correct

The registry-side conversion uses `tree.fractional_index` for sibling
comparison AND for the consumer's read. Both come from Loro, so the
order is internally consistent: a chord op computes a `new_key` from
two siblings' `Block.sort_key` values (which Phase 3.4 now sources from
Loro), the registry compares against the same siblings'
`tree.fractional_index` values (i.e. the same data), finds the same
gap, and calls `tree.mov_after` with the right predecessor. Loro
generates a new fractional index for the resulting position which the
consumer reads back on the next `read_block_from_tree` pass.

The chord-op-computed `new_key` and Loro's resulting fractional index
may differ as strings (Loro picks its own value), but they sit in the
same relative gap, so the ordering matches caller intent.

## Files touched

- `crates/holon/src/api/loro_backend.rs` — added
  `update_block_position` (`mov_after` / `mov_to`-based); deprecated
  `update_block_sort_key`; switched `read_block_from_tree` to
  `tree.fractional_index` with the legacy meta read as
  `ALLOW(fallback)`; added `update_block_position_reorders_siblings`
  test.
- `crates/holon/src/sync/block_cell_registry.rs` — added
  `compute_position_for_sort_key` helper; rewrote the `"sort_key"`
  arm in `write_field` to call `update_block_position` with the
  computed predecessor; dropped the call to `update_block_sort_key`.

## What did NOT change

- Chord ops in `crates/holon-core/src/traits.rs` still call
  `set_field(id, "sort_key", new_key)` with a `gen_key_between` result.
  The fractional-index module is still used. The only difference is
  what the registry does with the value.
- `apply_fields_changed`, `apply_create`, `apply_update_with_backend`
  in `loro_sync_controller.rs` still call the deprecated
  `update_block_sort_key`. These are the SQL→Loro inbound paths
  (org-parser seed, SQL-direct tests). They write the shadow meta key
  that `read_block_from_tree` falls back to. Routing them through
  `update_block_position` instead would need a sibling-scan helper
  shared with the registry; deferred until Phase 3.3 step 2 (the
  production gate flip) makes the inbound runtime path go quiet.
- `Block.sort_key` is still serialised to the SQL `sort_key` column by
  the outbound projector (`block_to_params` / `block_diff_params`).
  Phase 3.4 didn't change the SQL projection.

## Open follow-ups

- **Inbound sort_key cleanup**: route `apply_fields_changed`,
  `apply_create`, `apply_update_with_backend` through
  `update_block_position` (shared sibling-scan helper). Then delete
  `update_block_sort_key` and the shadow meta key write/read entirely.
  Best done alongside Phase 3.3 step 2 (production gate flip).
- **Drop `holon-core/src/fractional_index.rs`?**: chord ops still use
  `gen_key_between` to produce the `new_key` that the registry
  immediately throws away. We could replace the chord-op call with a
  sentinel like `set_field("sort_key", "after:<predecessor_id>")` —
  but that touches every chord op. Less invasive: keep
  `gen_key_between` as the chord-op-internal API and let the registry
  discard the value. The dead-code cleanup waits on a richer
  positioned-move call site refactor.
- **Same trick for parent_id?**: parent_id is structural, not
  fractional; it doesn't have the duplication problem sort_key did.
  No change needed there.
