## Flattening a merge diamond in jj history

The repository had a non-linear structure at the top of history: a diamond where two parallel docs commits (`vxmutrum`, `nvpwkmov`) split from a 7-way frontend merge and reconverged into a merge commit (`nvswsyqk`). The goal was to collapse this into a single linear commit.

**What happened**

- Attempted `jj squash` and `jj rebase` to flatten the structure, but both reintroduced conflicts during merge re-resolution
- Switched to a tree-preserving approach: created a fresh commit (`lmuwqovy`) on top of the frontend merge with `jj new`, then restored the exact final tree from the old merge commit using `jj restore`
- Verified the new commit was byte-identical to the old merge (0 files changed diff)
- Moved `main` and `dioxus-web-parity` bookmarks to the new commit and abandoned the old diamond commits

**Challenges**

- **Merge re-resolution conflicts**: jj stores merge commits as diffs against each parent. Reparenting or squashing forced jj to re-run the 3-way merge, reintroducing already-resolved conflicts. Solution: use `jj new` + `jj restore` to copy the final tree verbatim instead of replaying the merge logic.

**Decisions**

- Chose tree-copying over rebase because it guarantees the exact same final state without merge conflict re-resolution
- Preserved the accumulated merge message (now ~115KB) for now — can be trimmed separately if needed
- Noted that pushing will require a force/lease push since history was already published

**Status**: Diamond successfully flattened into a single linear commit; bookmarks updated and ahead of origin pending force push decision.
