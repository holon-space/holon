# 2026-05-13 — `holon-mcp` ~40% CPU root cause + actor instrumentation

## What was happening

`./target/debug/holon-mcp --stdio --orgmode-root /Users/martin/Workspaces/pkm/holon-pkm :memory:`
(PID 30417 at investigation time) was holding ~28–40% CPU at idle. No client
requests were in flight — the proxy chain (reloaderoo → mcp-rust-proxy → holon-mcp)
was attached but quiet.

## How we found it

`samply` can't attach without entitlements on macOS, but the built-in `sample`
profiler works without setup:

```sh
sample 30417 5 -file /tmp/mcp.sample.txt
```

Aggregating the per-frame weights (see `$CLAUDE_JOB_DIR/mcp.sample.txt` from the
investigation session), the busy stacks all land on one path:

```
TursoBackend::run_actor
  → TursoBackend::process_actor_command
    → TursoBackend::handle_query
      → turso::rows::Rows::next
        → DbspCircuit::run_circuit / execute_node
          → JoinOperator / MatchCounterOperator / BTreeCursor
```

So the Turso actor was constantly draining commands and each one was making
the incremental-view-maintenance circuit re-fire. The proximate cause is "the
DBSP circuit is running constantly"; the upstream cause is whatever is feeding
the actor with writes and matview reads.

## Persistent instrumentation

To make this observable in any future run without re-profiling, the Turso
actor now optionally records per-command + per-CDC-relation stats and dumps
them to tracing at a fixed interval.

### Enabling

```sh
HOLON_ACTOR_STATS=5  # window size in seconds; HOLON_ACTOR_STATS=1 → 5s default
RUST_LOG="holon::storage::turso::actor_stats=info,..."
./target/debug/holon-mcp ...
```

### What you get

Every window the logger emits three kinds of lines (target
`holon::storage::turso::actor_stats`):

```
[actor-stats] cmds=134 busy=10.1% top: ExecuteDdl=70(144ms) Execute=13(18ms) Query=37(9ms) ...
[actor-stats sql] 1x 39.3ms total: CREATE MATERIALIZED VIEW block_with_path AS WITH RECURSIVE ...
[actor-stats cdc] raw->coalesced per relation: block=15->13 watch_view_1570347602dda3f9=11->11 ...
```

- `busy=X%` is the fraction of wall time the actor spent inside
  `process_actor_command`. Sustained >30% with no client traffic is the
  signal that something is feeding the actor.
- `[actor-stats sql]` lists the top 5 SQL fingerprints by total time in the
  window — first 100 chars, whitespace collapsed.
- `[actor-stats cdc]` lists the top 8 CDC relations by raw change count;
  `raw->coalesced` shows how much each batch shrank after dedup.

The hash maps are reset every window so each line is "what happened in the
last N seconds," not cumulative.

### What the readings will look like for the bug

When this instrumentation is wired up on a fresh `holon-mcp --orgmode-root
…` startup, expect the first few windows to be dominated by `ExecuteDdl`
(matview creation) and `Execute` (bulk org-file ingestion via the
`OrgFileWatcher` initial scan). After that, in steady-state idle, the lines
should be near-empty — anything firing constantly post-startup is the
40%-CPU culprit. The smoke test in the worktree showed 134 commands in 2s
during startup-only traffic; idle on a quiet org-root should be ≪10
commands per window.

## Code

- `crates/holon/src/storage/turso_actor_stats.rs` — counters, fingerprinting,
  the 5s logger task.
- `crates/holon/src/storage/turso.rs` — `run_actor` records `(variant,
  sql_fingerprint, elapsed)` per command; the CDC `set_change_callback`
  closure records `(raw, coalesced)` per relation.

Both are gated on `HOLON_ACTOR_STATS`. When unset, the actor allocates no
`ActorStats` and the per-command hot path is unchanged (just an
`Option::is_none()`).

## Real root cause (second pass — from `holon-mcp` log file)

Once the instrumented binary was in place and we read its full `tracing`
output (the stdio path already writes everything to
`HOLON_MCP_LOG_FILE` — default `$TMPDIR/holon-mcp-<unix-ts>.log`), the
sample-based picture was eclipsed by an obvious finding. In ~7m47s of
idle operation the log accumulated:

| Event | Count | Rate |
|---|---:|---:|
| Turso actor panic `Reached invalid state! State was replaced, and not replaced back.` | 3003 | **6.4 / s** |
| Downstream `Actor response channel closed` | 2989 | ~6.4 / s |
| `[OrgMode] poll_external_changes error` (every 100ms poll fails) | 971 | ~2.1 / s |
| `re_render_all_tracked` fallback error | 414 | ~0.9 / s |
| `re_render_all_tracked` "No document found for path …" | 828 | ~1.8 / s |
| `Block change error for block:…` | 414 | ~0.9 / s |

The actor catches the panic via `catch_unwind` (turso.rs:1477), survives,
but the in-flight command's `oneshot::Sender` is dropped. Anything
holding the response receiver gets `Actor response channel closed`. The
`OrgSyncController`'s 100ms poll tick at
`crates/holon-orgmode/src/di.rs:961` keeps hammering the broken actor.
The 96% CPU is the cost of repeatedly catching the panic + retrying.

The panic message originates upstream:
`core/incremental/aggregate_operator.rs:2201` — the commit state machine
uses `std::mem::replace(self.commit_state, AggregateCommitState::Invalid)`
to take ownership during a loop iteration, then assigns the new state.
If commit returns I/O before restoring state, the next call sees `Invalid`
and panics. The comment at line 2194 calls this out: "we have to restore
the state if we return I/O. So we can't use `return_if_io!`".

## Reproduction

Two `AggregateOperator` panic variants exist in current Turso pin
`71ae352e`. Both fire on matviews using `json_group_array` /
`group_concat` over a LEFT-JOINed edge table — the exact shape of the
holon `block` matview (`crates/holon/sql/schema/block_matview.sql`):

1. **`aggregate_operator.rs:1470`** — *"json_group_array multiset went
   negative … delta consolidation invariant violated"*. Reproduces
   deterministically by replaying
   `crates/holon/sql/regressions/2026-05-08-block-matview-multiset-negative.sql`:

       cargo run --bin turso-sql-replay -- replay \
         crates/holon/sql/regressions/2026-05-08-block-matview-multiset-negative.sql

   The trigger is an INSERT + DELETE on `block_tags` where the deleted
   `tag` value also appears in *other* blocks. The minimizer can only
   shrink this from 147 → 146 statements — the bug needs a population of
   overlapping tag values across many parent blocks before it fires.

2. **`aggregate_operator.rs:2201`** — *"Reached invalid state! State was
   replaced, and not replaced back"*. This is the panic the live
   `mcp-pkm` process is hitting at 6.4/s. The existing 13 reproducers in
   `crates/holon/src/storage/turso_ivm_join_test.rs` all *pass* under
   the current pin — they target the older `MatchCounterOperator`
   path. To capture this variant as a standalone repro, enable
   `HOLON_TRACE_SQL=1` on the live MCP (alongside `HOLON_ACTOR_STATS`),
   reload, let the panic fire a few times, then feed the log through
   `turso-sql-replay extract | minimize --crash-pattern 'Reached invalid state'`.

## Recommended next steps

1. Bump the Turso pin to a version that fixes both panics, OR file the
   regression file from this devlog upstream as a clean repro.
2. Add a circuit breaker in `OrgSyncController`'s poll loop: after N
   consecutive `Actor response channel closed` errors, back off from
   100ms to 5s polling and surface a banner. The current behaviour
   spends 96% CPU silently retrying — closer to the fail-loud principle
   in CLAUDE.md.
3. Investigate why so many block events arrive without a recognizable
   `routing_doc_uri` (the 414 `re_render_all_tracked` fallbacks +
   828 "No document found" warns suggest paths under `_archive/` and
   files with spaces are getting routed to a `re_render_all_tracked`
   fallback that itself can't resolve them). May be related to memory
   entry `phase3_7_followups_landed.md` not covering all event sources.
