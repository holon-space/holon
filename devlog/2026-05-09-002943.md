## Phase 1 & 2: Loro as Preferred Content Writer—Design & Implementation

**Context:** Split-block was reading stale SQL projections while user edits lived in Loro's MutableText, silently discarding pending changes. After landing Phase 0 (PBT reproducer) and Phase 1 (live_content resolver hook), Phase 2 began refactoring toward Loro as the preferred writer—but fundamental design questions emerged about architecture and trait boundaries.

**What happened:**

- **Phase 0 (LANDED):** Built `headless_editor_mirror.rs` (~190 LoC) to model per-keystroke typing in PBT; relaxed focus-gate for headless mode; verified bug reproducible in ~25s.
- **Phase 1 (LANDED):** Added `BlockContentResolver` trait + `live_content` hook to `BlockOperations`; wired `LoroBlockContentResolver` + `LoroDocTextResolver` (with STABLE_ID prefix-strip fix); made split/join read from Loro; synchronized provider wiring in PBT to close race. Both Full and SqlOnly variants GREEN (~240s).
- **Phase 2 steps 1–3 (LANDED):** Made `handle_text_sync` a no-op for content (per-keystroke writes already project via `on_loro_changed`); added `set_live_content` to route chord ops (split/join/embed) through Loro first; dropped `_expected_content` watermark (no-op regress guard). All commits GREEN (~550s each).

**Challenges:**

- **bulk-1-0 deterministic flake:** CDC sees `"LM"` from first emission (before TypeChars fire), suggesting org-renderer round-trip writes initial state to SQL. Not a Phase-2 regression; separate issue.
- **Design reckoning at step 4:** Questioned whether to drop SQL `set_field` fallback for chord ops (would break SqlOnly) and inbound SQL→Loro sync (would orphan external writers). Current `BlockContentResolver` shape only fits Loro + MutableText neatly; feels ad-hoc beyond that.

**Decisions & Open Questions:**

- **Loro as preferred, not mandatory:** Kept SQL fallback (`set_live_content` returns false → `set_field` runs) to preserve "Loro is optional" modularity. This proved correct—the architecture degrades gracefully.
- **Trait unification:** Your insight: could Loro and Turso both implement a single `LiveContentStore` trait, with wiring determining the leader? This collapses `BlockContentResolver` (resolve) + `set_live_content` (write) into one shape.
- **`set_live_content` vs `set_field`:** Nearly identical signatures (`&str` vs `Value`). Why two? Should they be one method, or does the distinction serve a purpose?
- **`BlockContentResolver` shape critique:** Currently cache-with-delay listening to event bus. Does Turso need the same pattern, or is the abstraction wrong? Would a unified event-driven approach work for both stores?
- **`OperationResult.changes` flow:** Is the sync path (`operation_wrapper.rs:98 → sync_provider.sync_changes`) synchronous (SQL) or event-driven (Loro)? Affects how step 4–5 should be tackled.

**Status:** Phase 2 steps 1–3
