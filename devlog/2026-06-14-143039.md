## Implementing C4 System and Code Levels in archidoc Fork

**Context:** The archidoc fork was missing the top (`System`) and bottom (`Code`) levels of the C4 model, limiting architecture diagram expressiveness. Additionally, relationship validation had been half-built but never wired into the CLI.

**What happened:**

- **Part (a) — instant arrows:** Added `@c4 uses` declarations to 17 crate `lib.rs` files, derived from actual `cargo metadata` dependency graph. Component diagram went from 0 → 63 relationship arrows; baseline refreshed; `arch-validate` stays green.

- **Part (b) — relationship validation CLI:** Implemented `archidoc ir check-deps` subcommand in fork. Revived existing dead code (`ImportGraph`, `validate_relationships`) by building a `cargo_metadata.rs` adapter that reads workspace deps directly (no external tool). Detects both drift directions: missing edges (real dep, no `@c4 uses`—prints paste-ready suggestions) and stale edges (declared but no real dep). `--strict` exits 1 for CI. Tested against perturbed IR; all 3 new unit tests pass.

- **`@c4 system` level:** Added `C4Level::System` variant + parser + `generate_context()` → `c4-context.puml`. Container diagram renders system nodes as `System_Ext()` so cross-level arrows resolve. Verified end-to-end.

- **`@c4 code` level:** Heaviest feature. Extended parser to use `syn` to extract item-level `@c4 code` markers from `struct`/`enum`/`trait`/`fn` docs (previously only read module `//!` docs). Added `CodeElement` IR type, walker aggregation, and `generate_code()` render path → `c4-code.puml`. Targets in code arrows resolve to qualified component IDs for proper linking.

**Challenges:**

- Archidoc's walker reads only module-level `//!` docs. Item-level `///` parsing required adding `syn` item enumeration to `extract_code_elements()`, carefully positioned to avoid breaking the module-doc extraction path.
- Code element targets needed qualified resolution—bare struct names in `@c4 uses` were pointing to wrong nodes until target lookup was scoped to same-owner component.
- Pre-existing test failures in `polyglot_detection_test` suite (6 unrelated CLI surface issues on untouched `dev`) required verifying they pre-existed before committing.

**Decisions:**

- Kept code-level nodes **curated, not exhaustive**—`@c4 code` requires explicit markup; `ast-outline` already dumps every symbol. This preserves archidoc's identity: intentional, relationship-bearing architecture, not raw reflection.
- Revived `ImportGraph` instead of rebuilding—reused existing `RelationshipWarning` types and drift-detection logic.
- Split into three commits (check-deps, system, code) so upstream can accept/modify independently.

**Status:** PR #1 open at https://github.com/nightscape/archidoc/pull/1 with 3 commits (check-deps, `@c4 system`, `@c4 code`). All tested and building clean. Holon working tree has `@c4 uses` arrows uncommitted for review. Next: wire `just arch-check-deps`
