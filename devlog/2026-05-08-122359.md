## Materialized View Cursor IO-Resume Bug Fix

The first SELECT against a freshly-populated materialized view on a fresh database connection returned a partial subset of rows instead of the complete result set. Subsequent queries returned the correct full result.

- Reproduced bug in integration test: first query returned 83 rows, second query returned 1000
- Root cause: `MaterializedViewCursor::next()` at `core/incremental/cursor.rs:714` resumed from IO with `target_rowid=0`, but `process_btree_changes` uses this value in `zset.seek(target_rowid, op)`. For matviews with hash-based negative rowids, seeking to 0 returned empty, so cursor iteration terminated prematurely without finding matches
- Fixed by storing original `target_rowid` in `SeekState::Seek` and `SeekState::Advancing` structs as `original_target_rowid` field that survives IO yields, allowing the resume path to retrieve the correct seek target
- Verified: 72 IVM integration tests pass, 1715 turso_core unit tests pass, 152 sqltests pass, all 4 reproducer scenarios now correct
