## Debugger Session: Investigating SplitBlock Starvation

**Context**: The PBT test runs 50 transitions but zero edit transitions (including `SplitBlock`) ever fire. Previous analysis suggested the issue is in `main_editable_descendants()` returning empty, but the root cause—whether it's missing focus roots or no descendants under them—was unclear. Debugger session aimed to inspect the data flow.

**What happened**:
- Built `gpui_ui_pbt` with `debugger` profile (full debug symbols) to enable variable inspection in LLDB.
- Set breakpoints at `main_editable_descendants` (line 1188) and `filter_to_rendered` (line 79) to trace the data flow for `ClickBlock` and `SplitBlock` generators.
- Inspected locals when generators hit: **`editable_block_ids` was size=0 for both `Indent` and `SplitBlock`**.
- Drilling into `main_editable_descendants`: the function calls `expected_focus_root_ids(Region::Main)` and then filters descendants of those roots through `live_geometry::filter_to_rendered`.
- Attempted to inspect `open_pins[Main]` to determine if the root set itself is empty, but hit LLDB memory/REPL limits when expanding large state structures.

**Challenges**:
- **LLDB memory ceiling**: Expanding the full `ReferenceState` struct hit the 4GB limit; had to switch to surgical breakpoints instead.
- **Locals optimization**: Initial build with `debug = "line-tables-only"` stripped all locals; required rebuild with full debug info.
- **REPL inspection limits**: LLDB REPL didn't return output for complex expressions; had to pivot to breakpoint-side-effect strategies instead.

**Decisions**:
- Switched from full struct inspection to **targeted breakpoints at critical points** in the data flow (entry/exit of `main_editable_descendants`, post-filter in generators) to avoid LLDB saturation.
- Prioritized confirming the **symptom** (editable_block_ids size=0) over immediately debugging the root cause, since the starvation is already documented.

**Status**: Confirmed via debugger that `editable_block_ids` is empty at the point where `SplitBlock::weighted_generator` would use it to filter candidates. Root cause remains: either `expected_focus_root_ids(Main)` is empty (no focus pin) or no `Text` descendants exist under the pinned root after geometry filtering. Next session should inspect `open_pins` or take a targeted snapshot of Main-region descendants post-filter to isolate which stage is the bottleneck.
