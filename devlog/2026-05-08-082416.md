## Investigated and Fixed LEFT OUTER JOIN Matview Row Deletion Bug

**Context**: Redundant `UPDATE` statements on a `LEFT OUTER JOIN` materialized view with an empty right side were incorrectly dropping null-padded rows, causing the matview row count to drop from 1 to 0.

**What happened**:
- Reproduced bug: minimal case with single `LEFT JOIN`, no-op `UPDATE` caused row deletion
- Wrote failing tests in `ivm-left-join.sqltest` (#40 minimal repro, #41 with GROUP BY matching holon shape, #42 multi-update transaction)
- Enhanced differential fuzzer with `--redundant-dml-probability` flag to re-execute successful DML statements, catching idempotency bugs
- Verified fuzzer reproduces the bug on broken code (seed 101: Dual LEFT JOIN matview)
- Identified root cause in `MatchCounterOperator::commit()` and `eval_internal()`: deltas processed entry-by-entry without seeing each other's storage state updates
- Implemented fix: consolidated `deltas.left` and `deltas.right` at operator entry, allowing no-op UPDATEs to cancel before per-entry processing
- All three new tests pass; fuzzer previously-failing seeds (1, 100, 101) now pass

**Challenges**:
- Test #41 originally used `COUNT(j.tag)` which exposed a separate pre-existing bug (`COUNT(NULL)` returns 1 instead of 0 on null-padded rows); switched to non-aggregate verification
- Pre-existing test failures in rollback and CDC tests unrelated to this fix; confirmed via baseline run

**Decisions**:
- Consolidated deltas at operator entry rather than per-row to preserve multi-statement transaction semantics
- Added fuzzer flag with 0.1 default probability in matview mode to catch similar idempotency regressions

**Status**: Fix merged (`sypzkuos 05c33267`), holon bookmark updated, pushed to origin, fuzzer running extended validation.
