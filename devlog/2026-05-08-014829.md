## Debugged and set up live-reload workflow for holon-mcp

The `now-query` block was returning 0 rows on first call despite the database being fully loaded, and the dev workflow needed optimization for faster iteration.

**What happened:**
- Found that `.mcp.json` was pointing to `:memory:` with no `--orgmode-root`, so the DB was empty — patched to load `/Users/martin/Workspaces/pkm/holon-pkm`
- Discovered a real bug: `execute_source_block` returned 0 rows while identical SQL via `execute_raw_sql` returned 3 rows
- Implemented `ensure_warmed()` in server.rs with `OnceCell` to block first DB request until OrgSync reaches quiescence
- Set up live-reload dev workflow: switched from `cargo run` to `reloaderoo proxy` wrapper around the binary, with `cargo-watch` killing the process on rebuild for instant respawn

**Challenges:**
- **MCP handshake timeout**: adding `wait_for_ready=true` in startup made Claude Code timeout before stdio could respond. Solved by using `reloaderoo` to handle the proxy protocol immediately, deferring the actual wait until first query.
- **Process matching**: `pkill` matching cargo-watch's shell invocation accidentally. Fixed with explicit `pkill -x holon-mcp` to match binary name only.
- **Startup race ruled out**: matview had 968 rows immediately, but first cursor-open still returned 0 even after 25s quiescence wait — the ingestion-lag hypothesis was wrong. Likely root cause is Turso's `MaterializedViewCursor` lazy-opening behavior on autocommit.

**Decisions:**
- Used `OnceCell` for the warm gate rather than checking every request — amortizes the quiescence wait to first call only
- Kept `cargo-watch` as the rebuild trigger rather than polling — cleaner signal-based model

**Status:** Live-reload workflow operational; `now-query` returns 3 rows successfully on calls after the first. The zero-on-first-open bug persists despite warm-up — next session should investigate Turso cursor semantics or file upstream.
