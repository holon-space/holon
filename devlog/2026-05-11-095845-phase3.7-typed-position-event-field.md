# Phase 3.7 — typed `Event.position_after_block_id`; `_routing_after_block_id` retired

Date: 2026-05-11

## TL;DR

The `_routing_after_block_id` HashMap-smuggling convention is gone. Positional intent
for `EventKind::Created` (and now `Updated`) rides on a typed
`Event::position_after_block_id: Option<String>` field. Producers (split_block,
OrgSyncController) feed it via the unprefixed `after_block_id` param key; the SQL
operation provider lifts the value onto the typed field and drops the key from both
SQL columns and payload data. Consumers (`apply_create`, `apply_update_with_backend`)
read the typed field — no payload-side string lookups, no underscore-prefix
convention, no second-class look.

A side effect of the cleanup, not the headline: the **gen-strategy-mismatch class**
of Full-PBT failures collapsed from "first 2–3 children fully reversed" to "one
adjacent pair swapped" against a *different* root cause — see "Open follow-up"
below.

## Why

> "Is there a reason why `_routing_after_block_id` got this kind of syntax that
> makes it look like a non-official parameter? To me it's on the same level as
> `parent_id`, or is there something (except optionality) that distinguishes
> these two?"

The honest answer was: yes, `parent_id` is a stored field and
`_routing_after_block_id` is in-flight event-routing metadata, but the underscore
prefix was a pragmatic patch over the fact that the create-op payload was an
untyped `HashMap<String, Value>` and there was no other way to keep a non-column
field out of SQL. That convention worked, but at the API surface there was no
visible distinction between "real block field" and "operation-control hint" —
just a string key, and a `_routing_`-prefix filter in `SqlOperationProvider`.
Stage 2 makes the distinction structural.

## What landed

### Typed Event field + monotonic IDs

`crates/holon/src/sync/event_bus.rs`:

- New `pub const POSITION_AFTER_BLOCK_ID_PARAM = "after_block_id"`.
- New `Event::position_after_block_id: Option<String>` field, serde-default for
  backwards-compat with persisted events.
- New `Event::with_position_after_block_id(self, Option<String>) -> Self` builder.
- New process-global monotonic ULID generator
  (`once_cell::Lazy<Mutex<ulid::Generator>>`). `Event::new` uses it via
  `next_event_id()`. `Ulid::new()` is non-monotonic within a single millisecond,
  so two events emitted from the same batch in the same ms could sort in either
  order under `ORDER BY created_at, id` — breaking the dependent-order
  application of `tree.mov_after` chains. The generator gives strictly
  increasing IDs within the same ms; on the extremely rare counter-exhaustion
  wraparound (>2^80 events in 1 ms), falls back to `Ulid::new()` for one ms
  and self-heals on the next tick.

### Producer-side wiring

`crates/holon/src/core/sql_operation_provider.rs`:

- `partition_params` now treats `POSITION_AFTER_BLOCK_ID_PARAM` as
  operation-control metadata: skipped from SQL columns AND from the
  `extra_props` bag. Same handling class as `_routing_*` and `_expected_*`,
  but matched by exact key instead of underscore prefix.
- `build_event_payload` skips it explicitly — does not put it under
  `payload.data` or at the payload top-level.
- `prepare_create` extracts `after_block_id` from params and threads it onto
  the constructed Event via `.with_position_after_block_id(...)`.
- `publish_event` now takes an `Option<String>` for the typed positional
  intent so single-op call sites (the non-batch `execute_operation` arms) can
  attach it too.
- `execute_batch_with_origin`'s post-SQL Update-event construction (Phase 2b
  of the batch path) was emitting Updated events via `make_event` without the
  typed field; it now keeps the per-op `after_block_id` alongside `id` in the
  `update_ids` vec and threads it onto the Event.

### Producer-side call sites

- `crates/holon-core/src/traits.rs::split_block` — emits `after_block_id`
  (no prefix). The literal mirrors `POSITION_AFTER_BLOCK_ID_PARAM` from
  `holon`; `holon-core` cannot depend on `holon` so the contract is
  duplicated as a string, documented in-line.
- `crates/holon-orgmode/src/org_sync_controller.rs::on_file_changed`:
  - Walks `new_blocks_vec` once in document (DFS) order to compute a
    `predecessors: HashMap<EntityUri, Option<EntityUri>>` map keyed by
    block id. Existing siblings anchor the position of subsequent new
    siblings, so the per-parent cursor advances on every block — not just
    on new ones.
  - The creates pass looks up `predecessors[block.id]` and injects
    `after_block_id` into the create-op params for every new block.
  - The updates pass *also* injects `after_block_id`. Without this,
    re-canonicalised sort_keys (e.g. when a 2nd `BulkExternalAdd` grows a
    parent's sibling set and every sibling's `gen_n_keys`-assigned
    sort_key shifts) would fall back to `apply_sort_key_hint` and trigger
    the gen-strategy-mismatch path again on updates.
  - The updates pass iterates `new_blocks_vec` (document order), **not**
    the `new_blocks` HashMap. `LoroSyncController` applies events
    serially; if the updates arrived in HashMap-iteration order, a later
    sibling could `tree.mov_after` against its predecessor *before* the
    predecessor itself had been repositioned, scrambling the list.

### Consumer-side

`crates/holon/src/sync/loro_sync_controller.rs`:

- `apply_create`'s signature changed: `payload: &HashMap<String, Value>` →
  `position_after_block_id: Option<&str>`. Caller in `on_inbound_event_inner`
  passes `event.position_after_block_id.as_deref()`.
- `apply_update_with_backend` takes the same typed arg and routes through
  `update_block_position(target, parent, Some(after_id))` when set. The
  `sort_key`-hint path stays as `// ALLOW(fallback)` for SQL-direct test
  writes that don't use the typed channel — disclosed dual path.
- The early-bypass inside `apply_create` (`block already exists → defer to
  apply_update_with_backend`) propagates the typed arg through.

### Transport round-trip

`crates/holon/src/sync/turso_event_bus.rs`:

The events SQL table has a fixed column set. We round-trip the typed Event
field through the payload JSON under a designated transport key,
`POSITION_AFTER_BLOCK_ID_PAYLOAD_KEY = "__transport_position_after_block_id"`,
purely so persisted events can be rehydrated with the typed field intact:

- `publish` and `publish_batch`: just before JSON-serialising payload, flush
  `event.position_after_block_id` into payload under the transport key.
- The CDC-stream parser (`parse_event_row` / replay path) removes the
  transport key from payload and lifts it back into the typed Event field —
  so downstream consumers only ever see the typed view, never the string.

The transport key is an implementation detail of the SQL persistence layer
and is not a producer-facing API. Memory-only buses (none today, but a
future possibility) would skip the serialise/deserialise round-trip and
preserve the typed field directly.

### Pre-existing-warning sweep

While editing `event_bus.rs` the archlint `[no-underscore-params]` rule
flagged a pre-existing `async fn consumer_position(&self, _consumer: …)`
trait default that uses neither parameter. Renamed to bare `_` per the
rule's own guidance.

The Full-PBT failure mode visibly shrunk across the fix iterations:

1. **Pre-Stage-2**: first 2–3 children fully reversed under the parent
   (gen-strategy mismatch on every block in the batch).
2. **After typed field on creates**: one pair (`bulk-0-0` between
   `bulk-11-3` and `bulk-11-4`) — updates path was still using the hint.
3. **After typed field on updates**: still one pair swapped — same
   blocks. Update events being applied in HashMap-iteration order.
4. **After document-order iteration**: still one pair — same blocks. ULIDs
   created in same ms got non-monotonic random tie-breakers.
5. **After monotonic ULIDs**: still one pair — different cause now, see
   open follow-up. Order is preserved correctly through the typed
   pipeline; the remaining bug is structurally distinct.

## Open follow-up

Tracing the residual failure showed: when a 5-block create batch is
dispatched under the same parent, the **first** block flows through
`apply_create` normally; the **remaining four** all take `apply_create`'s
early-bypass to `apply_update_with_backend` because Loro reports they
*already exist*. The `[POS-TRACE apply_update]` lines correctly show
`(typed)` and correct `parent` / `after` — the typed-field plumbing is
fine. But because the four blocks are already in the tree at some
arbitrary position, the `tree.mov_after` calls don't produce the final
file order; instead they shuffle blocks from whatever state preceded.

These four blocks could not have been created by this batch's CDC events
(those are the events currently being processed). The trace shows no
prior application path for them in this test instance. Candidate sources:

- An **outbound-side echo** that already wrote them to Loro before the
  inbound CDC handler got around to them.
- A **second sync provider** (Loro snapshot import? Peer import?
  `OrgmodeSyncProvider`?) that runs in parallel with `OrgSyncController`
  and also imports the org file into Loro.
- A **snapshot load** racing with the file watcher's initial scan.

This is structurally distinct from the routing-field cleanup and gets its
own task. Independent of Stage 2: the typed-field pipeline is correct;
the bug is that some other path is racing the typed path into the same
tree.

  ULID generator + tidy-up on `consumer_position` trait default.
- `crates/holon/src/sync/turso_event_bus.rs` — payload-transport
  round-trip; deserialiser construction now picks up the typed field.
- `crates/holon/src/core/sql_operation_provider.rs` — param-skip in

- `crates/holon/src/sync/loro_sync_controller.rs` — `apply_create` /
  `apply_update_with_backend` signature + body; early-bypass propagation.
- `crates/holon-core/src/traits.rs::split_block` — emits `after_block_id`
  param (no prefix) with link-back doc to the constant.
- `crates/holon-orgmode/src/org_sync_controller.rs::on_file_changed` —
  document-order predecessor walk; creates AND updates emit the typed
  param; updates iterate `new_blocks_vec` (not the HashMap).

## What did NOT change

- `Block.sort_key` is still a SQL column and still gets populated by the
  outbound projector from `tree.fractional_index`. Stage 2's typed-event
  cleanup is orthogonal to the "make sort_key a strictly read-only
  projection" cleanup proposed earlier; that's a separate move.
- Chord ops (`move_to_position`, `move_block`, `join_block`'s reparent
  loop) still call `set_field("sort_key", gen_key_between(...))`. The
  `BlockCellRegistry::write_field`'s `sort_key` arm still translates that
  into a `tree.mov_after`. That arm is internally consistent for chord-op
  flows (caller computes the hint from `tree.fractional_index`-sourced
  sibling values), so it doesn't hit the gen-strategy mismatch. Migrating
  chord ops to a typed positional API on the cell registry is a
  follow-up.
- `_routing_doc_uri` still uses the underscore-prefix convention. It's a
  separate routing concern (which file owns this block) and OrgMode's DI
  graph already plumbs it through `ROUTING_DOC_URI_KEY`. Worth converting
  to a typed field in the same Event-builder pattern as a follow-up;
  scoped out of this change.

## Architectural note

Position is a **relation between siblings**, not a stored scalar. The
fractional-index encoding (`Block.sort_key`, Loro's
`tree.fractional_index`) is one *projection* of that relation, useful
because it allows `ORDER BY` to do the right thing in SQL. But position
intent should never be expressed by handing a fractional-index string
across an API boundary, because two generators of those strings can
disagree on what region of the lex space each value "lives in"
(`gen_n_keys` distributes evenly across `[0, 1)`; Loro's `mov_after` /
`mov_to` picks midpoints of the remaining gap). The typed
`position_after_block_id` carries the relation directly (the predecessor
block's stable id) and leaves the encoding entirely to the consumer
(`tree.mov_after` resolves to whatever fractional index it wants).

## How this fits the bigger Loro-authority story

The umbrella refactor — "move authority over the `block` entity from
Turso to Loro" — has been landing in named phases (1, 2, 3.2, 3.4, 3.5,
3.6, 3.7). The production flip lives in
`crates/holon/src/sync/loro_module.rs::register_services`, in the
`LoroSyncControllerHandle` factory's `Ok(handle)` arm:

```rust
let _hold_gate_open = &handle;       // <-- delete this
// handle.disable_inbound_runtime(); // <-- uncomment this
```

When `disable_inbound_runtime()` is called:

- The inbound runtime gate closes for everything except `EventOrigin::Loro`
  (echo-suppressed) and `EventOrigin::Org` (whitelisted because that's the
  file-watcher's legitimate post-startup SQL→Loro source).
- All other origins (`Other("sql")` — chord ops, MCP test writes, …) get
  *dropped* by the gate and counted on
  `inbound_runtime_drop_count`. That is the production "Loro is now the
  source of truth for blocks" state: chord ops MUST go through the cell
  registry (which writes to Loro directly), not through SQL→CDC.

Why it's still held: flipping the gate exposes any code path that
inadvertently writes blocks via SQL→CDC, turning a latent
"intermittently-correct" path into a hard drop. Phase 3.7 closes the
biggest class of failures that surface under the flip
(`apply_sort_key_hint` gen-strategy mismatch), but the residual
phantom-Loro-exists issue (Open follow-up above) needs to land first.

## Roadmap to gate flip + post-flip cleanups

In rough priority order:

1. **Resolve the phantom-Loro-exists flake** (Open follow-up above).
   Source-trace the second-writer path that's populating Loro before
   `apply_create` runs. Once identified, either remove the duplicate
   path or make the inbound apply idempotent in tree-position order.

2. **Flip the gate** (`handle.disable_inbound_runtime();` —
   uncomment in `loro_module.rs`). Run Full + SqlOnly PBT (both should
   be GREEN). The `let _hold_gate_open = &handle;` marker comes out
   in the same patch.

3. **Add the gate integration test** (deferred from Phase 3.3 step 2's
   original spec). Lives in
   `crates/holon-integration-tests/tests/inbound_runtime_gate.rs` (or
   similar). Asserts:
   - boots a fixture with `OrgFileWatcher` + the gate closed;
   - writes a file mid-test → blocks reach Loro (Org whitelist works);
   - performs a chord op → `handle.inbound_runtime_drop_count() == 0`
     (chord ops correctly route via cells, not SQL→Loro inbound);
   - manually publishes a non-Loro non-Org event →
     `inbound_runtime_drop_count()` increments (the gate actually drops).

4. **Stage 2-plus: retire the sort_key write path entirely** (separate
   PR after the gate flip is stable):
   - Chord ops (`move_to_position`, `move_block`, `join_block`'s
     reparent loop) stop calling `set_field("sort_key", …)`. Replace
     with a typed positional API on `BlockCellRegistry`:
     `set_position(target: &EntityUri, parent: &EntityUri,
     after: Option<&EntityUri>) -> Result<()>`.
   - `BlockCellRegistry::write_field`'s `"sort_key"` arm disappears
     (along with `compute_position_for_sort_key` and the sibling-scan
     helper it shares with `find_position_for_sort_key_hint`).
   - `apply_fields_changed`'s `"sort_key"` arm disappears.
   - `apply_create` / `apply_update_with_backend` drop the
     `apply_sort_key_hint` fallback — typed
     `position_after_block_id` becomes the only positional channel,
     and `Block.sort_key` becomes a strictly **read-only SQL
     projection** populated by the outbound projector from
     `tree.fractional_index`. No write path touches it.
   - `find_position_for_sort_key_hint` / `apply_sort_key_hint` /
     `compute_position_for_sort_key` deleted.
   - `gen_key_between` / `gen_n_keys` / `gen_key_after` from
     `holon-core/src/fractional_index.rs` either deleted entirely (if
     SqlOnly mode dies with the gate flip) or scoped to SqlOnly's
     `SqlBlockOperations`-internal positioning. `holon-markdown`'s
     bulk-seed via `gen_n_keys` (`parser.rs:488`) becomes obsolete
     because the org parser would emit `after_block_id` directly per
     the Phase 3.7 path.

5. **Same typed-event treatment for `_routing_doc_uri`** (separate
   PR, low priority). The transport pattern in this devlog (typed
   `Event` field + payload-key round-trip in `TursoEventBus`) is
   reusable. Currently OrgMode's DI graph reads
   `ROUTING_DOC_URI_KEY` as a string from `payload`; lifting it to a
   typed `Event::routing_doc_uri: Option<EntityUri>` removes the last
   underscore-prefix routing key from the producer-facing API.

6. **Chord-op direct positioning via cell registry**. Today
   `split_block` still passes `after_block_id` through the SQL → CDC
   pipeline (its chord-op create goes through `self.create(...)` →
   SQL → CDC → `apply_create`). After Stage 2-plus, `split_block`
   would call `cell_registry.create_block_with_position(parent,
   content, after_id)` directly, skipping the SQL detour for
   structural changes. The outbound projector reconciles SQL from
   Loro afterward. This collapses the create-then-position pair into
   one atomic primitive and eliminates the "block in Loro tree may
   be one CDC tick stale relative to its parent" race class.

7. **archlint rule** to forbid new `_routing_*` payload keys (or any
   underscore-prefixed param key intended as event metadata). After
   Stage 2-plus + step 5, the only legitimate underscore-prefix keys
   in params are `_expected_*` watermark guards; once cells make
   those obsolete too, the rule becomes blanket.

This devlog is the canonical entry point for picking up where Phase
3.7 left off. The next session should start by Read-ing the "Open
follow-up" + "Roadmap" sections above, deciding whether to chase the
phantom-Loro-exists root cause first or carve off Stage 2-plus items
that don't depend on the gate flip (e.g. `_routing_doc_uri` typing,
the archlint rule).
