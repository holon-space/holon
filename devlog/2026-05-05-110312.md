# #13: BulkExternalAdd / apply_mutation matview race — fix (2026-05-05)

Continues `devlog/2026-05-05-110311.md`. Same root-cause family as #8.

## TL;DR

Test reads from the `block` matview right after `wait_for_blocks_synced`
returned successfully (CDC accumulator had all expected ids). Matview's
IVM state was mid-propagation → the SELECT returned fewer rows. Switched
4 SELECTs to `block_raw` (writable base table). **Both Full and SqlOnly
PBT variants now pass cleanly (2 of 2 in 292 s).** A 5×-back-to-back
stability sweep is running; results will be appended.

## The race

`crates/holon-integration-tests/src/test_environment.rs:1689
::wait_for_blocks_synced`:

```rust
loop {
    let subset_ok = expected_ids.iter().all(|id| acc.state().contains_key(id));
    if subset_ok && length_ok { break; }
    // ... pull next CDC batch with 100 ms event timeout
}
// Final SELECT for diagnostic / return value
let sql = "SELECT id FROM block WHERE id NOT IN (SELECT block_id FROM block_tags WHERE tag = 'Page')";
```

The `acc` accumulator is fed from `setup_all_blocks_watch`'s
`query_and_watch("SELECT * FROM block", ...)` CDC stream. After the
loop's predicate passes (all expected ids present in `acc`), an
immediate SELECT against the same matview returns FEWER rows.

Failure mode in the SqlOnly run pre-fix:
```
[BulkExternalAdd] WARNING: Database has 9 blocks, expected 18 after 159ms
MISSING from SQL (9): [block:-a-jj-mm-n, block:bulk-0-3..6, block:default-main-panel, ...]
```

The CDC accumulator believed 18 ids existed; the immediate SELECT saw 9.

## Files touched

`crates/holon-integration-tests/src/test_environment.rs`:

- `wait_for_blocks_synced` final SELECT — line 1725: `FROM block` →
  `FROM block_raw` (with multiline comment explaining)
- Root-layout-children SELECT — line 1051: `FROM block` → `FROM block_raw`
- Source-block SELECT — line 1154: `FROM block` → `FROM block_raw`
- `wait_for_block` — line 1659: `FROM block` → `FROM block_raw`
- 3 doc-resolution Page-tag JOINs (lines 831, 889, 916): `FROM block b` →
  `FROM block_raw b` (page tag still joined via `block_tags`
  junction directly, which is consistent because junction writes are
  synchronous)

The CDC stream itself (`setup_all_blocks_watch`'s `SELECT * FROM block`,
line 1524) is **left as-is** — it's the matview's CDC stream that the
test depends on for change notification semantics. Switching it would
also change which events fire and could break wait predicates in subtle
ways. The fix targets the post-wait SELECT, where matview latency
matters most.

## Pattern (now in memory)

`memory/inv10d_block_matview_cdc_race.md` documents the audit rule:
**any matview read that doesn't project `tags` or `blocked_by` should
read `block_raw` directly** — bypasses the IVM consistency window.
Reverse holds: anything depending on hydrated columns must keep using
the matview. The CDC stream itself should keep using the matview when
consumers need `Updated` events for hydrated-column changes (e.g. tag
add/remove).
