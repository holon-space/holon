## Critiqued and Rewritten Plan: LEFT JOIN + Aggregation Matview Support

The original plan for supporting LEFT JOIN with aggregation in incremental matviews contained three critical falsified assumptions and several implicit invariants that would cause silent bugs or data loss on reopening.

**What happened:**

- Performed senior-dev code review of the breezy-dragon plan, grounding critique in actual codebase (`merge_operator.rs`, `aggregate_operator.rs`, `compiler.rs`)
- **Falsified Assumption 1**: Cross-side filter pushdown in `compiler.rs:2425-2442` is unsafe for LEFT JOIN — would drop null-padded rows instead of preserving them. Added Risk-1 and Phase 0 verification + test #21.
- **Falsified Assumption 2**: MatchCounter storage layout was incoherent — `WriteRow weight += delta` doesn't maintain per-key R-counts correctly when multiple L rows share a key. Redesigned to three separate stores (`L_PRESENCE`, `R_COUNT`, `R_PRESENCE`) keyed by join key.
- **Falsified Assumption 3**: `MergeOperator::next_rowid` and `seen_rows` aren't persisted across DB reopens, causing rowid collisions on session 2 — mirrors existing IVM bug in `RecursiveOperator`. Added Risk-2, Phase 8 fix, and task D-1 to verify pre-existing bug.
- Discovered `json_group_array()` over empty LEFT JOIN returns `[null]` not `[]`; added task D-2 to confirm Holon's requirements before Phase 1
- Added 5 follow-up tasks (D-1 through D-5) validating operator-id determinism, state persistence, and schema nullability
- Expanded test suite to 26 tests covering NULL-keyed rows, chained matviews, LEFT-LEFT chains, HAVING clauses

**Status:** Plan rewritten with 16 explicit hypotheses, 14 numbered risks, Phase 0 do-this-first validations, and deferred validations for transaction context (Phase 10+11) and CDC (Phase 11+12).
