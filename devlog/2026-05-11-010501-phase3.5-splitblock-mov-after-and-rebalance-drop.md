# Phase 3.5 — split_block via create + mov_after; rebalance_siblings removed

Date: 2026-05-11

Two of three follow-ups from the previous session landed. The third —
`join_block` migration — is parked on a product question about case-B
semantics (no-previous-sibling join into parent).

## Point 1 — split_block now expresses "create + mov_after" directly

`split_block` used to compute a new fractional-index value via
`gen_key_between(block.sort_key, next_sibling.sort_key)` and bake it
into the new block's create payload as the `sort_key` field. In Full
mode that hint was then sibling-scanned by `apply_sort_key_hint` and
turned into a `tree.mov_after` on the inbound CDC side — correct, but
indirect.

After this change, `split_block` adds `_routing_after_block_id = id`
to the create payload. The SQL provider strips `_routing_*` fields
before INSERT (existing convention from `_routing_doc_uri`) but
preserves them at the top level of the CDC event payload.
`apply_create` now reads it and dispatches
`LoroBackend::update_block_position(new_block, parent, Some(after_id))`
directly — a real `tree.mov_after`, no gen_key_between round trip,
no sibling scan.

The `sort_key` field is still computed via `gen_key_between` and
included in the create payload as the SqlOnly-mode value (no Loro
tree to compute the index there). It's the `ALLOW(fallback)` for the
non-CRDT path. Full mode ignores it: the outbound projector
overwrites SQL `sort_key` with Loro's auto-generated fractional index
after `tree.mov_after` lands.

### `apply_create` signature change

`apply_create(backend, data)` → `apply_create(backend, data, payload)`
so it can read the top-level routing field. The caller in
`on_inbound_event_inner` now passes `&event.payload` alongside `data`.

### Precedence in `apply_create`

1. If `_routing_after_block_id` is present →
   `update_block_position(new, parent, Some(after_id))`. Used by
   `split_block`.
2. Otherwise, if `sort_key` is present → `apply_sort_key_hint`
   (sibling-scan). Used by the org-parser seed and SQL-direct test
   writes that don't compute a predecessor.
3. Otherwise, leave the new node where `create_block` put it (end of
   parent's children, auto-indexed by Loro).

## Point 3 — rebalance_siblings deleted

The function rebalanced all siblings of a parent to evenly-spaced
fractional indices when a single key grew past
`MAX_SORT_KEY_LENGTH = 32` bytes. Its sole live caller was the retry
block in `move_to_position` after a `gen_key_between` produced a
too-long key.

Loro's internal `loro_fractional_index` keeps indices short in
practice — pathological cases would require an adversary repeatedly
inserting between two fixed bounds in the same parent, which our
edit patterns don't generate. If we hit a real ergonomic regression
we'll add targeted rebalancing back; until then, this is speculative
code maintaining a contract Loro already upholds.

Concretely:

- `BlockMaintenanceHelpers::rebalance_siblings` body deleted.
- `move_to_position`'s `if new_sort_key.len() > MAX_SORT_KEY_LENGTH`
  retry block deleted.
- `MAX_SORT_KEY_LENGTH` import dropped from `traits.rs`. Constant
  stays in `fractional_index.rs` (still referenced by that module's
  own tests).
- `gen_n_keys` import dropped from `traits.rs`. Function stays in
  `fractional_index.rs` because `holon-markdown/src/parser.rs:488`
  still uses it for bulk seed of parsed-markdown sibling order.

## Point 2 — deferred, awaiting product decision

`join_block` still uses `gen_key_between` + paired `set_field` for
re-parenting `id`'s children to the merge target. The case-B "place
children at id's old slot" semantics (when joining into parent
because there's no prev sibling) needs either:

- A `tree.mov_before` exposure on the cell registry, so we can place
  the first child before `id`'s former next sibling and chain the
  rest via `mov_after`.
- Or a simpler product choice: append children to end of parent
  instead of preserving id's slot.
- Or refuse the no-prev-sibling join entirely (Backspace at start of
  the first child becomes a no-op or an outdent).

Surfaced for user input.
