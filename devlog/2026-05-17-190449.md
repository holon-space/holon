## IVM Multiset Underflow from Btree Seek Boundary Bug

**Context**: A regression introduced by the AntijoinOperator refactor caused a panic (`json_group_array multiset went negative`) when processing dual-LEFT-JOIN materialized views. The bug manifested only under specific btree page boundary conditions and wasn't caught by existing fuzzer patterns.

**What happened**:

- Reproduced the bug using the 109-statement regression SQL file; panic occurs during synchronous CLI execution, not just async
- Traced through `WriteRow` operations and discovered `SeekOp::GE { eq_only: true }` silently returns `NotFound` when matching btree entries sit on leaf-page boundaries
- Identified the root cause: retractions became no-ops, causing `JoinOperator`'s `L_INDEX` to leak stale rows into the downstream second LEFT JOIN
- The downstream aggregate received duplicate retractions, underflowing its multiset counter
- Fixed `GetRecord` and `DeleteIndex` in `core/incremental/persistence.rs` to use `SeekOp::GE { eq_only: false }` + handle `TryAdvance` by advancing one record and verifying the cursor prefix matches
- Added regression test `test_ivm_json_group_array_multiset_negative.rs` replaying the full 109-statement Holon trace

**Challenges**:

- **Btree boundary conditions**: The bug only triggered when btree page splits positioned matching entries at boundaries, making it invisible to standard IVM tests
- **Silent failures**: `eq_only: true` mode returning `NotFound` for existing entries went undetected until tracing showed the leak in `L_INDEX`

**Decisions**:

- Mirrored the existing `read_next_join_row` pattern (handle `TryAdvance`) rather than inventing a new seek strategy
- Used the full 109-statement regression SQL as test data to ensure the exact trigger conditions are captured

**Status**: All 132 IVM sqltests and 76 IVM integration tests pass; 4 pre-existing integration test failures unrelated to this fix.
