## Trait-Driven Sort-Key Encapsulation & Inbound Gate Follow-Ups

**Context**: After landing the inbound runtime gate (item 3), a PBT test surfaced two production paths still emitting `origin=Other("sql")` for block creates. In parallel, the sort-key write path was leaking SqlOnly-ness throughout chord ops. This session unified both concerns under a `BlockOrdering` trait and prepared handoffs for remaining work.

**What happened**:

- Verified item 1b (phantom-Loro PBT mid-test variant) closed via full PBT with zero BYPASS lines; removed 5 investigation traces.
- Flipped the inbound runtime gate (item 2): `handle.disable_inbound_runtime()` now runs at startup; 4 full PBT runs green.
- Built gate integration test suite (item 3): three tests verifying gate-disabled-at-boot, Org→Apply, Ui→Drop paths; surfaced two unmigrated block-create origins.
- Item 4 phases 1–4: added `write_position` to `EntityCellRegistry` (phase 1), routed `move_to_position` through typed write (phase 2), optimized `join_block` to skip per-iteration `gen_key_between` (phase 3a), and extracted `BlockOrdering` trait to encapsulate SqlOnly leakage (phase 4). Three `gen_key_between` sites remain (definition + MemStore + SqlBlockOperations) — the minimum needed.
- Deleted legacy fallback code: `compute_sort_key_between_neighbors`, `fallback_sort_key`, and `gen_key_between` import from `holon-core`.

**Challenges**:

- **Test-surfaced origin gap**: PBT caught that `LiveDocumentManager::create` emits `origin=Other("sql")` via `execute_operation`, not the intended `EventOrigin::Org`. Gate's `drop_count` is the canary.
- **Trait-crate error alignment**: `block_ordering.rs` used `anyhow::Result`; holon-core uses `Result<T, Box<dyn Error + Send + Sync>>`. Unified on the latter.
- **SqlOnly conditionals scattered**: `move_to_position`, `split_block`, and `compute_sort_key_between_neighbors` each repeated "if Loro, use write_position; else gen_key_between." Consolidation via `BlockOrdering` impl collapsed that into two places (MemStore + SqlBlockOperations).

**Decisions**:

- **Trait-first encapsulation**: Rather than inline SQL-ness, moved it behind `BlockOrdering` impls so chord-op call sites stay generic and read-side queries can eventually hide behind `siblings_ordered`.
- **Leave read-side leakage for follow-up**: `Block::sort_key()` is still observed by Org renderer, event payloads, and SQL ORDER BY. Hiding it is valuable but orthogonal; captured as handoff (item 4 deeper half).
