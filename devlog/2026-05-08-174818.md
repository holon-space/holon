## Investigating Cursor Navigation and Split Block Bugs

The user flagged that cursor navigation and split_block don't work properly. After unblocking edit transitions via weighted generators, the PBT could finally expose these issues.

**What happened:**

- Boosted weights on `MoveCursor`, `DeleteBackward`, `SplitBlock` to fire frequently and expose staleness bugs
- Initial hypothesis: MutableText commits keystrokes synchronously to `block.content` (based on comment at `sut.rs:5991`). Tried patching `TypeChars::apply_to_ref` to `commit_active_editor_if_changed()` — PBT responded with inverse panic showing production *doesn't* sync
- Corrected understanding: `block.content` lags behind the editor's `in_memory_content` until blur or explicit chord-commit. On-screen display reflects the active editor's in-memory state only
- Fixed the display invariant at `sut.rs:5991` to compare on-screen text against `active_editor.in_memory_content` when an editor is active for that block, falling back to `block.content` when idle
- Re-ran 8 seeds: PBT now correctly surfaces **split_block staleness** — the exact bug class the user flagged

**The key insight:** The PBT wasn't lying; my assumption was wrong. By trying to bake a false sync into ref-state, I hid the real divergence. The corrected invariant lets the SUT and ref-state disagree *correctly* (in-memory vs persisted) and now exposes the actual production bug.

**Status:** Split_block and cursor-edit staleness bugs now consistently surfaced on multiple seeds. Ready to investigate root causes in split_block's apply_to_ref and cursor position tracking.
