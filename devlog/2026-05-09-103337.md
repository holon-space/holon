## Engaging Phase 2 design questions after code review

**Context:** After reviewing the Phase 2 handoff and codebase, Claude re-engaged with the core architectural tension: whether Loro should be a "leading store" for all block operations, or whether SQL owns structure and Loro owns only text content. This session evolved into a deeper thought experiment about Loro's actual roles in the system.

**What happened:**

- Confirmed the current design: `BlockContentResolver` trait (read/write for text content) is separate from `BlockOperations` (structural CRUD). This split is intentional, not accidental.
- Validated that in Full mode, Loro stays current via `on_inbound_event_inner` → `apply_fields_changed`, and that external writers (org parser, MCP) correctly route through SQL→CDC→Loro.
- Proposed unified `LiveContentStore` trait with async `read()`/`write()` methods, dropping the `bool` fallback and `OperationResult.changes` sync delta for content writes (option A: changes flow via CDC/matview, not synchronous deltas).
- Discovered the user's deeper question: What if Loro were treated like any other external datasource (Todoist, JIRA, Gmail)? This reframed the entire architecture question.

**Challenges:**

- The thought experiment exposed confusion about Loro's multiple roles: (1) CRDT text merge, (2) block tree storage, (3) sync mechanism. Testing these against other datasources revealed they're not substitutable in the same way.
- Decomposing Loro's roles more finely shows: Role A (RGA+Peritext for concurrent text edits) is unique and irreplaceable if offline+concurrent is required. Role B (LoroTree cycle-safe moves) is rarely-used but valuable in multi-user mode. Role C (persistent block structure) is mis-sourced—SQL is strictly better. Role D (sync wire format) is mostly orthogonal to storage.

**Decisions:**

- Keep `BlockContentResolver` as a separate trait scoped to text content only. The SQL-owns-structure / Loro-owns-text split reflects genuine responsibility boundaries, not leaky abstraction.
- The insight that "Loro for text merging + Turso for structure + async CDC bridge" is architecturally honest: each system does what it's good at, and the binding is explicit.
- The external-datasource thought experiment is valuable for future work (JIRA issue text edits, Gmail offline merging) but doesn't immediately change Phase 2. However, it suggests that Loro's role should be decoupled into "merge engine for any multi-peer text" vs "block tree storage," allowing either to be swapped.

**Status:** Architectural framing clarified. Ready to implement Phase 2 step 2 with unified `LiveContentStore` trait, async signatures, and no sync delta fallback. The deeper question of "should Loro be a pluggable merge engine independent of block storage?" is catalogued for Phase 3 strategic planning.
