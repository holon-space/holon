# Phase 3.3 step 2 — scaffolded; production flip held back by a Full-PBT flake from Phase 3.5/3.6

Date: 2026-05-11

## What landed (safe parts)

- **`EventOrigin` tag**: `OrgSyncController::on_file_changed` now dispatches its
  block batch via
  `execute_batch_with_origin(EntityName::new("block"), operations, EventOrigin::Org)`
  instead of plain `execute_batch` (which defaults to `Other("sql")`). The
  block-event aggregate type is unchanged; only the origin metadata
  changes. `EventOrigin::Org` already existed in `event_bus.rs:174`.
- **Inbound gate decision extracted to a pure helper.**
  `loro_sync_controller.rs::inbound_event_decision(origin, enabled) -> InboundEventDecision`
  with three variants — `EchoSuppress` (origin = `Loro`), `Apply`
  (origin = `Org`, or `enabled = true`), `Drop` (everything else when
  the gate is off). `on_inbound_event_inner` now matches on the
  decision; counter increments happen at the same call sites as before.
- **Five unit tests** in `mod inbound_gate_tests` covering every
  enum/gate combination — `Loro` always echo-suppresses, `Org` is
  whitelisted past the gate, `Other("sql")` applies pre-flip and drops
  post-flip, defensive coverage for `Ui` and `Todoist` origins.
- **Gate-flip call wired but disabled.**
  `loro_module.rs::register_services` has the `handle.disable_inbound_runtime()`
  call line staged (commented), with a `let _hold_gate_open = &handle;`
  marker so the surrounding type-shape stays stable. A long comment
  explains why it's held back (see "What's blocking the flip" below).

## What's blocking the flip

When I enabled `disable_inbound_runtime()` and ran the Full-mode PBT
(`general_e2e_pbt`, `PROPTEST_CASES=1`), the test failed with:

> `Org file block ordering wrong: Block order mismatch under parent
> 'block:ref-doc-N'`

— two blocks swapped near the top of a doc's children. I reverted the
flip and the `OrgSyncController` tag change separately and re-ran:

| Variant | OrgSyncController | Gate flip | Result |
|---------|-------------------|-----------|--------|
| (a) tagged + flipped     | `EventOrigin::Org` | enabled  | FAIL `ref-doc-0` |
| (b) tagged, no flip      | `EventOrigin::Org` | disabled | FAIL `ref-doc-3` |
| (c) untagged, no flip    | `execute_batch`    | disabled | FAIL `ref-doc-2` |
| (d) tagged, no flip (re-run for confidence) | `EventOrigin::Org` | disabled | (deferred — see next session) |

All three failures had the same shape — first 2–3 children of a doc
in unexpected order — but each on a different parent. The failure
reproduces independently of either of today's edits, which means it
predates this session.

The most recent successful Full-PBT run on this snapshot was reported
at the end of Phase 3.6 (`devlog/2026-05-11-013518…`): combined 530s.
Phase 3.6 only edited `join_block` and a test rename — nothing in the
inbound apply path. The likely culprit is Phase 3.5's
`_routing_after_block_id` / `apply_sort_key_hint` interaction in
`apply_create`, exposed by a NEW random seed today
(`PROPTEST_CASES=1` generates one random case per run on top of the
deterministic regression corpus; the corpus is unchanged in the
working copy, so the regressing case is the random one).

The SqlOnly variant of the same PBT (which bypasses Loro entirely and
exercises only the SQL projection path) passes cleanly today at 530s.
That's strong evidence the bug is in `LoroSyncController::apply_create`'s
positional handling under bulk-add, not in OrgSyncController or the
gate work.

**Flipping the gate would turn this latent flake into a hard failure
on every Full-mode run** — anywhere the bug currently produces
out-of-order Loro state, a chord-op routed through the cell registry
would land normally but the inbound mirror would drop because the
fix-up `Other("sql")` event would be denied. Holding the gate open
keeps the Full PBT in its current "intermittently green" state while
the underlying race gets root-caused separately.

## What's left (for the next session)

1. **Root-cause the Full-PBT block-ordering flake.** Most likely candidate:
   `apply_create`'s precedence between `_routing_after_block_id`
   (Phase 3.5) and `apply_sort_key_hint` when the SQL CDC batch
   arrives with all-equal `sort_key="A0"` from a freshly-parsed org
   file (BulkExternalAdd path). Hypothesis: `apply_sort_key_hint`'s
   sibling-scan finds the wrong predecessor when multiple in-flight
   blocks all share the same hint string against existing siblings
   whose Loro auto-assigned fractional indices straddle "A0".
2. **Flip the gate** (`handle.disable_inbound_runtime();` — uncomment
   in `loro_module.rs`) once the flake is fixed.
3. **Add an integration test** that exercises the production flip:
   boot a fixture with `OrgFileWatcher`, write a file mid-test,
   assert the new blocks reach Loro (proves the `Org` whitelist
   works) AND assert `inbound_runtime_drop_count == 0` for any
   chord op (proves chord ops correctly route through cells, not
   through SQL→Loro inbound).
4. **`no_inbound_loro_sync_runtime` arch-test gate**: landed in
   spirit as `inbound_gate_tests` (unit tests of the predicate).
   The integration form from item 3 will complete it.

## Why this matches the spec

The original devlog (`2026-05-10-231835-phase3-sortkey-marks-inbound-gate.md`)
called for an arch-test that boots a fixture, lets startup seeding
complete, flips the gate off, performs a chord op, and asserts
`inbound_runtime_drop_count == 0`. That test naturally lives in
holon-integration-tests because it needs the full DI graph. Step 3 in
"What's left" lands it directly; the unit tests landed in this session
cover the predicate's exhaustive enum/gate cross-product so the
integration test only has to assert one statistic.
