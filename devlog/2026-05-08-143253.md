## Fixed: Compound NULL-Check Predicates Silently Drop Second Clause in Incremental Materialized Views

A WHERE clause with compound AND of two NULL-check predicates (`IS NULL`/`IS NOT NULL`) was silently dropping the second predicate during incremental view maintenance, causing the matview to return incorrect row counts.

**What happened:**

- Reproduced the bug using variations of `WHERE a IS NOT NULL AND b IS NOT NULL` in both insert-after-matview (incremental) and from-scratch modes
- Identified the trigger: compound AND of two NULL checks, not aliases as originally suspected
- Created 4 failing tests covering the bug patterns in `ivm-null-where-filter.sqltest`
- Enhanced the differential fuzzer to generate compound NULL-check predicates, confirming it catches the bug on broken code (seed 12371730315876910877)
- Traced root cause to `predicate_needs_projection()` in `core/incremental/compiler.rs`: `IsNull` fell into the default `_ => true` arm, forcing it through the projection-rewrite path
- The projection path extracted only the LEFT side of the AND as a temp column, then `replace_complex_with_temp` rewrote both AND branches to check the same temp column—effectively `(a IS NOT NULL) AND (a IS NOT NULL)`, dropping the `b` check

**Fix applied:**

Added an explicit arm in `predicate_needs_projection()` at line 3597 marking `IsNull(Column)` as not needing projection, since `compile_filter_predicate` already handles it natively as `FilterPredicate::IsNull`/`IsNotNull`. This allows both predicates in an AND to compile independently and compose correctly in `FilterPredicate::And`.

**Verification:**

All 8 tests (4 new + 4 pre-existing recursive matview tests) pass. Enhanced fuzzer confirmed to catch the bug on broken code; other fuzzer failures observed (aggregate deduplication, numeric type ordering, overflow) are pre-existing bugs unrelated to this fix.
