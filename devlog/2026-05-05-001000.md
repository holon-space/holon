# Stale focus_roots Vec after NavigateBack — LiveData rowid-keyed delete fix

## Symptom

`crates/holon-integration-tests/tests/general_e2e_pbt.rs` (Full variant)
flaked ~1 in 15 runs at `crates/holon-integration-tests/src/pbt/sut.rs:3764`:

```
Region 'right_sidebar' focus_roots mismatch after navigation.
Focus: None
Expected IDs: []
Actual IDs: [EntityUri("block:dy-0d-i0ll5-vqrq-")]
```

`dump_nav_tables` showed the underlying `focus_roots` matview rows in SQL
were correct (only the `left_sidebar` entry remained). The SUT's
`live_focus_roots` Vec was the stale party.

## Root cause

`focus_roots` selects `(region, block_id, root_id)` — no `id` column. In
`crates/holon/src/storage/turso.rs::process_cdc_event` the `Delete` branch
falls back to the matview's internal rowid when `data.get("id")` is None:

```rust
let entity_id = data.get("id")
    .and_then(|v| match v { Value::String(s) => Some(s.clone()), _ => None })
    .unwrap_or_else(|| change.id.to_string());  // ← rowid string
```

Meanwhile `LiveData::apply_changes` did:

```rust
Change::Deleted { id, .. } => { lock.remove(&id); }
```

— but `live_focus_roots` keys items by `id_fn`-derived
`format!("{region}\u{1F}{root_id}")`. Rowid never matches the composite
key, so the delete silently missed. `live_block_tags` had the same shape.

It flaked instead of always failing because the same-key Delete+Insert
pair from a typical NavigateFocus/NavigateBack-with-prev-entry coalesces
to `Updated` (uses the correct id_fn key in `apply_changes`).
NavigateBack-to-NULL produces only a Delete with no replacement insert —
that's the unmasked path.

## Reproducer

`crates/holon/src/sync/live_data.rs::tests::test_apply_delete_composite_key_via_rowid`
constructs a LiveData with composite-key id_fn, applies a Created event
carrying `_rowid: "42"`, then a `Change::Deleted { id: "42" }`. Failed
pre-fix (`left: 1, right: 0`), passes post-fix.

## Fix

Two files.

### `crates/holon/src/sync/live_data.rs`

Added `rowid_to_key: Mutex<HashMap<String, String>>`.

- `Created`/`Updated`: extract `_rowid` from `data` (already injected by
  `process_cdc_event`), insert `rowid → user_key`.
- `Deleted`: try direct `lock.remove(&id)` first. If it succeeds, reap
  any stale rowid entries pointing at the same user key. If it misses,
  look up `rowid_map.remove(&id)` for the user key, then remove that.
- Initial rows: extract `_rowid` if present, populate the map.

### `crates/holon/src/sync/matview_manager.rs::query_view`

```rust
let select_sql = format!("SELECT *, rowid AS _rowid FROM {}", view_name);
```

Aligns initial-row shape with the CDC-event shape (which already
includes `_rowid`), so the very first event for an initial row can be a
Delete and still find its target.

## Verification

- 5/5 `live_data` unit tests green, including the new one.
- PBT 30-run loop: **30/30 PASS, 0 FAIL** (`/tmp/pbt_repro2.log`).
  Pre-fix repro had 1 FAIL in 4 runs with the right `focus_roots
  mismatch after navigation` signature.

## Out of scope (verified untouched)

- `EventBus` subscribe-with-replay (separate, already landed).
- CDC routing, `Consumer::parse`, `subscribe()` wiring.
- The previous `wait_for_live_data_mirrors` watermark drain — already
  worked correctly; the bug was downstream of it (delete event applied
  but a no-op).
