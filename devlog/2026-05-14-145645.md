## Deterministic focus deadlock in GPUI PBT post-SplitBlock; bounds instrumentation reveals structural bug

The sort_key fix from the previous session unmasked three pre-existing non-deterministic failures in the GPUI property-based test. With seed=42, the same code produces different failures across runs due to tokio scheduling variance. This session targeted the highest-priority failures: NavigateFocus click misses and post-SplitBlock focus stalls.

**What happened**

- Added missing `wait_for_entity_bounds` call in `NavigateFocus` apply before `click_entity` — failure A (sut.rs:800) now deterministic
- Instrumented `wait_for_entity_bounds` to dump `BoundsRegistry::all()` on 5s timeout; revealed that target blocks are completely absent from the registry, not under alternate element ids
- Updated SplitBlock ref model to track `focused_block` on the newly-created block (split_block.rs); added best-effort focus-await in `apply_split_block`
- Added polling to `inv-focus-matches-ref` invariant assertion so transient focus races don't immediately panic
- **Discovered root cause of failure C**: chicken-and-egg deadlock in production render pipeline — `EditorView` only renders when `focused_block` already points at the block, but `focused_block` only updates via `EditorView::InputEvent::Focus`. After `split_block` writes `editor_cursor`, no subscriber listens, so new block stays as `rendered_text` and never grabs focus
- **Landed production fix** in `frontends/gpui/src/lib.rs`: top-level `watch_editor_cursor` reactor that calls `services.set_focus()` directly, breaking the cycle and allowing new blocks to mount their `EditorView` on the next render tick

**Challenges**

- Bounds timeout diagnostics were misleading — blocks logged as "wait_for_entity_bounds" failures were genuinely absent from BoundsRegistry, not just under different element id conventions. Required adding explicit registry dump on timeout to surface this.
- Focus synchronization race required distinguishing between "click landed but focus hasn't propagated yet" (transient, retry-able) vs "focus fundamentally stuck" (structural). Soft polling in invariant assertions lets transient races resolve naturally.

**Status**

5 consecutive seed=42 runs now clear the post-SplitBlock focus deadlock. Remaining failures are 4 distinct pre-existing failure classes (bounds-timeout on split-target block, wrong-element click, display-text mismatch, org-roundtrip invariant). Run 5 progressed to step 7 before hitting an unrelated invariant.
