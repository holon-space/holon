## Diagnosing a `json_group_array` IVM Multiset Invariant Violation

A holon session was panicking with "multiset went negative for col 19" in Turso's `json_group_array` aggregator during matview updates to the `block` table.

**What happened:**

- Identified the root cause: an `UPDATE block_requires SET required_id = 'block:' || required_id` migration query (not in source control) was triggering a delta-consolidation invariant violation in the recently-landed `json_group_array` IVM implementation (commit `0fef90b39`, 3 days old)
- The `block` matview joins `block_raw LEFT OUTER JOIN block_requires`, then aggregates `json_group_array(br.required_id)` grouped by all base columns; the UPDATE on a junction table caused the IVM to retract values more times than they were inserted
- Verified the session is unrecoverable — after the first panic, subsequent matview queries fail at `aggregate_operator.rs:2192` with "Reached invalid state"
- Wrote comprehensive `turso-sql-replay` skill documentation (`SKILL.md`) explaining the extract/replay/minimize/assert workflow for capturing IVM bugs
- Attempted to reproduce with four progressively-richer hand-built repros (varying tag/require fold cardinalities, chained matviews, bulk UPDATEs); all ran cleanly
- Discovered the actual `/tmp/holon.log` was captured without `HOLON_TRACE_SQL=1`, so SQL statements are truncated to 120 chars — the extracted trace has malformed DDL and an incomplete UPDATE WHERE clause, making offline replay impossible

**Challenges:**

- Truncated SQL logging prevented extraction of a true reproducer from the live log; the trace captured only the first 120 chars of each statement, losing critical schema and predicate details
- Hand-built repros couldn't trigger the panic despite mirroring the data shapes; the bug likely depends on the full matview fanout tree (`focus_roots`, `block_requirement_edges`, user-watch matviews) or persistent on-disk DBSP state

**Decisions:**

- Prioritized concrete next steps over endless local repro attempts: the real fix requires a full-SQL trace captured with `HOLON_TRACE_SQL=1`
- Documented the turso-sql-replay workflow so the next iteration can auto-detect the panic pattern and minimize to a 10-line reproducible case

**Status:** Holon session needs restart; the underlying IVM `json_group_array` bug in Turso requires a properly-captured full SQL trace. Instructions provided for capturing one and filing upstream.
