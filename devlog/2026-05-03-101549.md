## PBT Test Performance: Fixing Timeout Cascades in `prime_seed_count`

**Context:** Integration tests regressed from ~70s to ~600s. Chrome-trace profiling showed `StartApp` consuming 79% of runtime, with 167s of unexplained idle gaps between test cases.

**What happened:**

- Reduced `prime_seed_count` timeout from 10s to 2s → saved 67s (19% improvement)
- Instrumented timeout logic with `eprintln!` to diagnose why it always fired
- Found root cause: **reference-state document IDs** (`block:ref-doc-N`) never appear in production state (which uses UUIDs); `doc_uri_map` unpopulated at prime time
- Applied fix: added `!b.is_page()` filter to `expected_block_ids()` (sut.rs:5414), mirroring existing filter in `expected_content_block_count`
- Re-ran full suite with filter in place → **252s total (−106s, 30% off original)**

**Challenges:**

- Debugger timeout: 255 MB test binary doesn't load symbols within 7s LLDB init hard limit → fell back to `eprintln!` instrumentation
- False metric: `expected` vs `acc` counts always matched; the timeout was purely ID-name mismatch (ref names vs UUIDs), not state divergence

**Decisions:**

- Kept 2s timeout on `prime_seed_count` despite now exiting early on success; conservative choice prevents regress if predicate ever becomes flaky
- Did not apply same fix to `BulkExternalAdd`/`await_block_count_or_panic` — their per-call cost (3–8s) was already well below 10s timeout, so page-block mismatch wasn't blocking them

**Status:** Test suite reduced to ~252s (from 600s baseline). Remaining 100s+ of idle gaps likely from per-case `tokio::runtime` teardown; next step is runtime reuse across test cases.
