### 1. Make the arch-validate drift gate actually run: wire it to CI, fix the currently-red baseline

**Doc:** docs/Architecture.md — Crate Responsibilities | **Kind:** design-flaw | **Severity:** critical | **Verified:** yes

**Context.** docs/Architecture.md:104-106 calls CrateMap.md "the authoritative, machine-checked inventory" and :114-115 claims "`just arch-validate` fails CI if the crate/frontend structure drifts from the committed baseline." Both halves of the guarantee are false today. (1) No automation runs the gate: .github/workflows/ci.yml has no archidoc/arch-validate step anywhere — its only test step (ci.yml:102) is `cargo test --workspace`, whose architecture test (crates/holon-architecture-tests/tests/architecture_rules.rs:33) shells out to archlint only. The `arch-validate` recipe exists solely in justfile:59-62 as a manual command. (2) The inventory has drifted: crates/holon-loro, crates/holon-petri, and crates/holon-profiles have zero `@c4` annotations in src/, and appear neither in docs/Architecture/baseline/crates/architecture.json nor in docs/Architecture/CrateMap.md. IMPORTANT correction to the review's mechanism claim: the tooling does NOT silently omit unannotated crates. I ran the real gate (`archidoc ir compile crates` then `ir validate --strict` against the committed baseline): it exits 1 with three `[WARN] UNDOCUMENTED — holon-loro / holon-petri / holon-profiles — annotated directory exists in actual but not in design`. So `just arch-validate` is RED right now — the guarantee failed not because the tool is blind but because nothing ever executes it, which is exactly the priority-4 "silently degrades to look fine" mode the project's error-handling philosophy forbids. Same state verified on mainline (/Users/martin/Workspaces/pkm/holon), so this is not worktree staleness. Note: part of the remediation touches crates/holon-loro/src/lib.rs (doc-comment-only @c4 block) — holon-loro is owned by the active PBT-composition/sharing tracks, so that one-file annotation should be coordinated (DESIGN-note flag: owned by active track for that file only; the CI wiring and doc edits are unowned).

**Options.**

**A. Wire the real gate into CI (make the doc claim true verbatim)**
- *Sketch:* Step 1 (unblocks everything): add @c4 blocks to holon-loro/holon-petri/holon-profiles src/lib.rs, run `just arch-baseline && just arch-docs`, commit baseline + CrateMap.md + diagrams — this turns the currently-red gate green. Step 2: add a CI job to .github/workflows/ci.yml: install a pinned archidoc (`cargo install archidoc --locked --version X` with ~/.cargo caching, or a prebuilt binary artifact), then run `just arch-validate` and `just arch-check-deps`. The justfile recipes already use --strict, which is what promotes UNDOCUMENTED warnings to exit 1 — the completeness check the review asked for already exists.
- *Pros:* Enforces the full contract, not just completeness: catches new unannotated crates (UNDOCUMENTED), removed crates (UNIMPLEMENTED), attribute/level drift (DIVERGED), and dep-arrow drift via arch-check-deps. Zero new code — the gate demonstrably works (exits 1 today). Doc needs no edits; the claim becomes true as written.
- *Cons:* CI grows an external binary dependency: archidoc version must be pinned and can skew against contributors' local installs (a newer local archidoc regenerating baseline could churn the JSON). cargo install adds CI minutes on cache miss. The gate still doesn't run on plain local `cargo test` — contributors only hit it in CI or via just.

**B. Fold a completeness gate into `cargo test --workspace` (no external binary)**
- *Sketch:* New test in holon-architecture-tests (sibling of architecture_rules.rs): using cargo_metadata + serde_json, assert (1) every workspace member under crates/ and frontends/ has an `@c4` block in src/lib.rs, and (2) every member's name appears as a node in docs/Architecture/baseline/crates/architecture.json (resp. frontends). Fail with the crate name and the two commands to fix (`just arch-baseline && just arch-docs`). Reword docs/Architecture.md:114-115 to: completeness is CI-gated via cargo test; structural/attribute drift is checked by `just arch-validate` (manual, pre-commit for structural changes).
- *Pros:* Runs everywhere CI already runs (ci.yml:102) AND on every contributor's plain `cargo test` — tighter loop than a CI-only job. No binary provisioning, no version-skew surface. Targets the exact failure class that actually occurred (crate added, never annotated, invisible in the map).
- *Cons:* Duplicates a slice of archidoc's validate logic — two definitions of 'validated' to keep aligned. Does not catch DIVERGED attribute drift, relevel changes, or dep-arrow drift; those deep checks remain manual, so the doc must be edited to narrow its claim honestly.

**C. Doc-only honesty fix: delete the guarantee, keep the gate manual**
- *Sketch:* Rewrite docs/Architecture.md:104-117: drop 'machine-checked' and 'fails CI'; state that CrateMap.md is generated from @c4 annotations and that `just arch-validate` is a manual pre-commit check to run after structural changes. Still annotate the three crates and regenerate baseline + CrateMap so the inventory stops lying by omission.
- *Pros:* Smallest change; immediately truthful; no CI or test-infra work; no external-tool pinning.
- *Cons:* Abandons drift protection entirely — and the evidence says manual discipline already failed (three crates rotted out of the map, and the red gate went unnoticed because nobody runs it). Readers of an 'authoritative inventory' that silently omits crates are worse off than with no inventory; this is the degraded mode the repo's own priority order ranks last.

**Recommendation.** Option A, with Option B's lib.rs-annotation assertion as an optional cheap add-on later. The gate is proven working — I ran it and it exits 1 flagging exactly the three drifted crates — so the entire fix is provisioning: annotate three crates, regenerate baseline/CrateMap, add one pinned-binary CI job. That preserves the full validation contract (completeness + DIVERGED + dep arrows) instead of reimplementing a weaker completeness-only shadow of it in Rust, and it keeps ONE source of truth for what 'validated' means (archidoc), consistent with parse-don't-validate/one-authority instincts. Choose B only if adding a pinned external binary to CI is unacceptable. Effort: S for the annotate+regenerate step (three doc-comment blocks + `just arch-baseline && just arch-docs`; note the holon-loro lib.rs touch sits in territory owned by the active PBT/sharing worktrees — coordinate or land as a trivial doc-only commit), M overall including CI wiring with version pinning and cache. Interim (if CI wiring waits): at minimum land the annotation+regen commit so `just arch-validate` goes green and the published map stops omitting three crates, and soften the ci claim per Option C until the job lands — a red gate nobody runs plus a doc promising CI enforcement is the worst available state.

### 3. Invariant 9 (tombstone GC) — decide between permanent-but-compact tombstones and a replica registry, or disclose it as undesigned

**Doc:** docs/Architecture/Model.md — Invariants — invariant 9 (tombstones outlive every base) | **Kind:** missing-decision | **Severity:** major | **Verified:** yes

**Context.** docs/Architecture/Model.md:82-84 states invariant 9: "a tombstone may not be GC'd until every registered replica's base has advanced past it." Verified 2026-07-04 that every load-bearing noun in that sentence is unimplemented: (1) "registered replica" — the only grep hit for replica registration in the entire repo is the doc line itself (Model.md:83); no registry type, no persistence, no enrollment path. (2) "tombstone" — holon-api/src/repository.rs:195-196 documents `delete_block` as "Delete a block (tombstone)", but no `deleted_at` column exists in any .rs file (docs/Architecture/Sync.md:134,374 describe one — that doc is stale on this point); SQL-side deletes are hard `DELETE FROM` (e.g. crates/holon/src/core/sql_operation_provider.rs:776-784). The actual resurrection defense is per-replica base snapshots (crates/holon-filesystem/src/sync_base_store.rs — `BaseStore`/`BaseKey{peer,file}`, lines 42-63, 91-99) plus, in Full mode, Loro's internal op history. (3) "base has advanced past it" — bases are block-snapshot maps (`HashMap<String, SnapshotBlock>`), not frontiers/watermarks, so "advanced past a tombstone" has no defined comparison; only the Loro-backed base is a frontier (Replication.md:166). (4) "GC" — none exists, so the invariant is today vacuously true via unbounded retention, a choice the doc never discloses. Meanwhile the hazard is already live in one place: the Loro document store writes shallow snapshots (crates/holon-loro/src/loro_document_store.rs:172, loro_document.rs:154), i.e. history IS trimmed, and crates/holon-loro/src/iroh_sync_adapter.rs:55-79 handles "peer below shallow base" with a full-snapshot fallback — exactly the stale-replica-meets-GC'd-history collision invariant 9 is about. The doc also dodges the hard question: org dirs are replicas that can legitimately be parked offline for a year, so any liveness-keyed GC must choose between blocking forever and resurrection risk. OWNERSHIP FLAG: the Loro-history/shallow-snapshot half of this is owned by the active Loro+Iroh sharing track — for that surface this is a DESIGN note only; the Model.md invariant wording and the SqlOnly/org side are unowned and actionable now.

**Options.**

**A. Downgrade to a disclosed open question (doc-only)**
- *Sketch:* Rewrite Model.md item 9 as a future-GC precondition, not a settled mechanism: 'No deletion GC exists; deletion knowledge lives in per-replica bases (SyncBaseStore) and Loro op history, both retained unboundedly. Any future GC must not collect deletion knowledge still needed by a replica that could reintroduce the block — this requires a replica registry and a stale-replica eviction policy, both OPEN.' Fix the stale Sync.md deleted_at rows (134, 374) to match the hard-delete reality, and cross-link iroh_sync_adapter.rs:55-79 as the one live GC surface (owned by the sharing track).
- *Pros:* Honest immediately; zero code risk; removes the fake-settled reading a future agent would build on (the strongest-signal-is-artifacts principle); does not preempt the sharing track's shallow-snapshot design.
- *Cons:* Leaves unbounded growth undecided; the invariant stops being an invariant (nothing checkable); the question resurfaces the moment shared-doc history trimming or a vault-compaction feature lands.

**B. Registry-free permanence: tombstones are never collected, only compacted**
- *Sketch:* Decide that deletion knowledge is permanent and bound its COST instead of its lifetime. SqlOnly/org side: introduce a minimal durable deleted-ids ledger (id + deletion stamp only — no content, no edges; roughly the deleted_at row Sync.md already imagines, but as an append-only ledger a hard-deleting sink can consult), so a stale org dir re-appearing after a year diffs against it and its blocks stay dead. Loro side (DESIGN note for the sharing track): constrain shallow_snapshot to frontiers that dominate every outstanding registered base, OR carry the deleted-ids ledger alongside the shallow doc so the iroh_sync_adapter.rs:76 snapshot-fallback cannot resurrect. Rewrite invariant 9 to codify permanence: 'deletion knowledge is never discarded; GC means compaction to the ledger, never removal.'
- *Pros:* No replica registry, no liveness protocol, no eviction policy — the whole undesigned surface disappears; consistent with local-first reality (parked-for-a-year replicas are legal, not a fault); resurrection impossible by construction; ledger rows are tiny so 'unbounded' is ~bytes/deletion.
- *Cons:* Truly unbounded id-ledger (fine for a PKM, wrong if block churn is machine-generated at scale); the Loro-side constraint needs sharing-track buy-in; a new durable artifact must be wired into wipe-and-reseed (DurableReplicaState::durable_paths) and the keystone PBT.

**C. Real replica registry + watermark GC with manual, fail-loud eviction**
- *Sketch:* Implement the invariant as written. Registry: persist replica enrollment keyed by the existing BaseKey{peer,file} (sync_base_store.rs:42) in a sidecar next to the base sidecar (BASE_SIDECAR_FILENAME pattern). Stamp every deletion with a monotonic per-consolidator deletion epoch; each replica's base records the highest epoch it has synced past (this fixes the snapshot-vs-frontier type gap — bases gain a watermark field). GC threshold = min(watermark) over registered replicas. A parked replica blocks GC indefinitely and the UI discloses it ('GC blocked by replica X, last seen <date>'); unblocking is an explicit user command `evict replica X`, after which X's reappearance is refused with a banner (ForeignIdCollision pattern, share_projection fix precedent).
- *Pros:* Delivers actual bounded storage for active meshes; the fail-loud manual eviction respects the error-handling priority order (visible degraded mode, never silent); watermark epochs also give the sharing track a principled 'safe shallow-snapshot frontier'.
- *Cons:* Largest surface: new persistent registry + epoch stamping in both consolidators + base schema change + eviction UX + PBT coverage (a new composed transition class for replica lifecycle); solves a pressure that does not exist yet — no user-visible growth problem today; registry itself becomes replicated state with its own convergence questions.

**D. Lease/TTL auto-eviction (Cassandra gc_grace_seconds model)**
- *Sketch:* As C, but a replica silent for N days is auto-evicted and GC proceeds; a returning evicted replica's diff may resurrect deleted blocks, mitigated by refusing ingest of any id present in a retained short-horizon deleted-ids buffer.
- *Pros:* Bounded growth with zero user intervention; the standard industry answer; simplest mental model for a hosted/multi-device future.
- *Cons:* Auto-eviction of a parked vault dir is exactly priority-4 'silently degrades to look fine' unless the resurrection-refusal buffer is itself permanent — at which point this collapses into option B plus extra machinery; N is an unprincipled constant in a local-first system where a year-parked replica is normal.

**Recommendation.** Do A now (effort S — doc-only, safe against all active worktrees) and pre-commit the direction to B (effort M when built). Rationale: in Holon's local-first model a replica parked for a year is legitimate, so any liveness-keyed GC (C, D) either blocks forever or trades in silent resurrection risk — C's cost buys nothing until a real growth problem exists, and D collapses into B once you make its resurrection-refusal buffer permanent. B is the only option that dissolves the undesigned registry/eviction surface instead of designing it, and its per-deletion cost (an id + stamp) is negligible at PKM scale. Concretely: rewrite Model.md invariant 9 per option A but state B as the chosen end-state ("deletion knowledge is permanent; GC = compaction to a deleted-ids ledger"), fix the stale deleted_at rows in Sync.md:134/374, and hand the Loro shallow-snapshot constraint (dominate-all-bases frontier OR ledger-alongside) to the Loro+Iroh sharing track as a design requirement — that track's iroh_sync_adapter.rs:76 snapshot-fallback is where invariant 9 can actually be violated today. When B is built, wire the ledger into DurableReplicaState::durable_paths and add a keystone-PBT resurrection guard (delete → stale-replica re-sync → block stays dead) per the ONE-PBT north star.

### 4. Scope Model.md's supremacy clause to intent; stop letting it cover status claims

The flaw: Model.md is not a pure-intent page — it embeds volatile status claims that the clause was never meant to cover: "HOLON_CRDT_ENABLED switch currently flips several axes" (Model.md:34), "holon-markdown exists but is unwired — no crate depends on it" (Model.md:40), "Today that migration is unbuilt (spec 0008 Phase 4.1) ... HOLON_CONSOLIDATOR_MIGRATE=1 is an INTERIM wipe-and-reseed" (Model.md:92-99), and invariant 12's backing-type inventory "LwwTextCellBacking/LwwScalarBacking<T> ... via BlockCellRegistry::sql_only_wired ... pending Cells plan Phase 2.3" (Model.md:106-114). CAVEAT on the finding's evidence: the two concrete drift instances it cites are RECONCILED today — inv 12 now matches both Storage.md's backing table (Storage.md:88-94) and code (crates/holon-core/src/cell.rs:250,301; crates/holon/src/sync/event_infra_module.rs:151), and inv 10's disclosure matches crates/holon-app/src/consolidator_epoch.rs:16 and the guard tests (crates/holon-integration-tests/src/test_environment.rs:552). **Options.**

**A. Scope the precedence clause to intent (typed precedence)**
- *Sketch:* Rewrite Model.md:7-8 to a two-tier rule: 'On INTENT (layer rules, invariants as norms, the mode-axis grid), this page wins and a disagreeing detail doc is presumed stale. Optionally tag inline status claims with a visible marker, e.g. '[status 2026-07]', so readers can classify a sentence at a glance.
- *Pros:* Smallest diff (one paragraph + a few markers); immediately corrects the trust direction for agents; preserves inv 10's safety-critical wipe-and-reseed disclosure at the point of first reading, which matters for fail-loud (an agent about to flip HOLON_CRDT_ENABLED should hit that warning in the first doc it loads).
- *Cons:* Status claims still rot in place — the clause stops mis-directing trust but doesn't stop drift; readers must self-classify each sentence as intent vs status; markers add visual noise to the 'one page' mental model.

**B. Purge status from Model.md; make the clause true by construction**
- *Sketch:* Move every volatile claim out: Model.md:40's holon-markdown wiring note → CrateMap.md; Model.md:92-99's migration status → the spec 0008 doc / Replication.md, leaving inv 10 as the pure norm ('handover is an epoch; toggling without base re-seed produces phantom diffs') plus one line 'current migration status: see X'; inv 12's type inventory → already lives in Storage §Cells (Storage.md:88-94), so Model.md keeps only the norm ('every field write resolves a cell backing; disclosed exceptions: tree-position, derived/control fields') with the existing pointer. The supremacy clause then needs no qualification.
- *Pros:* Model.md becomes durable — the clause is sound as written, no reader classification needed; eliminates the drift-regeneration mechanism rather than annotating it; Storage §Cells already demonstrated the pattern works (per-backing status table there matched code through two reconciliations).
