## What landed

`crates/holon-integration-tests/src/test_environment.rs::wait_for_org_files_stable`
now performs a watermark-based gate at the start:

```rust
if let Some(bus) = self.event_bus.as_ref() {
    use holon::sync::event_bus::{Consumer, EventBus};
    let snapshot_global = bus.watermark().await.unwrap_or(0);
    if snapshot_global > 0 {
        let watermark_deadline = start + timeout;
        let mut last_pos: i64 = -1;
        while tokio::time::Instant::now() < watermark_deadline.into() {
            let pos = bus.consumer_position(Consumer::ORG).await.unwrap_or(0);
            if pos >= snapshot_global {
                break;
            }
            // ...
            tokio::time::sleep(std::time::Duration::from_millis(2)).await;
        }
        // ... timeout warning if not caught up
    }
}
// fall through to existing OrgSyncIdleSignal + mtime-stable
```

Three layers of gating now:
1. **NEW:** WatermarkState — wait for org consumer to catch up to all
   events emitted before the wait
2. OrgSyncIdleSignal — wait for the controller's loop to be idle for
   `stability_ms` (caller-supplied, default 25ms)
3. mtime-stable — short final check that file mtimes have settled

## What's still racing

After the org consumer marks an event processed, there's another
window before the file is actually flushed to disk. The consumer's
"mark_processed" call (`event_bus.mark_processed_batch(&ids,
Consumer::ORG)` at `crates/holon-orgmode/src/di.rs:1084`) is on the
`mark_flush_tick` branch — bumping the consumer position is decoupled
from the file write itself.

Looking at the controller loop more carefully:
- `event_rx` arm processes the event AND calls `controller.on_block_changed`
  (which writes the file)
- THEN `mark_progress()` fires (idle signal)
- THEN — separately, on a flush tick — `mark_processed_batch` is
  called (consumer watermark advances)

So the order is: file write → idle signal → consumer watermark. The
idle signal is the more accurate gate for "file is on disk", BUT the
idle signal can transiently flicker if the loop hits the
`mark_flush_tick` branch between events.

Two hypotheses:
- **A**: file write completes but ORG renderer for that file is async
  / batched separately from the event processing
- **B**: there's a separate code path firing org renders that doesn't
  bump the watermark or the idle signal

Either way, the org file's contents diverging while watermark is
caught up means the contract "org consumer marked event N processed"
≠ "org file reflects all events ≤ N". The watermark is the right
direction but not sufficient.
