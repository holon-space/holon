# Phase 3.4 follow-up — drop legacy sort_key fallback; refactor move_block chord op

Date: 2026-05-11

## What landed

Two follow-ups from `2026-05-11-000712-phase3.4-sortkey-via-loro-internal-index.md`:

1. **Dropped the legacy shadow meta key entirely** — including the read
   fallback in `read_block_from_tree`, the `update_block_sort_key` API
   on `LoroBackend`, and all three inbound `apply_*` callers in
   `loro_sync_controller.rs`. There are no un-migrated docs in the
   fleet, so the fallback was dead weight.
2. **Inbound paths route through `apply_sort_key_hint`** — a new
   `LoroBackend` async method that takes a fractional-index hint
   string, scans siblings to find the right predecessor, and
   dispatches `update_block_position` (which calls `tree.mov_after`).
   The sibling-scan logic is shared with `BlockCellRegistry` via a
   `pub(crate)` free function `find_position_for_sort_key_hint`.
3. **`move_block` chord op refactored to use a `move_to_position`
   helper** on the `BlockOperations` trait. The helper internally pairs
   `set_field("parent_id", …)` with `set_field("sort_key", …)` — same
   wire behaviour, but the (compute neighbors → gen_key_between →
   rebalance retry → paired writes) sequence lives in one place
   instead of being inlined and duplicated. `compute_sort_key_between_neighbors`
   is the inner helper that runs the neighbor query + `gen_key_between`
   call (now shared between the first attempt and the post-rebalance
   retry).

## Why correctness holds

`Block.sort_key` now sources from `tree.fractional_index(node)`
exclusively. The inbound `apply_*` paths receive a hint string from
the SQL CDC payload, but at the point they fire (org-parser seed,
SQL-direct test writes), the hint was originally produced by chord
ops via `gen_key_between` against `Block.sort_key` values — which
themselves came from `tree.fractional_index`. So the hint sits in a
real gap between siblings' fractional indices; `apply_sort_key_hint`'s
sibling scan finds the right predecessor every time.

For freshly-created blocks during initial seed, Loro auto-assigns
fractional indices in creation order (the org parser walks the file
top-to-bottom). Read-back yields ascending indices, matching the
source-file order. SQL projection reflects that.

`move_block` chord op behaviour is unchanged from the call-site
perspective: same args, same return type, same inverse. Internally,
the duplicated rebalance-retry block disappears; the only logic that
runs twice is now `gen_key_between` (cheap, called inside the helper).

## Files touched

- `crates/holon/src/api/loro_backend.rs`:
  - Removed `.or_else(|| meta.get_typed("sort_key", …))` legacy
    fallback from `read_block_from_tree`. Reads `tree.fractional_index`
    only.
  - Added `find_position_for_sort_key_hint` (`pub(crate)` free
    function) — sibling-scan helper.
  - Added `LoroBackend::apply_sort_key_hint(target_id, hint)` — async
    wrapper that takes the read lock, runs the helper, dispatches
    `update_block_position`.
  - **Deleted** `LoroBackend::update_block_sort_key` (was
    `#[deprecated]` in the previous commit).
  - Renamed the regression test `sort_key_round_trips_through_loro_meta`
    → `sort_key_reflects_tree_fractional_index`; added
    `apply_sort_key_hint_repositions` exercising the inbound entry
    point against a three-sibling fixture.
- `crates/holon/src/sync/block_cell_registry.rs`:
  - `compute_position_for_sort_key` shrunk to a 1-line shim over
    `find_position_for_sort_key_hint`.
- `crates/holon/src/sync/loro_sync_controller.rs`:
  - `apply_fields_changed`'s `"sort_key"` branch:
    `update_block_sort_key` → `apply_sort_key_hint`.
  - `apply_create` and `apply_update_with_backend`'s `sort_key`
    branches: same swap.
- `crates/holon-core/src/traits.rs`:
  - Added `BlockOperations::move_to_position(id, parent, after)` +
    `compute_sort_key_between_neighbors` helpers.
  - `move_block` refactored to call `move_to_position`; the inline
    neighbor query / gen_key_between / rebalance-retry block dropped
    in favour of the helper. Depth update + descendant recursion
    stays where it was.

## What was NOT migrated (yet)

- `join_block` (both parent-path and prev-sibling-path child re-parent
  loops) still uses inline `gen_key_between` + paired `set_field`. The
  loop accumulates `last_sort_key` across iterations and ends with
  `next_sibling_sort_key` as the upper bound. `move_to_position`
  doesn't yet support a "between A and B" anchor — only "after A". A
  later migration could extend the helper or replace the loops with
  per-child `move_to_position(after = previous_child_id)` calls if we
  can prove the semantics match.
- `split_block` writes the new block's `sort_key` as part of its
  create payload (not via `set_field`). That's a create-time
  positional intent, handled by the create path. Not affected by the
  helper.
- `rebalance_siblings` iterates children and calls
  `set_field("sort_key", …)` directly. Each call is intercepted by
  the cell registry and turned into a tree position update. No
  refactor needed; the loop is already concise.

## Open follow-ups

- Migrate `join_block` to call `move_to_position` once we have an
  ergonomic helper that takes both anchors (or once we can prove the
  iterative "after = previous child" form matches the existing
  "between None and fixed-upper-bound" semantics).
- Drop `holon-core/src/fractional_index.rs` once chord ops carry
  positioned-move intent at the call site (so `gen_key_between` no
  longer needs to be available to the trait). That requires a typed
  positioned-move method on the cell registry that takes
  `after_block_id` directly, plus an EntityCellRegistry-style trait
  exposing it.
- Phase 3.3 step 2 (production flip of the inbound runtime gate) is
  still pending; once it lands, `apply_sort_key_hint` becomes a
  startup-only entry point and the inbound CDC handling can shrink
  further.
