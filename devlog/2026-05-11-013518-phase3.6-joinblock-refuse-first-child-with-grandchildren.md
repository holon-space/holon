# Phase 3.6 — join_block refuses the no-prev-sibling case when id has children

Date: 2026-05-11

User check against LogSeq confirmed option (c): a first-child block
with its own children **cannot** be joined into its parent. We mirror
that.

## What changed

`BlockOperations::join_block` now exits early (no-op, no changes) when:

- The block being joined has no previous sibling (`into_parent` path), AND
- The block itself has children (`!block_children.is_empty()`).

Backspace at the start of the first child of `P` is a no-op when that
first child has its own subtree. The simpler cases stay supported:

- **Case A** — `id` has a prev sibling: merge into prev, re-parent any
  children of `id` to the end of prev's existing children, delete `id`.
- **Case B (without children)** — `id` is first child and has no
  children: append `id`'s content to parent, delete `id`. Nothing to
  re-parent.

The entire `into_parent && !block_children.is_empty()` branch (with
its `gen_key_between` slot-preservation logic) is gone.

## Case-A child reparent: kept local-variable sort_key tracking

I initially tried migrating the case-A re-parent loop to use
`self.move_to_position(child, target, last_anchor)` per child. PBT
caught a regression in Full mode: positions of two siblings in a doc
ended up swapped.

Root cause: `move_to_position` calls
`compute_sort_key_between_neighbors` which queries
`get_by_id(after_id).sort_key` and `get_next_sibling(after_id)`. In
Loro-enabled mode, per-keystroke writes commit to Loro synchronously
but the SQL projection lands **asynchronously** through the outbound
projector. So between iterations of the reparent loop, child[i-1]'s
SQL row could still hold its pre-move sort_key. The freshly-queried
"prev sort_key" lay outside the intended gap; `gen_key_between(stale,
None)` produced a value that no longer ordered correctly with the
others.

The pre-3.5 loop tracked `last_sort_key` in a local variable across
iterations — the new value, never re-queried. I restored that pattern.
The loop's body is still a paired `set_field("parent_id") +
set_field("sort_key")`, but the second call uses the locally-tracked
value, dodging the SQL-projection race entirely.

PBT runs GREEN with this restoration (`general_e2e_pbt_sql_only` +
`general_e2e_pbt` Full, PROPTEST_CASES=1, combined 530s).

This race is a general property of the cell-routed Loro mode, not
specific to join_block. Any chord-op loop that reads back a sibling's
sort_key after a write needs to track the new value locally or wait
for the outbound projector to quiesce. Worth pinning in the
architectural notes — see open follow-up below.

## Updated test

`join_block_into_parent_reparents_grandchildren_to_old_slot` →
`join_block_into_parent_with_grandchildren_is_refused`. Same fixture,
asserts the no-op (`p.content` unchanged, `A` still present, X/Y still
under A). The test name documents the LogSeq parity.

## Open follow-ups

- **Pin the SQL-projection-race rule for chord-op loops**: any chord-op
  loop that reads a sibling's just-written sort_key needs to use a
  local variable (or wait for outbound quiescence). The
  `move_to_position` helper is safe for one-shot use but not safe
  inside a tight loop that depends on cross-iteration ordering. Worth
  capturing as a memory entry and/or an archlint heuristic.
- **F4 (parent_id has the same race)**: Phase 3.5 already had `move_block`'s
  per-call `move_to_position` using a single round of queries; that's
  safe. The race only bites the iterative pattern. No change there.
